## 一、工期估算（基于实测吞吐外推）

### 1.1 实测基准（四个已完成任务的真实耗时）

| 时间段 | 完成内容 | 产出规模 |
|---|---|---|
| 约 54 min | M0 契约冻结 | 4 份契约文档 1880 行 + 验收记录 |
| 约 51 min | 前端准备块（Vue 3） | 29 文件 2291 行 |
| 约 19 min | 选型落地（lucide + uPlot） | 依赖 + 图表封装 + 图标替换 |
| 约 18 min | 库收口层 + 门禁 | 收口组件 + check-drift 门禁 |

**基准结论**：约 2.5 小时完成 4 个任务、产出约 5000 行，平均每任务 20~55 分钟（含独立验收）。

> 这 4 项属 M1 的前置准备，不计入 `docs/11` 的里程碑编号。

### 1.2 剩余里程碑预估

| 里程碑 | 预估执行 | 难点 / 风险 |
|---|---|---|
| M1 骨架跑通 | 1.5~2 h | 后端从零 + 双通道认证 + 路径白名单 + 前后端联调 |
| M2 单格式压缩 | 1.5~2 h | 压缩链路 + 事件驱动进度 |
| M3 任务系统 | 2.5~3.5 h | **核心**：队列 / 状态机 / 落盘 / SSE 快照 |
| M4 多格式插件化 | 1.5~2 h | 注册表 + 4 个格式包 |
| M5 删除原文件 | 2~2.5 h | **最危险**：校验 / 回收站 / 二次确认，含安全测试 |
| M6 黑名单与预检 | 1~1.5 h | 三层黑名单 + 2 倍空间预检 |
| M7 性能看板 | 1.5~2 h | uPlot 六卡片 + 指标采集 |
| M8 打磨与触屏 | 2~2.5 h | 右键菜单 / 快捷键 / 拖拽 / 触屏兼容 |
| M9 APK 准备 | 0.5~1 h | API 冻结 + PWA |

**合计：14~19 小时纯执行时间。**

### 1.3 折算成工作日

- **连续推进**（每天 6~8 小时有效开发，里程碑一次过）：约 **2~3 个工作日**
- **按实际节奏**（含选型讨论、变更返工、每轮验收往返）：约 **3~5 个工作日**

### 1.4 会拖慢的因素（本项目实际发生过）

| 因素 | 实例 | 影响 |
|---|---|---|
| 选型 / 契约变更 | 原生 JS → Vue 3；图标与图表库未定；补收口层 | 每次变更带一次返工 + 重派任务 |
| 环境坑 | 工作区 NFS `noexec`；依赖目录被清理需重装 | 排查与方案验证耗时 |
| 核心里程碑返工 | M3（核心架构）、M5（唯一会丢数据的功能） | 验收不会一次过 |
| 验收往返 | 每轮独立复核（含复现门禁变红等） | 每轮 10~20 分钟 |

### 1.5 加速条件

契约已冻结（M0 完成）是最大有利条件；只要**不再改选型**、每个里程碑一次通过，就能贴近 2~3 个工作日那条线。

## 二、模型分工

### 2.1 模型能力速览

| 模型 | 核心优势 | 主要短板 |
|---|---|---|
| **DeepSeek-V4-Flash** | 极致性价比、Agent 任务可靠、前端组件能力强 | 纯文本，无法直接识图 |
| **DeepSeek-V4.1-Flash** | 综合能力全面提升；编程与 Agent 能力突出；原生多模态视觉理解 | 需持续多步推理的硬核 Agent 场景仍可能陷入错误循环 |
| **GLM-5.3-Flash** | 综合智能指数高；编程能力与顶级模型持平；原生多模态；**漏洞发现能力突出** | 输出价格略高；输出速度较慢 |

### 2.2 按里程碑的选型建议

| 里程碑 | 主力 | 辅助 | 分工理由 |
|---|---|---|---|
| **M0 契约冻结** | DeepSeek-V4.1-Flash | GLM-5.3-Flash | 架构设计能力强，适合定 API 与插件契约；GLM 审查契约安全性（路径白名单、错误码） |
| **M1~M2 骨架与单格式压缩** | DeepSeek-V4.1-Flash | DeepSeek-V4-Flash | V4.1 前端组件强且多模态（可"看着"设计稿写前端），后端路由与压缩逻辑效率高；V4-Flash 写单测与文档（性价比高） |
| **M3 任务系统（核心）** | DeepSeek-V4.1-Flash | GLM-5.3-Flash | V4.1 的 Agent 与工具调用能力适合复杂队列、状态机与持久化；GLM 审计边界条件（磁盘满、任务冲突） |
| **M4 多格式插件化** | DeepSeek-V4.1-Flash | GLM-5.3-Flash | V4.1 编码速度更快；GLM 审查 zstd 集成安全性与各插件错误处理完备性 |
| **M5 删除原文件（最危险）** | **GLM-5.3-Flash** | DeepSeek-V4.1-Flash | GLM 的漏洞发现能力适合白盒审查，专门"找茬"，确保「校验失败不删除」「删除可恢复」等不变量不被违反；V4.1 按审计报告修复 |
| **M6~M8 黑名单 / 看板 / 打磨** | DeepSeek-V4.1-Flash | GLM-5.3-Flash | V4.1 处理黑名单匹配、指标采集、看板可视化；GLM 审查前端安全性与触屏兼容性 |
| **M9 APK 准备** | DeepSeek-V4.1-Flash | DeepSeek-V4-Flash | V4.1 梳理并冻结 API；V4-Flash 生成 PWA 的 manifest 与 Service Worker |

### 2.3 总体分工原则

- **DeepSeek-V4.1-Flash 是主力**：负责"把东西做出来"—— 速度快、编程与 Agent 能力强，是推进进度的引擎
- **GLM-5.3-Flash 是关键场景的补充**：负责"确保做出来的东西没问题"，尤其在 M5 这类高风险环节，其安全审计能力是宝贵防线
- **预算允许时**：可在 M0 架构评审与 M5 安全审计两个节点，临时引入顶级模型做一次"终审"；日常开发中这套组合已足够覆盖绝大部分工作

### 2.4 实际执行方式

| 项 | 做法 |
|---|---|
| **主开发** | DeepSeek-V4.1-Flash，同一成员持续推进；常规里程碑不新开成员 |
| **审计方**（仅 M5 等高风险环节） | GLM-5.3-Flash，**只写审计报告、不改代码**，与实现方写入范围物理不重叠 |
| **验收方** | 独立复核，不依赖成员自评；复跑套件、亲手复现关键路径 |
| **创建时能否指定模型** | 不能 —— 只能创建后切换，且切换需等成员空闲 |
| **切换是否生效的可靠判据** | 会话日志中 `request/header` 事件的 `data.header.config.{provider, model}`，**连续多轮**都是新模型才算持久生效。切换回执只表示"已写入意图"，不是生效证据 |

> **教训**：**切换回执 ≠ 生效**。缺少可靠查询手段时，记录应写「待验证」而不是断言。

### 2.5 M5 双成员协作方案（删除原文件阶段）

M5 是本项目**唯一会丢数据**的里程碑，因此不沿用"单成员推进"，而采用**双成员 + 串行分工**：

| 角色 | 模型 | 写入范围 | 职责 |
|---|---|---|---|
| **审计方** | GLM-5.3-Flash | `docs/audit/`（只写审计报告） | 白盒审查删除链路：逐条核 INV-01（先校验后删）、回收站可恢复、二次确认、并发竞态、极端场景（磁盘满 / 中断 / 权限 / 符号链接） |
| **实现方** | DeepSeek-V4.1-Flash | `server/`、`web/`、`scripts/` | 实现删除流程；按审计报告逐条修复；提供可复跑的不变量脚本 |

**硬约束：不并发写文件。** 两个角色的写入范围物理不重叠 —— 审计方只写 `docs/audit/`，实现方只写代码与脚本。这同时满足"审计方不写代码"的独立性要求。

**串行时序**（用共享任务的 `blocked_by` 表达依赖，不靠人工记顺序）：

1. 实现方完成 M5 初版（删除链路 + `delete.mode` + 回收站）
2. 审计方接入 → 产出审计报告（**只读代码、不改代码**）
3. 实现方按报告逐条修复
4. 审计方复验（复跑不变量脚本 + 逐条复查修复点）
5. 验收方终验：独立构造「校验失败 / 中途中断 / 磁盘满 / 权限不足」等场景，确认**原文件绝对不丢**

**为什么要两个角色**：删除流程的审计需要"不信任实现"的视角 —— 同一方既实现又自审，会沿用自己的假设，而 M5 恰恰是最不能靠假设的地方。审计方不写代码，也避免了与实现方抢改同一批文件。
