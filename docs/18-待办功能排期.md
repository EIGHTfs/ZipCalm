## ① 7z / rar 格式支持

### 目标

让 7z（写 + 读）与 rar（只读，rar 无自由写入实现）成为可选的格式插件。

### 关键设计

- **插件化落地**：新增 `server/plugins/formats/sevenzip/index.js` 与 `rar/index.js`，实现 `docs/03` 的契约（`id` / `name` / `ext` / `extAliases` / `mime` / `levelRange` / `defaultLevel` / `available` / `unavailableReason` / `create` / `list` / `test` / `estimate` / `extract`）。注册表扫描自动加载，**不改总入口**
- **`available()` 必须真探测**：`7z` 与 `unrar` 二进制是否存在且可执行（`ZC_7Z_BIN` / `ZC_UNRAR_BIN` 可覆盖路径）；不可用则该格式置灰并显示 `unavailableReason()`
- **进度来源**：外部二进制的 stdout（`7z a -bsp1` 输出百分比；`unrar` 输出逐文件）；解析失败时降级为「文件级进度」而不是报错
- **rar 只读**：`create()` 返回不可用并说明原因（无自由许可的写入实现），只支持 `list` / `test` / `extract`
- **条目安全**：沿用 `_shared/entrySafety.js` 的 zip-slip 防护，不各写一份

### 依赖与前提

- 目标机需装 `7z`（群晖 `/bin/7z` 已确认存在）与 `unrar`（`/bin/unrar` 已确认存在）
- 非群晖环境可能缺失 → 靠 `available()` 降级，不假设

### 验收要点

- [ ] 7z 压缩 + 解压往返，逐文件 hash 一致
- [ ] rar 解压现有 rar 包，内容一致；`create()` 明确返回不支持
- [ ] 二进制缺失时该格式置灰，`unavailableReason()` 给出可操作提示（如「未找到 7z 命令，请安装或设置 ZC_7Z_BIN」）
- [ ] 移走 `sevenzip/` 目录，其余格式照常工作（插件化验收）
- [ ] 进度在压缩大目录时连续更新，不出现「卡住不动」

### 风险

- 外部二进制输出格式随版本变化 → 解析要宽松（拿不到百分比就退化为文件级）
- 密码支持（功能 ②）会改动 `create()` 签名 → **预留 `options.password` 参数位**

## ② 压缩包密码

### 目标

压缩时可设置密码；解压加密包时可输入密码。

### 关键设计

- **写入**：`archiver` 不支持 AES 加密 → zip 加密需走 7z 二进制或专用库；7z 原生支持 `-p<password>` 与 `-mhe=on`（加密文件名）
- **读取**：加密 zip/7z 需带密码；错误密码要能**明确区分**「密码错」与「文件损坏」
- **密码不落日志**：日志与 API 响应中对密码脱敏（只记「已设置密码」）
- **密码不进任务持久化**：`tasks.json` 不存明文密码；若必须跨重启保留，需加密存储并明确风险
- **压缩后自测**：设了密码就必须用该密码试解一次（`test()` 带密码），失败则任务 `failed` 且**不删原文件**
- **删除原文件前的额外护栏**（参考 MT 管理器的做法）：删除前必须确认「包密码已通过试解验证」+「已明确提示用户妥善保存密码（密码丢失后压缩包无法恢复）」，避免永久丢数据
- **常用密码自动尝试**（借鉴 MT 管理器的设计，证据见 `docs/research/mt-apk-reverse.md` §2.3）：
  - 维护「常用密码」列表（用户自建），解压加密包时**按顺序自动尝试**，全部失败才让用户手输
  - **记住最近一次成功匹配的密码**，下次优先试
  - 压缩时也可从常用密码里快速选择
  - **为什么值得做**：直接消灭「忘记密码 = 数据不可读」这个不可逆风险，比每次手输体验好得多

### 依赖

- **必须在 ① 之后**：加密写入依赖 7z 二进制
- 若不做 ①，则 zip 加密需引入额外库（如支持 AES 的 zip 库），成本更高

### 验收要点

- [ ] 设密码压缩 → 用密码解压成功；无密码解压失败且提示「需要密码」
- [ ] 错误密码 → 提示「密码错误」而非「文件损坏」
- [ ] 密码不出现在日志、API 响应、`tasks.json`
- [ ] 密码压缩 + 删除原文件 → 删除前已验证密码可解
- [ ] 忘记密码场景：UI 明确警告「密码丢失后压缩包无法恢复」并要求确认

### 风险

- **密码丢失 = 数据不可读**（若同时删了原文件 = 永久丢失）→ 这是本项目第二个「不可逆」功能，风险等级与删除、硬链接去重同级
- 加密会显著降低压缩速度与压缩率 → UI 要提示

## ③ 硬链接预检提示

### 目标

选 zip 压一个含硬链接的目录时，提前告诉用户「ZIP 会存多份，体积会翻倍，建议用 TAR」。

### 背景（实测数据，见 `docs/06` §六）

同一份 2MB 数据做两个硬链接：
- 压 **zip** → 4,001,476 字节（**翻倍**）
- 压 **tar** → 2,002,432 字节（单份）

预检现在用 `lstat().size` 逐条累加，对 zip 恰好准确、对 tar 偏保守（多算但不会漏拦）。**问题不是不安全，是用户看不见差异。**

### 关键设计

- **采集**：在现有源遍历（`sourceWalk.js`）中顺手统计 `ino` 重复数（同一 `dev + ino` 出现 ≥2 次即为一组硬链接），成本很低
- **计算**：预检结果同时给出「逻辑大小」与「按所选格式估算的实际产出」；差异超阈值（如 >10%）时提示
- **提示文案**：`检测到 N 组硬链接（共 M 个文件）：当前格式 ZIP 会各存一份，预计产出 X GB（逻辑大小 Y GB）；改用 TAR 可只存一份`
- **不改删除逻辑**：这是纯提示，不影响 INV-01/02/03
- **跨文件系统**：只有同 `dev` 且同 `ino` 才算硬链接（不同分区的相同 ino 不是）

### 验收要点

- [ ] 造两个硬链接文件 → 选 zip 时预检提示「检测到 1 组硬链接」
- [ ] 切到 tar → 提示消失或改为「TAR 会保留硬链接」
- [ ] 无硬链接的目录 → 无提示（不打扰）
- [ ] 不同分区的相同 ino 不被误判
- [ ] 提示不阻塞压缩（用户可忽略继续）

### 风险

低。唯一注意点：遍历大目录时多算一次 `ino` 统计，需确认不显著增加预检耗时（`ino` 来自已有的 `lstat` 结果，无额外 syscall）。

## 执行纪律（每项都必须遵守）

### 一、验证方式：浏览器实际点击，不是只跑 API

**这是硬要求**，任何涉及网页的功能都必须：

1. **用浏览器插件实际打开页面、点击按钮、走完整流程** —— 不用 curl 代替
2. **看画面**：布局是否错乱、文字是否可读、按钮是否可见可点、空态/错误态是否友好
3. **截图留证**：关键步骤与最终结果各一张
4. **窄视口（390×844）必看** —— 桌面正常不代表手机正常（曾因此抓出侧栏挤成竖排、底部栏撑宽页面等 3 个 bug）
5. **API 只用于交叉验证**（如确认产物真的落盘、任务状态真的变了），**不能替代界面验收**

**理由**：API 通 ≠ 页面正常。历史上多次出现「接口返回 200，但按钮被遮挡点不到 / 文字显示成空 / 元素挤成一列」—— 这些只有真看页面才能发现。

### 二、收尾四步（`docs/14` §一）

审计 + 顺手优化 → 全套验收（15 套）→ 停服务 → 带证据汇报。

### 三、每项单独提交

一个功能一个 commit，message 写清做了什么与验证方式；推送前报告。
