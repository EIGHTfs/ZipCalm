## 附一：压缩性能实测（2026-10-24，本机）

**测试集 A**：89 MB 混合数据（20MB 随机 + 20MB 文本 + 15MB 高重复 + 36MB APK）
**测试集 B**：1.5 MB 真实源码与文档（本仓库 `server/` + `web/src/` + `docs/`）

| 方案 | A 耗时 | A 产物 | B 耗时 | B 产物 |
|---|---|---|---|---|
| zstd **level 3** | **0.85 s** | 53 M | 0.74 s | 418 K |
| zstd **level 19** | 36.1 s | 53 M | 1.83 s | **335 K** |
| 7z **-mx5**（LZMA2） | 19.0 s | 53 M | **0.66 s** | **331 K** |
| 7z **-mx9** | — | — | 0.79 s | 329 K |
| tar.gz **-6** | — | — | 0.08 s | 441 K |

**三条结论**：

1. **「zstd 比 7z 快 3~5 倍」只在 level 3 成立** —— 实际快 **22 倍**（0.85s vs 19s），但压缩率差 **26%**（418K vs 331K）
2. **zstd level 19 能追上 7z 的压缩率**（335K vs 331K，差 1.2%），但**比 7z -mx5 慢一倍**（36s vs 19s）
3. **7z 的价值在「中间档」**：`-mx5` 用 0.66s 拿到 331K（比 zstd 19 快 2.8 倍、率一样）

> **所以「tar.zst 完美替代 7z」不成立** —— 同等压缩率下 zstd 更慢，同等速度下 zstd 压缩率更差。
> 但 **zstd 的 level 可调反而是优势**：日常用 level 3（极快），归档用 level 19（逼近 7z），比"只有一个档位"的 7z 更灵活。
> 而且**两者都不需要外部依赖之外的运行时** —— zstd 在 Node 内置，7z 要装二进制。

## 附二：压缩包密码的写入引擎（需决策）

**实测确认的能力边界**：

| 能力 | 现状 |
|---|---|
| `archiver` 写加密 zip | ❌ **不支持**（源码中无 password/encrypt/AES 相关） |
| `unzipper` 读加密 zip | ✅ 支持（有 `Decrypt.js`，读 ZipCrypto 传统加密） |
| 系统 `zip -P` | ⚠️ 需探测命令是否存在 |

**所以要「写加密包」，必须选一个引擎**：

| 方案 | 加密强度 | 外部依赖 | 说明 |
|---|---|---|---|
| A. 系统 `zip -P` | 弱（ZipCrypto，可被已知明文攻击破解） | 需 `zip` 命令 | 零新增 npm 依赖，但安全性不足 |
| B. `7z` 二进制 | 强（AES-256，可选加密文件名） | 需 `7z` 命令 | 与「7z 格式」共用同一引擎 |
| **C. 纯 JS AES 库** | **强（AES-256）** | 新增 1 个 npm 依赖 | **零系统依赖** |

### 决策：选 C，具体用 `archiver-zip-encrypted`

**核实结果**（npm registry 实时查询，2026-10-24）：

| 项 | 结果 |
|---|---|
| 版本 | `2.0.0` |
| 描述 | `AES-256 and legacy Zip 2.0 encryption for Zip files` |
| 依赖 `archiver` | `^7.0.0` —— **项目当前 7.0.1 ✓ 兼容** |
| 加密实现 | 依赖 `aes-js`（**纯 JS，无 native 编译**） |
| 引擎要求 | `node >=16`（项目要求 ≥22.15 ✓） |
| 最后更新 | 2024-03-23 |

**为什么选它而不是 `@zip.js/zip.js`**：它是 **archiver 的插件**，能直接复用现有流式压缩管道（`archiver` → 进度事件 → 校验）；`@zip.js/zip.js` 是独立的完整库，接入等于并行两套压缩链路。

**因此 7z 格式彻底不做** —— 密码功能不再依赖它。

### 连带影响：7z 从排期移除

原计划里 7z 存在的唯一不可替代理由是「写加密包」。改用 `archiver-zip-encrypted` 后：

- 压缩率：`tar.zst`（level 19）已能覆盖（差距 1.2%，见 §附一）
- 加密：纯 JS 库解决
- 7z 格式本身：**用户不需要**（`tar.zst` 更通用且零依赖）

**结论：7z 不做，也不留占位插件** —— 留空占位会让"以后要不要做"悬着，反而增加决策负担。若将来真有需求，按插件契约加一个包即可（`plugins/formats/` 加目录即注册）。

## 附三：RAR 的法律边界（2026-10-25 核实 RARLAB 官方 EULA）

### 结论：压缩**能做**，但方式受限 —— 不是「不能生成 RAR」，而是「不能打包分发 RAR 二进制」

核实来源：RARLAB 官方 EULA（`rarlab.com/license.htm`）+ 下载页（`rarlab.com/download.htm`）。

**EULA 原文三条关键**：

> The software is distributed as **try before you buy**. This means that anyone may use the software during a test period of a **maximum of 40 days** at no charge. Following this test period, the user must purchase a license to continue using the software.

> The software's **unlicensed trial version may not be distributed inside of any other software package** without written permission.

> Nobody may distribute separate parts of the package, **with the exception of the UnRAR components**, without written permission.

**从这三条推出**：

| 做法 | 合法性 | 依据 |
|---|---|---|
| **调用用户自己安装的 `rar` 命令** | ✅ **合法** | ZipCalm 不打包、不分发 RAR；用户自行下载安装并自负许可（40 天试用 / 购买）。程序只做「探测 `rar` 是否存在」 |
| **把 `rar` 二进制打进 ZipCalm** | ❌ **禁止** | EULA：unlicensed trial version 不得放进其他软件包；RAR 压缩组件不得单独分发 |
| **随包附带 `unrar`** | ⚠️ **允许但不必** | EULA 明确 UnRAR 组件可单独分发；不过探测系统已有的更省事 |
| **自己实现 RAR 压缩器** | ❌ **禁止** | unRAR 源码许可禁止用于创建压缩器；RAR 算法未公开完整规范 |
| **用 7z 生成 rar** | ❌ 技术不可行 | 7z 只能读 rar，不能写 |

### 因此的正确做法

**RAR 压缩 = 可选能力，靠 `available()` 探测用户环境里的 `rar` 命令**：

```
有 rar 命令  → 允许用户选 RAR 格式，压缩走 `rar a -p<pwd> out.rar files`
没有 rar     → RAR 不出现在压缩格式列表里（或置灰 + unavailableReason 提示）
```

`unavailableReason()` 提示文案应说明：**「需自行安装 RAR（RARLAB 官方，试用 40 天后需购买许可）；本软件不附带 RAR 二进制」** —— 把许可责任明确交回用户。

**这与调用 `7z` / `unrar` 完全同一个模式**：程序不内置算法、不分发二进制，只探测并调用用户环境里用户自己安装的合法工具。所以 RAR 压缩与 7z、unrar 在法律上属同一类做法，**不是禁区**。

### 本机现状（2026-10-25 实测）

```
unrar  → /bin/unrar（UNRAR 5.70 freeware，仅解压）✓
rar    → 不存在 ✗
7z     → /bin/7z ✓（能读 rar，不能写）
```

**因此当前只能做 RAR 解压**；RAR 压缩路径要等用户自己装了 `rar` 才会亮起 —— 这也正好符合「`available()` 真探测 + 置灰」的设计。

## 附四：7z WASM 三方案对比（2026-10-24 实测，三库均已 npm 安装运行）

### 结论：7z 不需要外部二进制 —— 且**多线程 WASM 比系统的旧 p7zip 还快**

| 指标 | 7z-wasm@1.2.0 | sevenzip-wasm@26.5.0 | **js7z-tools@2.5.0**（JS7z） | 系统原生 p7zip 16.02 |
|---|---|---|---|---|
| 上游 7-Zip 版本 | 24.09 | **26.05**（2026-10-21） | 25.01（2025-08） | 16.02（**2016 年**） |
| 线程 | 1 | 1 | **3（MT，随 CPU 自适应）** | 3 |
| real.tar 1.5 MB `-mx5` | 924 ms / 330 K | 648 ms / 332 K | **680 ms / 332 K** | 312 ms / 332 K |
| data.tar 89 MB `-mx5` | 38.3 s | 38.1 s | **16.8 s** | 19.7 s |
| 产物大小（89MB） | 53278 K | 53278 K | 53278 K | 53282 K |
| 内存峰值（89MB 输入） | 437 MB（上轮曾测 618 MB，波动大） | 422 MB | 460 MB | — |
| WASM 启动 | 20 ms | 18 ms | 26 ms | — |
| npm 最后发布 | **2025-06（停更 ~16 个月）** | **2026-10-21（3 天前）** | 2025-10-05 | — |
| 周下载量 | 29,615 | 196 | 63 | — |
| 产物经原生 `7z t` 互验 | ✓ Ok | ✓ Ok | ✓ Ok | — |
| 解压回写真实盘（NODEFS） | ✓ | ✓ | ✓（嵌套 tar.gz 需两步，与原生一致） | — |

**四条关键发现**：

1. **`js7z-tools`（JS7z）是唯一多线程版** —— 89 MB 实测 **16.8 s，反超系统原生 p7zip 的 19.7 s**（原生是 2016 年老版本且算法代差）。产物大小与另两家完全一致
2. `sevenzip-wasm` **维护最活跃**（3 天前更新、紧跟上游 26.05），但单线程 → 比 MT 慢 2.3 倍
3. 我此前推荐的 `7z-wasm` 综合垫底：最慢、停更 16 个月、上游版本最老 —— **结论作废，以本篇为准**
4. **集成陷阱：`js7z-tools` MT 模式的 `callMain` 是异步的，完成信号必须等 `onExit` 回调** —— 实测踩坑：同步检查解包结果误报「缺目录」，实际稍后才落盘（原生 CLI 的同步语义在这里不成立）

**共性限制**：三者都是 32 位 ILP32 WASM（内存 4 GB 地址上限）→ 超大输入仍建议回退原生或改用 `tar.zst`；WASM 内存峰值 420~460 MB 在 NAS 上可控但仍应设单任务输入上限（建议 2 GB 提示）。

### 建议方案（修订：三级回退链，与 zstd 同构）

```
① 系统有 7z / 7za        → 用原生（零新增依赖，先探测再决定）
② 否则用 js7z-tools      → WASM MT，实测 ≥ 旧 p7zip，1.9 MB，无外部依赖
③ 不想引入任何依赖        → 不装，该格式置灰 + unavailableReason 说明
```

**许可合规**：三者均为 LGPL + **unRAR 限制许可** —— 同样**能解 rar、不能生成 rar**（不改变 §附三结论）；MIT 项目引用 LGPL 库属正常用法，分发时保留包内 license 文件即可。`sevenzip-wasm` 若更看重"跟得上上游安全修复"，可作备选（26.05 vs 25.01）。

### 什么时候值得做

| 场景 | 判断 |
|---|---|
| 只压日常文件与备份 | ❌ 不必 —— `tar.zst` level 19 率只差 1.2%，速度快得多 |
| 需要产出 7z 给 Windows 用户 | ✅ 值得 —— 7z 在 Windows 普及度高于 tar.zst |
| 追求极限体积 | ⚠️ 边际收益小（1.2%） |
| NAS 内存紧张 + 常压大文件 | ⚠️ 可行但设上限 —— MT 版 460 MB 峰值、速度已不输旧原生；>2 GB 单任务建议改 `tar.zst` |

## ① RAR 解压（只读）

### 目标

支持**解压** rar 包；**不做压缩**（法律约束，见 §附三）。

### 关键设计

- **插件化落地**：新增 `server/plugins/formats/rar/index.js`，实现 `docs/03` 的契约。注册表扫描自动加载，**不改总入口**

- 注册表**自动发现**（放一个目录即注册），未改总入口
- 解压流程：`unrar x` 先解到**目标目录旁边的中转目录** → 逐条过 `_shared/entrySafety.planTargets`（zip-slip / 绝对路径 / 符号链接 / 不覆盖同名）→ `writePlan` 搬进目标目录；中转目录无论成败都清掉
- 错误映射：**缺密码与错密码在 unrar 侧同为 exit 11 + 同一句提示**，只能按"我们有没有传密码"区分 `MISSING_PASSWORD` / `BAD_PASSWORD`；损坏包 exit 1 → `ARCHIVE_CORRUPTED`
- 进度：外部阶段只有文件名（unrar 不报字节数），搬移阶段给精确字节；两段都单调不减（避免回退）

## ② 压缩包密码（**已完成**，实现与验收详情见 `docs/19-压缩密码与能力插件设计.md` §八/§九）

> 状态：**全部落地**。压缩（AES-256 / ZipCrypto，能力插件架构、压完自测、明文三通道脱敏、删除护栏）与解压（加密包识别、7z 统一解包、密码错 / 缺密码 / 包损坏三态区分、zip-slip 防线不因加密绕过）均已实现并验收。
>
> **常用密码本（自动尝试 / 记住最近成功）已决定搁置**，不做。理由：密码输入只走用户手输已够用，而密码本要落盘保存用户密码，多一份凭据存储面就多一份泄漏风险与运维负担；真有高频复用需求时再单独评估（届时须先定密钥保护方案，不能明文落盘）。

### 目标

压缩时可设置密码；解压加密包时可输入密码。

### 关键设计

- **写入**：`archiver` 本身不支持加密 → 用 **`archiver-zip-encrypted`**（archiver 插件，AES-256，底层 `aes-js` 纯 JS），复用现有流式管道；**不依赖任何外部二进制**（选型依据见 §附二）
- **读取**：`unzipper` 已内置 `Decrypt.js`，可读 ZipCrypto 加密包；AES-256 包的读取能力需实现时实测确认
- **错误区分**：密码错要能**明确区分**「密码错」与「文件损坏」（MT 的做法是统一文案，我们可以做得更清楚）
- **密码不落日志**：日志与 API 响应中对密码脱敏（只记「已设置密码」）
- **密码不进任务持久化**：`tasks.json` 不存明文密码；若必须跨重启保留，需加密存储并明确风险
- **压缩后自测**：设了密码就必须用该密码试解一次（`test()` 带密码），失败则任务 `failed` 且**不删原文件**
- **删除原文件前的额外护栏**（参考 MT 管理器的做法）：删除前必须确认「包密码已通过试解验证」+「已明确提示用户妥善保存密码（密码丢失后压缩包无法恢复）」，避免永久丢数据
- **常用密码自动尝试**（借鉴 MT 管理器的设计，证据见 `docs/research/mt-apk-reverse-04-借鉴点与结论.md`）：
  - 维护「常用密码」列表（用户自建），解压加密包时**按顺序自动尝试**，全部失败才让用户手输
  - **记住最近一次成功匹配的密码**，下次优先试
  - 压缩时也可从常用密码里快速选择
  - **为什么值得做**：直接消灭「忘记密码 = 数据不可读」这个不可逆风险，比每次手输体验好得多

### 依赖

- **不依赖 ①**：加密写入用 `archiver-zip-encrypted`（纯 JS），与 RAR 解压插件无关
- 新增 1 个 npm 依赖：`archiver-zip-encrypted@2.0.0`（依赖 `archiver ^7.0.0`，与项目 7.0.1 兼容）
- **加密仅对 zip 生效**：`tar.*` 系列没有标准加密方案 → UI 上选 tar 系列时密码项置灰并说明

### 验收要点

- [ ] 设密码压缩 → 用密码解压成功；无密码解压失败且提示「需要密码」
- [ ] 错误密码 → 提示「密码错误」而非「文件损坏」
- [ ] 密码不出现在日志、API 响应、`tasks.json`
- [ ] 密码压缩 + 删除原文件 → 删除前已验证密码可解
- [ ] 忘记密码场景：UI 明确警告「密码丢失后压缩包无法恢复」并要求确认

### 风险

- **密码丢失 = 数据不可读**（若同时删了原文件 = 永久丢失）→ 这是本项目第二个「不可逆」功能，风险等级与删除、硬链接去重同级
- 加密会显著降低压缩速度与压缩率 → UI 要提示

## ③ 硬链接预检提示

### 目标

选 zip 压一个含硬链接的目录时，提前告诉用户「ZIP 会存多份，体积会翻倍，建议用 TAR」。

### 背景（实测数据，见 `docs/06` §六）

同一份 2MB 数据做两个硬链接：
- 压 **zip** → 4,001,476 字节（**翻倍**）
- 压 **tar** → 2,002,432 字节（单份）

预检现在用 `lstat().size` 逐条累加，对 zip 恰好准确、对 tar 偏保守（多算但不会漏拦）。**问题不是不安全，是用户看不见差异。**

### 关键设计

- **采集**：在现有源遍历（`sourceWalk.js`）中顺手统计 `ino` 重复数（同一 `dev + ino` 出现 ≥2 次即为一组硬链接），成本很低
- **计算**：预检结果同时给出「逻辑大小」与「按所选格式估算的实际产出」；差异超阈值（如 >10%）时提示
- **提示文案**：`检测到 N 组硬链接（共 M 个文件）：当前格式 ZIP 会各存一份，预计产出 X GB（逻辑大小 Y GB）；改用 TAR 可只存一份`
- **不改删除逻辑**：这是纯提示，不影响 INV-01/02/03
- **跨文件系统**：只有同 `dev` 且同 `ino` 才算硬链接（不同分区的相同 ino 不是）

### 验收要点（2026-10-27 实测结果）

- [x] 造硬链接文件 → 选 zip 时预检提示「检测到 1 组硬链接」 —— 实测 3 个名字同 1MB inode：`groups=1 files=3 duplicateBytes=1048576 estimatedBytes=3145728 hint=true`
- [x] 切到 tar → 改为「当前格式会保留硬链接，同一份数据只存一份，比各存一份省 X MB」 —— 实测 `preservedByFormat=true estimatedBytes=1048576 hint=false`
- [x] 无硬链接的目录 → 无提示（抽屉里不渲染任何提示节点，不留空框）
- [x] 不同分区的相同 `ino` 不被误判（判定要求 `dev` 与 `ino` 同时相同）
- [x] 提示不阻塞压缩（提示在场时点「开始压缩」建任务成功、产物落盘）
- [x] 重复占比低于阈值（10%）时不提示，避免打扰

### 环境限制：CIFS/SMB 挂载上检测不到硬链接（实测，非实现缺陷）

CIFS 服务端把硬链接呈现成**各自独立、link count 也不一致**的条目，`dev+ino` 判定自然失效：

```
# 本地盘（btrfs）：三个名字同一个 inode，检测正常
a.bin  dev=38 ino=366 links=3
b.bin  dev=38 ino=366 links=3
c.bin  dev=38 ino=366 links=3

# CIFS 挂载：ln 报告成功，但每个名字拿到不同 inode
orig.bin   dev=40 ino=6375157 links=3
link1.bin  dev=40 ino=6375159 links=1   ← inode 不同
link2.bin  dev=40 ino=6375160 links=1   ← inode 不同
```

结果是预检给出 `groups: 0`、不提示。

- **影响面**：只有把 CIFS 挂载当浏览根的部署会看到；本地盘（btrfs / ext4 / xfs）正常。
- **不做特殊适配**：CIFS 的 `ino` 本身不可靠，按名字或 mtime 猜会误判，代价比收益大。
- **兜底**：即使检测不到，用户选 TAR 时**永远只存一份**（格式语义决定，与检测无关）—— 功能退化为「少一条建议」，不会给出错误结论。

### 风险

低。`ino`/`dev` 来自已有的 `lstat` 结果，无额外 syscall；大目录遍历不增加 I/O 次数。

## 执行纪律（每项都必须遵守）

### 一、验证方式：浏览器实际点击，不是只跑 API

**这是硬要求**，任何涉及网页的功能都必须：

1. **用浏览器插件实际打开页面、点击按钮、走完整流程** —— 不用 curl 代替
2. **看画面**：布局是否错乱、文字是否可读、按钮是否可见可点、空态/错误态是否友好
3. **截图留证**：关键步骤与最终结果各一张
4. **窄视口（390×844）必看** —— 桌面正常不代表手机正常（曾因此抓出侧栏挤成竖排、底部栏撑宽页面等 3 个 bug）
5. **API 只用于交叉验证**（如确认产物真的落盘、任务状态真的变了），**不能替代界面验收**

**理由**：API 通 ≠ 页面正常。历史上多次出现「接口返回 200，但按钮被遮挡点不到 / 文字显示成空 / 元素挤成一列」—— 这些只有真看页面才能发现。

审计 + 顺手优化 → 全套验收（15 套）→ 停服务 → 带证据汇报。
