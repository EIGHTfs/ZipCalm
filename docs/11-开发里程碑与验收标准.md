# 11 开发里程碑与验收标准

> 定位：M0~M9 分步计划与逐条可测的验收标准。

## 一、规划需求

项目属中大型规模，需要分步计划大纲，以及每个里程碑的验收标准。

## 二、阶段划分总览

按"先打通主链路、再补细节、最后加固"的思路排，一共 9 个里程碑。每个里程碑有明确的可验收标准，**不通过不进下一阶段**。

| 阶段 | 名称 | 核心交付 | 估算 |
|---|---|---|---|
| M0 | 契约冻结 | API 规范 + 插件契约 + 数据模型 | 3~5 天 |
| M1 | 骨架跑通 | 能浏览、能登录、能调 API | 1 周 |
| M2 | 单格式压缩 | zip 能压、能看到进度 | 1~2 周 |
| M3 | 任务系统 | 任务列表、后台执行、状态落盘 | 1 周 |
| M4 | 多格式插件化 | zip/tar/tar.gz/tar.zst 全通 | 1~2 周 |
| M5 | 删除原文件 | 校验 + 回收站 + 二次确认 | 1 周 |
| M6 | 黑名单与预检 | 智能跳过 + 磁盘预检 | 1 周 |
| M7 | 性能看板 | 6 个卡片 + 2 秒轮询 | 1 周 |
| M8 | 打磨与触屏 | 快捷键、右键菜单、触屏兼容 | 1~2 周 |
| M9 | 手机端 | PWA（可添加到主屏幕）+ 移动端适配 | 3~5 天 |

**总计约 9~12 周（单人开发）。**

## 三、M0：契约冻结（最先做，不做完不许写代码）

**为什么放第一：** 你踩过的最大的坑，就是"AI 不看 SPEC 就写代码"。所以契约先定，后面所有开发都以契约为中心。

**交付物：**

- **API 规范文档**（OpenAPI 或 Markdown 表格）
  - 每个端点的输入、输出、错误码
  - 统一响应格式 `{ ok, data, error }`
  - 错误码枚举（DISK_FULL、PATH_NOT_FOUND、PERMISSION_DENIED、TASK_CONFLICT 等）
- **压缩插件契约**
  - 每个格式包必须实现的接口：ext、create、list、test、available、estimate
  - 明确边界：格式包只负责"怎么压"，不负责调度/删除/预检
- **数据模型**
  - 任务对象字段（UUID、状态机、进度结构）
  - 黑名单结构
  - 配置结构
- **不变量清单（这部分最关键）**
  - 原文件删除前必须通过完整性校验
  - 任务状态落盘，不依赖前端连接
  - 路径必须经过白名单校验
  - 磁盘预检：剩余空间 ≥ 待压文件 × 2

**验收标准：**

- □ 三个文档写完，能通过"换一个不熟悉项目的人读一遍就能说出怎么调用"的测试
- □ 错误码枚举覆盖所有已知失败场景
- □ 压缩插件契约里的方法签名确定，每个格式包都能对号入座

## 四、M1：骨架跑通（能浏览、能登录）

**交付物：**

- 服务端：HTTP 框架（Fastify 或原生 http）、路由骨架、认证中间件
- 文件浏览 API：列目录、文件详情
- 前端：登录页、文件列表页（只读）
- 路径白名单：从第一天就做，别等

**验收标准：**

- □ 能用用户名密码登录，拿到 Session
- □ 能浏览配置的根目录，不能浏览根目录之外的任何路径
- □ 尝试路径穿越（../、%2e%2e）返回 403
- □ 前端能展示文件列表，显示名称/大小/修改时间
- □ 目录可以进入，面包屑可以返回上级

**不通过的表现：** 能访问 /etc、/root、配置根目录之外的任何路径 → 打回重做。

## 五、M2：单格式压缩 + 解压（先跑通 zip）

**为什么只做 zip：** 先打通"选文件 → 压缩 → 进度 → 下载"的完整链路，再考虑多格式。贪多必崩。

**范围说明（含解压）**：压缩与解压共用同一条管道 —— 同一个格式包契约、同一套任务/进度/校验/删除机制，`extract` 与 `create` 对称。所以解压顺手做，边际成本低；不引入第二套流程。

**交付物：**

- zip 格式包：**`create`（写）用 archiver；`extract` / `list` / `test`（读）用 unzipper** —— archiver 是纯写入库、没有读能力，读侧必须另配（纯 JS、流式、无原生编译）。对齐 `docs/M0/插件契约.md` §3.4 / §3.4.1 / §3.5 / §3.6
- 压缩与解压的进度都走事件推送（文件级 + 字节级，≥100ms 节流）
- 前端：多选文件 → 压缩抽屉 → 开始压缩；选中压缩包 → 解压 → 可选「**解压后删除压缩包**」
- **解压安全**：zip-slip 防护 —— 归档内条目名含 `../`、绝对路径、盘符、symlink 指向目标目录外，一律拒绝
- **删除对称**：压缩侧的「保留原文件 / 删除原文件」与解压侧的「解压后删除压缩包」共用同一套「**先校验 → 再删**」机制，并统一受 `delete.mode` 约束（开发期 `log-only` 只记日志、不真删）

**验收标准：**

- □ 能选多个文件，点"压缩"，生成一个 zip；压缩过程进度实时更新（文件级：当前处理的文件名）
- □ 压缩包能用**系统 zip 工具**正常解压（外部工具交叉验证，不是自证）
- □ 能选中 zip → 解压到目标目录；解压过程进度实时更新
- □ **往返一致性（假数据 + hash）**：生成确定性假数据并**记录每个文件的 hash** → 压缩 → 解压 → 逐文件比对 hash **全部一致**（这是压缩/解压正确性的核心证据，不靠肉眼看文件名或数量）
- □ **zip-slip 拒绝**：构造含 `../` / 绝对路径 / symlink 逃逸的恶意 zip → 解压必须拒绝，且**不在目标目录之外写出任何文件**
- □ 「解压后删除压缩包」选项生效，且删除走「先校验 → 再删」（`delete.mode=log-only` 时只记日志、不真删）
- □ 压缩过程中刷新页面，重新进入后能查询到任务状态
- □ 压缩失败（如磁盘满）时给出明确错误

**特别注意：** 这个阶段的进度只是"能看"，还没做任务系统。任务状态暂时可以只在内存，M3 再落盘。

## 六、M3：任务系统（后台执行 + 状态落盘）

**为什么单独一个里程碑：** 这是整个项目的核心架构，压缩任务不受前端连接影响就在这里落地。

**交付物：**

- 任务管理器：任务队列、单任务执行、状态机
- 任务状态落盘（JSON 或 SQLite）
- SSE 端点 /api/v1/tasks/events
- 前端：底部任务条 + 任务列表抽屉
- 任务 API：创建、查询、取消、列表

**验收标准：**

- □ 关掉浏览器，任务继续跑
- □ 重新打开页面，能看到当前任务的实时进度
- □ 服务重启后，未完成的任务状态被标记为"中断"，可以重试
- □ 能取消正在执行的任务
- □ 同一时刻只有一个任务在执行（串行），后续任务排队
- □ 任务历史可查（最近 N 条）

**关键测试：** 手动 kill 服务进程，重启后状态文件里的任务状态应该是"中断"，且 .tmp 产物保留。

## 七、M4：多格式插件化

**交付物：**

- 格式注册表 + 插件契约落地
- 四个格式包：zip、tar、tar.gz、tar.zst
- tar 系列用 node-tar
- zstd 用 **Node ≥ 22.15 内置的 `node:zlib`**（零依赖、流式；回退链：内置 → 系统 `zstd` 命令 → 都不可用则该格式 `available()=false` 置灰）
- 前端：格式选择下拉

**验收标准：**

- □ 四个格式都能压
- □ 新增格式只需加一个包 + 注册，不改主逻辑
- □ 删除某个格式包，其余格式不受影响
- □ zstd 二进制不存在时，available() 返回 false，UI 上该选项置灰

**关键测试：** 把 zip 包的文件移走，其余格式仍然能正常压。

## 八、M5：删除原文件（最危险的里程碑）

**为什么单独一个里程碑：** 这是整个项目里**唯一会丢数据的功能**，必须独立验收。

**交付物：**

- 校验流程：压缩完成后，用 list() 或 test() 校验
- 删除流程：先标记 → 确认 → 进回收站 → 记录日志
- 前端：压缩设置里的"删除原文件"选项 + 二次确认弹窗

**验收标准：**

- □ 默认不删除原文件
- □ 勾选"删除原文件"后，二次确认弹窗明确列出"将删除 N 个文件、共 X GB"
- □ 压缩失败时，原文件绝不删除
- □ 校验失败（如压缩包损坏）时，原文件绝不删除
- □ 删除进回收站（.trash 或系统回收站），不是真删
- □ 删除操作有日志，可追溯

**关键测试：**

- 压缩一个 10 GB 的文件，中间 kill 进程 → 原文件必须还在
- 压缩完成后手动损坏压缩包 → 校验失败 → 原文件必须还在
- 正常压缩 + 删除 → 回收站里能找到原文件

## 九、M6：黑名单与磁盘预检

**交付物：**

- 三层黑名单：全局默认（**仅系统垃圾**：`Thumbs.db` / `.DS_Store` / `@eaDir`）、用户自定义、任务级临时
  - 注：全局默认最初含 jpg/mp4/zip 等 12 个「已压缩格式」，后移除 —— 打包不一定为省体积（如把照片打成一个包发给别人），默认静默跳过会违背意图。机制保留，用户可自行加入
- 前端：黑名单管理页 + 压缩设置里的"启用黑名单"
- 磁盘预检：启动任务前检查剩余空间

**验收标准：**

- □ 用户层配置了规则后，选中命中项压缩 → 提示"X 个文件已跳过"
- □ 打包模式下，跳过文件仍保留在原目录
- □ 单独压缩模式下，跳过文件不生成空压缩包
- □ 用户能在设置里添加/删除黑名单扩展名
- □ **跳过项不参与删除**（INV-02）
- □ 磁盘剩余 < 待压文件 × 2 时，任务拒绝启动，给出明确提示

**关键测试：** 把磁盘塞满到只剩 1 GB，然后尝试压 500 MB 的目录 → 应该拒绝。

## 十、M7：性能监控看板

**交付物：**

- 后端：**零新依赖** —— Node 内置（`perf_hooks` + `node:os`）＋ `/proc/{stat,meminfo,diskstats}` 采集指标
  - 为什么不引 `systeminformation`：契约要的字段全部内置可得；它会多出温度/风扇/网络（契约明确不做），且不少方法靠 spawn 系统命令实现，与「开销 < 1%」相反
- 前端：6 个卡片（CPU / 内存 / 事件循环延迟 / 磁盘 IO / 活跃任务 / 最近完成）
- 前端 **2 秒轮询** `GET /api/v1/metrics/snapshot`（对齐 `docs/07` §三 与 API 规范 §4.6）
  - 为什么不用 SSE：指标是**快照**不是事件，2 秒轮询已足够；若走 SSE 则 `metrics/snapshot` 契约成为死字段。任务进度用 SSE（推送事件）、性能指标用轮询（拉取快照），两者语义不同，不要统一。

**验收标准：**

- □ 6 个卡片实时更新（2 秒刷新）
- □ 事件循环延迟能反映"服务卡不卡"
- □ 压缩任务执行时，看板能看出 CPU/磁盘变化
- □ 监控本身开销 < 1% CPU

**关键测试：** 启动一个大的压缩任务，看板显示 CPU 飙升、磁盘 IO 飙升。

## 十一、M8：打磨与触屏兼容

**交付物：**

- 右键菜单（文件、目录、空白处）
- 快捷键（Ctrl+A、Delete、F2、上下箭头）
- 拖拽（文件到目录树、拖到压缩区）
- 触屏兼容：长按 = 右键、按钮 ≥ 40px、行高 ≥ 44px
- 视图切换（列表 / 网格）

**验收标准：**

- □ 所有高频操作有右键菜单入口
- □ 键盘能完全驱动文件浏览
- □ 手机上能完成"选文件 → 压缩 → 查看进度"全流程
- □ 手机上不出现"悬停才显示"的操作

## 十二、M9：手机端（PWA 路径）

> 2026-10-18 定：曾评估过「做 MT 管理器插件」替代 APK，调研后放弃（v3 插件无文件菜单扩展点，且最小验证需在真机装探针插件）。详见 [09 §11.7](09-API契约与APK铺路.md) 与 [research/mt-plugin-feasibility.md](research/mt-plugin-feasibility.md)。**结论：走 PWA。**

**交付物：**

- API 稳定化：确认 v1 接口冻结
- 双认证：登录同时返回 Session 和 Bearer Token（长期在线客户端用 token）
- **PWA manifest + Service Worker**：可"添加到主屏幕"，离线壳、断网提示
- 移动端适配复查：触屏目标尺寸、横向滚动、小屏下的看板与压缩抽屉（与 M8 打磨一起做）

**验收标准：**

- □ 用 curl + Bearer Token 能完整跑通文件浏览 + 压缩
- □ 手机上"添加到主屏幕"后打开，**浏览 / 多选 / 压缩 / 删除确认 / 看板全部可用**
- □ 所有错误码都是机器可读的
- □ 断网时有明确提示，恢复后能续上（任务状态在服务端，不依赖连接）

## 十三、阶段间的依赖与风险

| 风险 | 影响 | 应对 |
|---|---|---|
| M0 契约没定清 | 后面每个阶段都要返工 | 契约冻结后不再改，有变更走 v2 |
| M3 任务系统没做 | M5/M6/M7 都要依赖 | M3 是核心，务必做扎实 |
| M5 删除逻辑有 bug | 数据丢失 | 独立验收，每条都要手动测 |
| zstd 二进制不存在 | M4 卡住 | M0 阶段就调研清楚目标环境 |
| 前端越做越复杂 | M8 拖很久 | 每完成一个功能就冻结，不回头加需求 |

## 十四、每阶段结束时的固定动作

- 跑一遍自审：代码质量、路径安全、错误处理
- 更新文档：API 文档、README、变更日志
- 手写验收测试：把验收标准逐条走一遍，记录结果
- 打 tag：v0.M0、v0.M1……方便回溯
- 保留一个可运行的产物：每阶段结束时，项目必须能跑

## 十五、一句话总结

**M0 定契约，M1~M2 打通单格式主链路，M3 建任务系统，M4 扩多格式，M5 最危险的删除独立验收，M6~M8 补黑名单/看板/打磨，M9 为 APK 铺路。** 每个里程碑都是"能跑 + 能验收 + 能回退"。最不能省的是 M0 和 M3——契约和任务系统，是整个项目的地基。删除功能务必独立里程碑，不要混在其他阶段做，否则出问题找不到边界。
