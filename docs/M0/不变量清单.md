## 二、逐条不变量与验证方式

### ⭐INV-01 删除原文件前必须通过完整性校验

- **陈述**：原文件删除动作只允许发生在「该任务的**每一个**产物都 `verified === true`」之后。校验由格式包 `test()` 完成（CRC / 读通），结果与策略写入 `result.packages[].verified/verifyStrategy`。
- **依据**：docs/11 §三「原文件删除前必须通过完整性校验」；docs/06 §二「压缩完成 → 校验 → 通过 → 标记 → 待确认 → 删除」。
- **违反后果**：损坏包 + 已删源 = 数据永久丢失（本项目唯一会丢数据的功能）。
- **验证方式**：
  1. **单元（`test/unit/verify.test.js`）**：
     - 构造 `test()` 返回 `{ok:false, failures:[{entry,reason}]}` 的桩格式包 → 断言 `deleter` **零调用**、任务 `status==='failed'`、`error.code==='VERIFY_FAILED'`。
     - 构造 `test()` 抛 `ARCHIVE_CORRUPTED` → 断言同样不删除、任务 `failed`。
     - 断言校验通过但**删除前**再次比对集合差异非空 → 拒绝删除。
  2. **集成（`test/integration/api-compress.test.js`）**：
     - 正常压缩 → 用字节篡改产物中间段（保持文件长度）→ 走"删除原文件"流程 → 断言 `GET /tasks/{id}` 为 `failed` + `VERIFY_FAILED`，且源文件 `stat().mtime/size` 未变。
  3. **手工复现**：
     ```bash
     # 压完后故意损坏压缩包，再触发校验/删除路径
     printf 'x' | dd of=<产物路径> bs=1 seek=200 conv=notrunc
     # 断言：任务 failed(VERIFY_FAILED)，原文件仍在
     ls -l <源目录>; curl -s -H 'Authorization: Bearer <token>' /api/v1/tasks/<taskId> | jq '.data.task | {status, error}'
     ```
- **自动化门禁**：`test/unit/verify.test.js` + `test/integration/api-compress.test.js` 必须全绿；任何跳过校验的代码路径（如 `verifyDeep=false` 时的轻量分支）**仍必须调用 `test()`**。

### INV-02 只删"真正进包且未被跳过"的条目

- **陈述**：`delete.targets[]` ⊆ `result.packages[].entries` ∩ `sources` 差集 `result.skipped[]`。黑名单跳过的文件**永不进删除集合**（因为它没进包，删了就丢）。
- **依据**：docs/06 §一「如果压缩包里只有 98 个（2 个跳过了），删除时要只删那 98 个对应的。必须精确对应」；docs/04 §三「跳过但保留在原目录」。
- **违反后果**：静默丢失未压缩的文件。
- **验证方式**：
  1. **单元（`test/unit/deleter.test.js`）**：给 100 个输入（其中 2 个命中 `*.jpg`），断言 `delete.targets` 长度为 98，且被跳过的两个路径**不在**集合中。
  2. **集成**：压缩一个含 `a.txt` + `thumb.jpg` 的目录（`keepOriginal:false, deleteConfirmed:true`）→ 断言删除后 `thumb.jpg` 仍在、`a.txt` 进 `storage/trash/<batchId>/`。
  3. **断言**：`result.skipped.length + delete.targets.length === 源条目总数`（集合完备性）。
- **自动化门禁**：`test/unit/deleter.test.js`。

### INV-03 默认保留原文件；删除需显式请求 + 二次确认

- **陈述**：① `options.keepOriginal` 缺省 `true`；② `keepOriginal:false` 且 `deleteConfirmed:false` 时，任务必停在 `phase==='waiting_confirm'`，不得自行删除；③ **二次确认时**必须回传 `expectedFiles/expectedBytes`，与服务端实际值不一致则拒绝（**两个维度都要比**，只比 files 视为未实现）；④ **等待必须有界且可取消**：`delete.confirmTimeoutMs`（默认 30 分钟，`0`=不限）超时按**放弃删除**结算（`delete.status='skipped'`，reason=`confirm_timeout`）—— **超时绝不等于确认**；`waiting_confirm` 阶段**可取消**（取消=放弃删除，不删原文件），且**不得阻塞串行队列**（等待期间后续任务必须能继续执行）；⑤ **执行前复核**：确认通过后、真正执行删除前，必须逐条复核 `{size, mtimeMs, ino}` 与扫描时快照一致 —— 变化的条目跳过（reason=`source_changed`），**全部变化则整批拒删**。
- **依据**：docs/06 §一「默认值设为保留原文件」「删除必须二次确认」；docs/11 M5 验收第 1、2 条。
- **违反后果**：用户手一抖就丢数据。
- **验证方式**：
  1. **默认值测试**：`POST /compress/tasks` 不传 `keepOriginal` → 断言任务 `options.keepOriginal === true`、`delete === null`。
  2. **状态守卫测试**：`keepOriginal:false, deleteConfirmed:false` → 任务完成后 `phase==='waiting_confirm'`、`delete.status==='pending'`、源文件仍存在；再调 `POST /compress/tasks/{id}/confirm-delete`（正确数字）→ 进 `deleting`。
  3. **数字不符测试**：`expectedFiles` 传错 → `INVALID_STATE`(409) 或 `VALIDATION_FAILED`(400)，且**不删除**。
  4. **越权测试**：`phase !== 'waiting_confirm'` 时调 `confirm-delete` → `INVALID_STATE`，不删除。
- **自动化门禁**：`test/integration/api-compress.test.js`（删除流程用例集）。

### ⭐INV-04 任务状态落盘，不依赖前端连接

- **陈述**：任务执行、进度推进、状态落盘与任何客户端连接**完全解耦**。零 SSE 订阅者时任务照常执行、照常写 `storage/tasks.json`。
- **依据**：docs/11 §三「任务状态落盘，不依赖前端连接」；docs/05 §三.2「进度是状态不是消息」；docs/11 M3 验收「关掉浏览器，任务继续跑」。
- **违反后果**：关浏览器任务停摆；重连后状态回退。
- **验证方式**：
  1. **单元（`test/unit/task-manager.test.js`）**：直接构造任务管理器（**不建任何 SSE/HTTP 连接**）→ 推进到 `running` → 断言 `tasks.json` 中该任务 `status==='running'` 且 `progress.percent > 0`；断言 `progress.js` 的广播函数在订阅者为空时**不抛错**。
  2. **集成（`test/integration/api-tasks.test.js`）**：
     - 创建任务 → **立刻关闭所有连接** → 轮询 `GET /tasks/{id}` 直到终态，断言中间过程 `startedAt/finishedAt` 递增且状态连续（无回退）。
     - 断言进程内无任何"仅连接持有"的状态（代码审查点：`core/task/*` 不得 import 任何 HTTP/SSE 对象）。
  3. **手工复现**：
     ```bash
     # 起任务后立刻断开所有客户端，观察磁盘状态仍在推进
     curl -s -X POST /api/v1/compress/tasks -d '{...}' > /dev/null
     sleep 3; jq '.[0].progress.percent' storage/tasks.json   # 必须 > 0 且持续增长
     ```
- **自动化门禁**：`test/unit/task-manager.test.js`、`test/integration/api-tasks.test.js`。

### INV-05 进度是"状态"不是"消息"：重连先拿快照

- **陈述**：SSE 连接建立后**第一条**事件必须是 `snapshot`（含当前全部非终态任务 + 队列），之后才是增量；客户端丢失任何增量都能靠下一次快照/查询恢复。`since` 落在保留窗口之外时服务端直接重发 `snapshot`。
- **依据**：docs/05 §三.2；docs/10 §二.2 参考实现 `subscribe()`（`:490-502` 发快照）。
- **违反后果**：重连后 UI 显示过期进度，用户以为任务卡死。
- **验证方式**：
  1. **集成断言**：连接 `GET /tasks/events` → 读取第一条报文，断言 `event: snapshot`、`data.tasks` 为非空数组（有在途任务时）。
  2. **丢事件模拟**：连上后主动丢弃 3 条 `task` 增量 → 重新查询 `GET /tasks/{id}` → 断言字段与真实状态一致（证明不依赖增量补齐）。
  3. **`since` 越界**：传 `since=1`（早于窗口）→ 断言服务端返回 `snapshot` 而非报错。
- **自动化门禁**：`test/integration/api-tasks.test.js`（SSE 用例集）。

### ⭐INV-06 所有文件路径必须过白名单校验

- **陈述**：任何接受路径的入口（HTTP 参数、任务创建、内部调用）都必须经过 `core/fs/safePath.js`：① 拒绝含 `..` 的段；② 归一化后必须满足 `resolved === root || resolved.startsWith(root + sep)`（**必须带分隔符**，防 `/data-evil` 被 `/data` 放行）；③ `storage.root === "/"` 时拒绝启动（避免白名单退化为全盘）。
- **依据**：docs/11 §三「路径必须经过白名单校验」；docs/11 M1「尝试路径穿越（../、%2e%2e）返回 403」；docs/10 §七（wfmanager 反例、kadi `startsWith` 前缀缺陷反例、cloudcmd `root.js:14` 正例）。
- **违反后果**：任意文件读写（最严重的安全缺陷）。
- **验证方式**（`test/unit/safePath.test.js`，数据驱动，全部必须拒绝并返回 403/`PATH_OUT_OF_ROOT`）：

  | 输入 | 期望 |
  |---|---|
  | `/../etc/passwd` | 拒绝 |
  | `/a/../../etc/passwd` | 拒绝 |
  | `/%2e%2e/etc`（解码后 `..`） | 拒绝 |
  | `/a/%2e%2e%2fetc` | 拒绝 |
  | `/..%5c..%5cwindows`（反斜杠） | 拒绝（统一按 `/` 拆段后再判） |
  | `data-evil/x`（当 root=`<root>/data`） | 拒绝（前缀攻击，必须带 `sep` 比较） |
  | 绝对路径 `/etc/passwd`（root 非 `/`） | 拒绝（必须相对 root 解析） |
  | `\0` 字节注入 | 拒绝（`INVALID_PATH`） |
  | symlink 指向 root 外 | 拒绝（`realpath` 后二次校验） |
  | root 内正常路径 | 放行 |

  1. **集成**：`curl '…/fs/list?path=/../../etc'` → 断言 HTTP 403 + `error.code === 'PATH_OUT_OF_ROOT'`；`curl '…/fs/list?path=/etc/passwd'` → 断言 404 或 403（**绝不能返回内容**）。
  2. **symlink 专项**：在 root 内建 `link -> /etc`，请求 `/link` → 拒绝；`link -> <root>/sub` → 允许。
  3. **反例自证**（门禁必须先变红）：把实现临时改成裸 `startsWith(root)`（不带 `sep`），跑 `/data-evil` 用例 → **必须失败**，否则说明测试没覆盖到，门禁无效。
- **自动化门禁**：`test/unit/safePath.test.js` + `test/integration/api-fs.test.js`，作为提交前必跑项。

### ⭐INV-07 磁盘预检：剩余空间 ≥ 待压文件 × 2

- **陈述**：任务创建前必须校验 `freeBytes ≥ requiredBytes`，其中 `requiredBytes = Σ(进包条目原始大小) × preflightFactor`，`preflightFactor` 默认 **2** 且不允许 < 2。`single` 模式按**单个待压源滚动检查**（压完一个释放一个，docs/06 §三）；`bundle` 模式按总量一次检查。同时校验**目标目录所在分区**的剩余空间（产物写在那里）。
- **依据**：docs/11 §三「磁盘预检：剩余空间 ≥ 待压文件 × 2」；docs/06 §三（峰值 = 原文件 + 临时产物）；docs/11 M6 验收「剩余 < 待压 × 2 时任务拒绝启动」。
- **违反后果**：写到一半满盘 → 产物损坏、原文件不敢删。
- **验证方式**：
  1. **单元（`test/unit/preflight.test.js`）**：注入 `statfs` 桩返回固定 `freeBytes`。
     - `free = 2×size - 1` → 断言拒绝 + `DISK_FULL`。
     - `free = 2×size` → 断言通过（**边界必须通过**，`≥` 不是 `>`）。
     - `single` 模式：源 A（10GB，放得下）+ 源 B（超限）→ 断言只拒绝 B、A 正常入队（**不做整体失败**，docs/04 §二）。
     - `bundle` 模式：A+B 总量超限 → 整单拒绝。
     - 目标目录与源目录不同分区 → 按目标分区判定（docs/06 §三）。
  2. **集成**：用一台小容量临时文件系统/配额目录（或用桩注入）模拟 `free = 1GB` → 提交 500MB 目录（需 1GB）→ 断言拒绝 + `DISK_FULL`；把同一目录改小到 400MB → 通过（M6 关键测试的反向验证）。
  3. **边界回归**：断言 `preflightFactor < 2` 的配置**启动即失败或被强制改为 2**。
- **自动化门禁**：`test/unit/preflight.test.js`（桩注入是唯一可稳定复现的方式，禁止依赖"真的把磁盘塞满"）。

### INV-08 绝不覆盖既有产物/既有文件

- **陈述**：产物命名冲突时自动加 ` (n)` 后缀（数据模型 §9.2）；改名/移动遇到同名目标返回 `TARGET_EXISTS`(409) 并整批拒绝，不做部分执行；格式包写 `tempPath` 前若已存在同类文件必须抛 `TARGET_EXISTS`。
- **依据**：docs/10 §二.2「computeTarget：目标已存在时自动加 ` (1)`、` (2)` 后缀，**绝不覆盖**」；本契约 [插件契约.md](插件契约.md) §3.4 第 7 条。
- **违反后果**：静默覆盖用户既有数据。
- **验证方式**：
  1. **单元（`test/unit/naming.test.js`）**：`2024.zip` 已存在 → 期望 `2024 (1).zip`；再存在 → `2024 (2).zip`；复合扩展名 `2024.tar.gz` → `2024 (1).tar.gz`（后缀在主扩展名前）。
  2. **集成**：预置同名文件 → 跑压缩 → 断言新产物为 ` (1)` 版本、旧文件 `mtime/size` 未变。
  3. **改名/移动**：目标同名 → 断言 409 `TARGET_EXISTS` 且**两边的文件都在**。
- **自动化门禁**：`test/unit/naming.test.js`、`test/integration/api-fs.test.js`。

### INV-09 压缩执行串行，同一时刻仅 1 个 `running`

- **陈述**：v1 全局串行；并发提交 N 个任务时，最多 1 个 `running`，其余为 `queued`；`options.parallel` 恒 `false`；`compress.parallelEnabled = true` 只告警不生效。
- **依据**：docs/05 §二「并行开关占位……即使值是真，也强制串行」；docs/11 M3 验收「同一时刻只有一个任务在执行（串行），后续任务排队」。
- **违反后果**：CPU 抢占、进度互相污染、失败难回滚。
- **验证方式**：
  1. **单元**：向队列投 5 个任务 → 断言任一时刻 `running` 计数 ≤ 1，完成顺序 = `createdAt` 升序。
  2. **集成**：并发 `POST /compress/tasks` × 3（互不冲突的路径）→ 轮询 `GET /tasks`，断言 `queue.active` 唯一、`data.queue.parallel === false`。
  3. **配置对抗**：把 `parallelEnabled` 改为 `true` → 断言启动日志出现告警、`/health` 或 `/tasks` 仍报 `parallel:false`。
- **自动化门禁**：`test/unit/task-manager.test.js`、`test/integration/api-compress.test.js`。

### INV-10 创建即落盘；重启把非终态标 `interrupted` 并保留 `.part`

- **陈述**：任务创建响应返回前必须已写入 `storage/tasks.json`；进程启动加载时，`queued`/`running`/`cancelling` → `interrupted`（`error.code = INTERRUPTED`），`.part` 产物**保留不清理**，不自动续跑。
- **依据**：docs/05 §三.3「压缩到一半的 .tmp 产物：保留」「绝对不能：重启后把 .tmp 当正式产物」；docs/11 M3「手动 kill 服务进程，重启后状态文件里的任务状态应该是"中断"，且 .tmp 产物保留」。
- **违反后果**：重启后状态错乱或半成品被当成正式产物。
- **验证方式**：
  1. **单元（`test/unit/persistence.test.js`）**：构造 `tasks.json`（含 `running`/`queued`/`failed`/`done` 各一）→ 调 `load()` → 断言 `running`/`queued` → `interrupted`；`failed` 保持；`done` 不变（或已不在活动表）。
  2. **集成（`test/integration/restart-recovery.test.js`）**：起一个压缩任务 → `kill -9` → 重启 → 断言：① 任务 `interrupted` + `error.details.reason === 'SERVER_RESTART'`；② `<产物>.part` 仍存在；③ 源文件未被动过；④ 无 `.part` 被 rename 成正式产物。
  3. **手工复现（docs/11 M3 关键测试原始步骤）**：
     ```bash
     kill -9 <pid> && node server/boot.cjs
     jq '.[0] | {status, error}' storage/tasks.json     # interrupted / INTERRUPTED
     ls -l <产物目录>/*.part                            # 仍在
     ```
- **自动化门禁**：`test/unit/persistence.test.js`、`test/integration/restart-recovery.test.js`。

### INV-11 失败/取消清理 `.part`；成功走原子 `rename`，无 `.part` 残留

- **陈述**：`create()` 只写 `<产物>.part`，总入口负责 `rename` 到最终产物；`failed`/`aborted` 必须删除 `.part`（`interrupted` 例外，按 INV-10 保留）；成功任务的目录中**不存在**该任务的 `.part`。
- **依据**：docs/05 §三.3；docs/10 §二.2「abort 时 cleanup() 删半成品」；本契约 [插件契约.md](插件契约.md) §3.4 第 1、4 条。
- **违反后果**：磁盘被半成品占满；用户误用不完整包。
- **验证方式**：
  1. **单元**：注入"写一半抛 `ENOSPC`"的桩格式包 → 断言 `.part` 被删除、`outputPath` 不存在。
  2. **集成**：取消任务 → 轮询到 `aborted` → 断言 `<产物>.part` 不存在、`outputPath` 不存在。
  3. **成功路径**：正常压缩 → 断言 `outputPath` 存在且 `test()` 通过、同目录无 `.part`。
  4. **属性断言（可做成回归用例）**：任务终态为 `done`/`aborted`/`failed` 时，其产物目录内不得存在该任务遗留的 `.part`（`interrupted` 除外）。
- **自动化门禁**：`test/integration/api-compress.test.js`。

### INV-12 错误码机器可读，且与任务状态机自洽

- **陈述**：① 所有失败响应 `error.code` 必须来自 `shared/error-codes.js` 枚举（禁止裸字符串/任意新码）；② 任务对象满足 `error !== null ⟺ status ∈ {failed, interrupted}`；③ 删除阶段的错误记在 `delete.error`，不改任务 `status`。
- **依据**：docs/09 约定 7；docs/11 M9「所有错误码都是机器可读的」；本契约 [API规范.md](API规范.md) §八/§九。
- **违反后果**：APK/前端无法分支处理，只能展示字符串。
- **验证方式**：
  1. **契约测试（`test/unit/error-contract.test.js`）**：遍历 `shared/error-codes.js` 的全部导出，断言每个码在 API 文档表中存在、且 `lib/errors.js` 能构造出对应实例；反向断言运行时抛出的码都在枚举内（用一个 Proxy/白名单包装）。
  2. **状态自洽测试（属性测试）**：随机走 200 次状态迁移（含重启、取消、失败注入）→ 断言不变式 `error !== null ⟺ status ∈ {failed, interrupted}` 恒成立。
  3. **HTTP 映射测试**：对每个错误码断言其 HTTP 状态与 API 规范 §八 表格一致。
- **自动化门禁**：`test/unit/error-contract.test.js`。

### INV-13 `.part` 半成品不可下载

- **陈述**：`GET /api/v1/fs/download?path=<...>.part` → `INVALID_STATE`(409)；任务进行中请求其产物路径 → 同样不可下载。
- **依据**：docs/09 约定 5（下载要可靠）；本契约 API 规范 §六.3。
- **违反后果**：用户拿到损坏压缩包，误以为压缩成功。
- **验证方式**：单元（`test/unit/download.test.js`）：直接对存在的 `.part` 请求 → 断言 409 + `INVALID_STATE`；对已完成产物请求 → 200/206 正常。集成：压缩中请求产物 → 409；完成后 → 206 Range 正常。
- **自动化门禁**：`test/unit/download.test.js`。

### INV-14 枚举唯一来源是 `shared/`，前端不硬编码

- **陈述**：错误码、任务状态、任务阶段、压缩模式、格式列表五个枚举只在 `shared/` 定义；`server/` 与 `web/` 都从 `shared/` 引入。前端不得写裸字符串字面量做分支（如 `if (status === 'done')` 出现在没有 import 的模块里）。
- **依据**：docs/12 §四「如果一边改一边忘，就会出现"后端返回 DISK_FULL，前端不认识"的 bug」。
- **违反后果**：两端枚举漂移 → UI 显示未知状态。
- **验证方式**：
  1. **静态扫描（`scripts/check-drift.js` 的一部分）**：在 `web/src/**` 与 `server/http/**` 中 grep 状态/错误码字面量，出现且文件未从 `shared/` 引入 → 报错。
  2. **契约快照测试**：对 `shared/*.js` 的导出集合做快照，改动必须显式更新快照（防静默改枚举）。
  3. **构建期检查**：前端构建时若引用了 `shared/` 之外的枚举定义 → 失败。
- **自动化门禁**：`scripts/check-drift.js` + `test/unit/shared-enums.test.js`。

### INV-15 格式包不越界（不改/不删源文件、不预检、不排队）

- **陈述**：格式包只写 `tempPath`；对源路径**只读**；不删/移/改源文件；不做空间预检与黑名单匹配。
- **依据**：docs/03 §二「格式包只负责"怎么压"，不负责"压完删不删"、"任务排不排队"、"磁盘够不够"」；[插件契约.md](插件契约.md) §八。
- **违反后果**：删除逻辑散到各格式包 → 改一处漏一处；某个包误删数据。
- **验证方式**：
  1. **契约测试（`test/unit/formats/contract.test.js`）**：对四个格式包统一跑：源目录建快照（路径+size+mtime 的哈希）→ 执行 `create()` → 断言源目录快照**逐字节未变**；断言只创建了 `tempPath`；断言 `create()` 期间无 `unlink/rename` 作用于源路径（可用 `fs` 探针包装统计）。
  2. **静态检查**：`server/plugins/formats/**` 中禁止出现 `delete`/`unlink`/`rm`/`rename`/`rmdir` 调用（除删除自己的 `tempPath`）——白名单式 ESLint 规则。
  3. **边界测试**：对格式包调用 `create()` 时不传 `outputPath`（模拟错误调用）→ 必须抛 `VALIDATION_FAILED`，不得自行推导路径。
- **自动化门禁**：`test/unit/formats/contract.test.js` + lint 规则。

### INV-16 凭据不落明文；日志不含敏感字段

- **陈述**：`storage/auth-tokens.json` 只存 token 的 sha256 + 过期时间；配置里只存 `passwordHash`；日志与 API 响应不得出现密码、明文 token、`passwordHash`。

- **自动化门禁**：`test/unit/redaction.test.js`。

### INV-17 路径与文件操作必须跨平台安全（Linux / macOS / Windows）

- **陈述**：代码不得假设「分隔符一定是 `/`」「文件名一定大小写敏感」「路径长度无上限」。具体六条：

1. **拼接与比较**：路径拼接/前缀校验一律走 `path.sep` / `path.resolve`（不手写 `/`）；对外 API 路径统一 POSIX 形式（`/` 分隔），内部按平台转换。
2. **输入归一化**：用户传入的反斜杠按平台语义归一化（Windows 上 `\` 同为分隔符），且归一化后仍需过白名单（INV-06）。
3. **大小写**：不得硬编码假设；「绝不覆盖」（INV-08）在大小写不敏感平台必须识别 `A.txt` 与 `a.txt` 指向同一目标。
4. **长度上限**：整条与单段长度限制走配置（`limits.maxPathLength` / `limits.maxPathSegmentLength`），不写死数字；超限返回 `INVALID_PATH`(400)，不落 500。
5. **符号链接**：读取（`lstat` / `realpath`）必须可用；Windows 上**创建**链接会因权限失败，必须给出明确错误码而非静默跳过。
6. **空间预检**：用 `fs.statfs`（Node ≥ 18.15）；Windows / macOS / Linux 均由 libuv 实现（Windows 侧走 `NtQueryVolumeInformationFile`）。**拿不到空间信息时必须显式呈现**（`freeBytes: null` + 明确标记「未执行空间预检」），**不得静默当作空间充足**。

- **为什么**：本项目为 NAS 开发，但同一份代码可能跑在 Windows / macOS。文件树遍历与路径判定是最容易「在 Linux 上碰巧对」的一层。
- **验证方式**：同一套不变量脚本在 Windows（或大小写不敏感环境）复跑；模拟 `statfs` 失败，断言响应显式标注而不是静默通过。
- **当前落地情况**：`server/core/fs/safePath.js` 已用 `path.sep` 做带分隔符前缀校验、反斜杠归一化、`path.posix` 处理对外路径；`server/config/schema.js` 已拒绝把存储根设为盘符根（`^[A-Za-z]:[\\/]?$`）；`limits.maxPathSegmentLength` 已可配（默认 255，按字节）。**待补**：大小写不敏感的覆盖判定、`statfs` 拿不到时的显式标注。
