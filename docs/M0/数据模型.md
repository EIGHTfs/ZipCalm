## 一、通用约定

| 项 | 约定 |
|---|---|
| 任务 ID | **UUID v4**（`crypto.randomUUID()`），全局唯一、与数组下标无关（docs/09 约定 2） |
| 时间 | Unix **毫秒**整数；`createdAt` / `startedAt` / `updatedAt` / `finishedAt` |
| 路径 | 对外（API 字段）一律**相对存储根的 POSIX 路径**（根 `/`）；进程内部字段（如 `absPath`）不出现在 API 响应中 |
| 字节 | 整数 bytes；`ratio` 为浮点（保留 4 位） |
| 枚举来源 | 所有枚举以 `shared/` 为唯一来源，前后端共用（docs/12 §四） |
| 空值 | 未发生 → `null`（不用 `undefined`、不用空字符串占位） |
| 追加字段 | 允许**加字段**（非破坏）；不允许改字段语义或删字段 |

`shared/` 枚举清单（v1 冻结）：

| 文件 | 内容 |
|---|---|
| `shared/error-codes.js` | 错误码枚举（见 API 规范 §八） |
| `shared/task-status.js` | `queued / running / cancelling / done / failed / aborted / interrupted` |
| `shared/task-phase.js` | `precheck / scanning / compressing / verifying / waiting_confirm / deleting` |
| `shared/compress-modes.js` | `single / bundle` |
| `shared/format-list.js` | 四个格式 id 与 `ext`（`zip / tar / targz / tarzst`） |

## 二、任务对象 Task

### 2.1 字段表

| 字段 | 类型 | 必现 | 说明 |
|---|---|---|---|
| `id` | string(uuid) | ✅ | 任务 UUID，所有任务 API 的主键 |
| `kind` | string | ✅ | `compress` \| `extract`（v1 含两者；`move` 仍预留） |
| `status` | enum | ✅ | `queued`/`running`/`cancelling`/`done`/`failed`/`aborted`/`interrupted`（第三章） |
| `phase` | enum | ✅ | 仅 `running`/`cancelling` 期间有意义；终态保留最后一次 phase |
| `mode` | enum | ✅ | `single`（每个源各一个包）/ `bundle`（合成一个包）（docs/04） |
| `format` | string | ✅ | 格式 id：`zip`/`tar`/`targz`/`tarzst` |
| `sources` | Source[] | ✅ | 用户提交的源（见 2.2） |
| `options` | object | ✅ | 生效后的选项快照（含默认值展开后的结果，便于复现） |
| `progress` | Progress | ✅ | 进度结构（第四章），`queued` 时为初始零值 |
| `result` | Result \| null | ✅ | 成功后的产物清单与节省统计；未完成 `null` |
| `delete` | DeleteState \| null | ✅ | 原文件删除状态；`keepOriginal:true` 时 `null` |
| `error` | TaskError \| null | ✅ | `failed` 必带；`interrupted` 也带（`code: INTERRUPTED`） |
| `createdAt` | number | ✅ | 任务创建（入队）时间 |
| `startedAt` | number \| null | ✅ | 真正开始执行时间 |
| `finishedAt` | number \| null | ✅ | 进入终态时间 |
| `updatedAt` | number | ✅ | 最后一次状态/进度变更时间 |
| `retryOf` | string \| null | ✅ | 重试来源任务 id（"中断后重试"用） |
| `bootId` | string \| null | ✅ | 执行该任务的进程启动 id（识别"跨重启任务"，见 API `/health`） |

### 2.2 子结构

```jsonc
// Source —— 用户提交的源条目
{
  "path": "/photos/2024",        // 对外相对路径
  "name": "2024",                // basename，产物命名用
  "kind": "dir",                 // "file" | "dir"
  "sizeBytes": 5368709120,       // 扫描后回填（创建时可为 null）
  "entryCount": 1200             // 扫描后回填（file 恒为 1）
}

// options —— 生效选项快照
{
  "level": 6,
  "keepOriginal": true,          // 默认 true（docs/06 §一）
  "deleteConfirmed": false,      // 提交时是否已二次确认（compress）
  "deleteArchiveAfterExtract": false,  // extract：解压成功并校验后是否删除压缩包（默认 false；与 compress 的 keepOriginal 对称，同样走「先校验 → 再删」）
  "outputDir": null,             // null = 与源同目录（docs/01 §四.1 默认）
  "blacklist": { "enabled": true, "extraPatterns": ["*.bak"] },
  "parallel": false              // 恒 false（开关占位，docs/05 §二）
}

// Result —— 成功产物
{
  "packages": [
    {
      "sourceIndex": 0,
      "sourcePath": "/photos/2024",
      "outputPath": "/photos/2024/2024.zip",
      "bytesOut": 1610612736,
      "entries": 1180,
      "durationMs": 84210,
      "verified": true,
      "verifyStrategy": "crc"
    }
  ],
  "bytesIn": 5368709120,        // 实际进包条目的原始总量（不含被跳过项）
  "bytesOut": 1610612736,
  "savedBytes": 3758096384,     // bytesIn - bytesOut
  "ratio": 0.3,                 // bytesOut / bytesIn，保留 4 位
  "skipped": [                  // 黑名单跳过（**原文件保留**，docs/04 §三）
    { "path": "/photos/2024/thumb.jpg", "pattern": "*.jpg", "layer": "global" }
  ],
  "completedAt": 1730000000000
}

// DeleteState —— 原文件删除状态（keepOriginal=false 时才存在）
{
  "requested": true,
  "confirmed": false,           // 用户是否已二次确认
  "confirmedAt": null,
  "status": "pending",          // "pending" | "deleting" | "deleted" | "skipped" | "failed"
  "targets": [                  // 精确删除集合 = 已进包 ∩ 未跳过
                                // **形状固定为 {path, kind, sizeBytes}**（落盘与 API 同一形状）
                                // 内部形状（含 absPath / userPath / size）只允许存在于**传参链路**里
                                // （例如 stageDelete 的 input.targets）；一经写入 info.delete.targets
                                // 就必须只有上面三个键 —— **绝不进 API 响应**（与 sources[].absPath 同一红线）
    { "path": "/photos/2024", "kind": "dir", "sizeBytes": 5368709120 }
  ],
  "trashBatch": null,           // 删除开始后 = storage/trash/<batchId>/
  "deletedAt": null,
  "logRef": null,               // storage/logs/delete-<yyyymmdd>.jsonl 里的记录 id
  "error": null                 // status=failed 时的 TaskError
}

// TaskError
{
  "code": "VERIFY_FAILED",      // 必须来自错误码枚举（API 规范 §八）
  "message": "压缩包校验未通过：3 个条目 CRC 不匹配",
  "at": 1730000000000,
  "details": { "failures": 3 }
}
```

## 三、状态机

### 3.1 状态枚举与语义

| 状态 | 语义 | 终态 | 是否落盘 | UI 文案 |
|---|---|---|---|---|
| `queued` | 已入队，等待执行（串行队列） | 否 | ✅ | 排队中 |
| `running` | 正在执行（具体看 `phase`） | 否 | ✅ | 压缩中 |
| `cancelling` | 取消请求已受理，等待执行器收尾（过渡态） | 否 | ✅ | 正在取消 |
| `done` | 压缩成功（产物已原子落盘） | ✅ | ❌（进历史） | 已完成 |
| `failed` | 失败（必带 `error.code`）；产物已清理或保留视阶段而定 | ✅ | ✅ 保留（可重试） | 失败 |
| `aborted` | 用户取消完成；`.part` 已清理 | ✅ | ❌（进历史） | 已取消 |
| `interrupted` | 服务重启/崩溃导致的非正常中断；`.part` 保留；原文件未删 | ✅ | ✅ 保留（可重试） | 已中断 |

> 与 `docs/12` 冻结枚举的差异见第十一章第 1 条：这里把"取消"（`aborted`）与"重启中断"（`interrupted`）分开，并新增过渡态 `cancelling`——因为 M3 明确要求「服务重启后未完成任务状态标记为中断」且「能取消正在执行的任务」，两者语义不同。

### 3.2 迁移表

| from | to | 触发 | 守卫条件 |
|---|---|---|---|
| — | `queued` | 创建任务成功 | 预检通过（权限/黑名单/空间/格式可用/无冲突） |
| `queued` | `running` | 队列调度到它 | 串行执行器空闲 |
| `running` | `running` | 进度/phase 前进 | — |
| `running` | `done` | 压缩 + 校验通过 + 产物 rename 完成 | `test().ok === true` |
| `running` | `failed` | 任何环节抛错 | 已清理 `.part` 或保留（见 4.3） |
| `running` | `cancelling` | 用户取消 | `phase ∈ {precheck, scanning, compressing, verifying, waiting_confirm}` |
| `queued` | `cancelling` | 用户取消 | — |
| `cancelling` | `aborted` | 执行器响应 abort 并清理完毕 | `AbortSignal` 已触发 |
| `cancelling` | `failed` | 清理阶段自身失败 | 记录 `error.code` |
| `running`（`phase==='waiting_confirm'`） | `done` | 用户取消确认 **或** 确认超时 | **不回滚压缩结果**；`delete.status = 'skipped'`，reason 区分 `user_cancelled` / `confirm_timeout`。**终态是 `done` 而非 `aborted`** —— 压缩本身成功、产物有效，标 `aborted` 会让用户误以为压缩失败（与「`deleting` 失败不回滚任务」同一精神） |
| `running`/`queued`/`cancelling` | `interrupted` | 进程启动时加载到该任务（服务曾异常退出） | 启动恢复时无条件迁移（docs/11 M3 关键测试） |
| `failed`/`interrupted` | `queued`（**新任务**） | 用户点"重试" | 生成**新 UUID**，`retryOf = 原 id`；原任务保持终态不变 |
| `done` | `done` + `delete.*` | 删除阶段推进 | 见 3.3 |

**禁止迁移**（实现必须拒绝，否则产生脏状态）：任何终态 → `running`；`done` → `failed`；`aborted` → `done`。

### 3.3 `phase` 与删除子状态机

```
precheck → scanning → compressing → verifying → [waiting_confirm] → deleting → (任务仍为 done)
```

- `precheck`：权限/黑名单/空间二次确认（创建时已做过一次，执行前再校验一次，防竞态）。
- `scanning`：递归收集条目 + 汇总 `totalBytes`（进度分母，docs/01 §三.2）。
- `compressing`：调用格式包 `create()`。
- `verifying`：调用格式包 `test()`；**不通过 → 任务 `failed`，原文件绝不删除**。
- `waiting_confirm`：`deleteConfirmed=false` 且 `keepOriginal=false` 时停留，等 `POST /compress/tasks/{id}/confirm-delete`。此状态**任务整体仍是 `running`**（因为业务未完结），但 `progress.percent` 置 100 并在 UI 上显示"待确认删除"。三条硬要求：
  1. **必须有过期时间**（`delete.confirmTimeoutMs`，`0` = 不限）。超时按**放弃删除**结算（`delete.status='skipped'`，reason=`confirm_timeout`）—— **超时绝不等于确认**（安全默认方向）。
  2. **必须可取消**：取消 = 放弃删除（不删原文件），任务按 §3.2 迁 `done`。
  3. **不得阻塞串行队列**：等待期间后续任务必须能继续执行。服务级假死（一次未确认导致所有任务永久 queued）是必须被测试挡住的形态。
- `deleting`：进回收站 + 写删除日志；此阶段失败**不回滚任务**（压缩本身已成功）：任务保持 `done`，`delete.status = failed`。

### 3.4 错误码 × 状态自洽（与 API 规范 §九 同源，此处为服务端视角）

| 错误码 | 可出现于 | 是否终态 | 原文件是否受影响 |
|---|---|---|---|
| `DISK_FULL` / `QUOTA_EXCEEDED` | `failed` | ✅ | 不受影响（删除流程未开始） |
| `PATH_NOT_FOUND` / `PERMISSION_DENIED` | `failed` | ✅ | 不受影响 |
| `VERIFY_FAILED` / `ARCHIVE_CORRUPTED` | `failed` | ✅ | **绝不删除**（INV-01） |
| `ABORTED` | `aborted`（`error` 为 `null`，语义由状态表达） | ✅ | 不受影响 |
| `INTERRUPTED` | `interrupted`（`error.details.reason = "SERVER_RESTART"`） | ✅ | 不受影响；`.part` 保留（INV-10） |
| `TARGET_EXISTS` | `failed` | ✅ | 不受影响 |
| `INTERNAL_ERROR` | `failed` | ✅ | 不受影响 |

要点：**`error` 非空 ⟺ `status === "failed"` 或 `status === "interrupted"`**；`done`/`aborted`/`queued`/`running`/`cancelling` 的 `error` 必须为 `null`。删除阶段自身的错误记在 `delete.error`，**不改任务 `status`**。

## 四、进度结构

### 4.1 两层进度 + 单模式额外层

| 层 | 字段 | 更新时机 | 依据 |
|---|---|---|---|
| 字节级 | `processedBytes` / `totalBytes` / `percent` / `speedBps` / `etaSeconds` | 每 ≥100ms 或每 1MB | docs/05 §一（事件驱动，非定时采样） |
| 文件级 | `processedFiles` / `totalFiles` / `currentFile` | 每进一个文件 | docs/05 §一（"连续"的体验来源） |
| 模式层（`single` 专属） | `packagesDone` / `packagesTotal` | 每个子包完成 | docs/04 §一「第 X/Y 个包」 |

```jsonc
{
  "percent": 42.5,            // 0~100，1 位小数；写入时 Math.min(100, ...) 夹取
  "processedBytes": 2281701376,
  "totalBytes": 5368709120,
  "processedFiles": 503,
  "totalFiles": 1180,
  "currentFile": "IMG_2043.HEIC",   // 相对源根的展示名
  "packagesDone": 0,
  "packagesTotal": 1,               // bundle 恒为 1；single 为源目录/文件个数（跳过项不计）
  "speedBps": 27114296,             // 滑动窗口（最近 5s）速率的整数
  "etaSeconds": 114,                // 无法估算时为 null
  "updatedAt": 1730000000000
}
```

### 4.2 节流与持久化频率（防止"saveTask 全量写盘"重演，docs/01 §五）

| 项 | 规则 |
|---|---|
| 内存进度更新 | 每事件更新（廉价） |
| SSE 广播 | ≤ 10 次/秒/任务（100ms 节流） |
| 落盘（`tasks.json`） | ≤ 2 次/秒（500ms 节流）+ **状态/phase 变化时立即落盘**（不等节流） |
| 完成后 | 立即落盘一次（终态），随后进历史 |

### 4.3 失败时的进度语义

- `failed` / `interrupted`：`progress` 保留**最后一次真实值**（不归零），便于 UI 显示"卡在哪"。
- `aborted`：`percent` 置 0，`currentFile` 置 `null`（docs/10 参考实现 `finalizeTask` 的 cancelled 分支即置 0）。
- `done`：`percent` 强制 100（即使字节级估算有偏差，也避免进度条停在 99%，对齐 `FflateZipAdapter` 的"补一次 100%"经验）。

## 五、队列与执行模型

| 项 | 契约 |
|---|---|
| 并发 | **v1 强制串行**：全局同一时刻最多 1 个任务处于 `running`（docs/05 §二、docs/11 M3） |
| 队列 | FIFO，`queued` 任务按 `createdAt` 升序执行 |
| 并行开关 | 配置 `compress.parallelEnabled` 存在但**被强制忽略**；API `options.parallel` 恒为 `false`；UI 开关置灰并提示"暂未启用" |
| 调度者 | `core/task/queue.js` 单执行器循环；不与 SSE 订阅者耦合（INV-02） |
| 取消 | 通过 `AbortSignal` 传递；执行器自行清理 `.part`，不杀进程（对齐 `getTaskSignal` / `abortController.abort()`） |
| 重启 | 启动时把 `tasks.json` 里非终态任务迁为 `interrupted`；队列**不自动续跑**，等用户点"重试"（避免用户不在场时自动重跑大任务） |
| 冲突 | 创建时按"源/目标路径相等或互为父子"判定 `TASK_CONFLICT`（API 规范 §八） |

## 六、落盘模型

| 文件 | 内容 | 写入方式 | 保留策略 |
|---|---|---|---|
| `storage/tasks.json` | **非终态 + 失败/中断**任务（`queued`/`running`/`cancelling`/`failed`/`interrupted`） | 原子写（写 `tasks.json.tmp` → `rename`），500ms 节流 | 非终态**永不清理**；`failed`/`interrupted` 保留最近 **100 条**或 **7 天**（先到者为准），超出即移除（`task-history.jsonl` 里仍可查） |
| `storage/task-history.jsonl` | 每次进入终态追加一行（`done`/`failed`/`aborted`/`interrupted`） | 追加写（`appendFile`）+ 定期压缩重写 | 最近 **200** 条（`limits.taskHistoryMax`） |
| `storage/blacklist.json` | 用户层黑名单 | 原子写 | 覆盖式 |
| `storage/config.json` | 运行期配置覆盖项（默认值在 `server/config/defaults.js`） | 原子写 | 覆盖式（可选文件） |
| `storage/auth-tokens.json` | Bearer token 的 **sha256 + 过期时间**（不存明文） | 原子写 | 过期清理 |
| `storage/logs/` | 运行日志、删除日志 `delete-<yyyymmdd>.jsonl` | 追加写 | 按天 |
| `storage/trash/<batchId>/` | 删除进回收站的原文件（保留相对目录结构） | move | 手动清空（UI 提供） |

落盘规则（可测）：

1. **创建即落盘**：`POST /compress/tasks` 返回前必须已写入 `tasks.json`（对齐参考实现 `createExternalTask` 的"创建即持久化"）。
2. **终态不留在 `tasks.json`**：`done`/`aborted` 写入历史后从 `tasks.json` 移除；`failed`/`interrupted` 保留以便重试。
3. **原子性**：任何 `storage/*.json` 的写入都必须是"临时文件 + rename"，禁止原地截断写（docs/12 `lib/atomic-json.js`）。
4. **恢复规则**：启动加载 `tasks.json` 时，`queued`/`running`/`cancelling` → `interrupted` + `error.code = INTERRUPTED`；`failed` 保持；`.part` 产物**保留不清理**（用户可重试或手动删，docs/05 §三.3）。
5. **历史读取**：`GET /api/v1/tasks?status=done` 优先读内存中的非终态，终态从 `task-history.jsonl` 反向读取最近 N 条（进程内缓存最近 200 条）。
6. **终态保留策略（防写放大）**：`tasks.json` 里的 `failed`/`interrupted` 保留最近 **100 条**或 **7 天**（任一先到即清理）；清理时机 = 启动时 + 每完成一个任务后。
   - 依据（实测）：每条约 **1.9KB**，而该文件每次状态变更都**全量重写** —— 无上限增长会让单次写从 KB 级涨到 MB 级（1000 条 ≈ 2MB/次），既慢又磨损磁盘。
   - 超出保留窗的失败任务并非丢失：它们仍在 `task-history.jsonl` 中可查。
7. **非终态永不清理**：`queued`/`running`/`cancelling`/`waiting_confirm` 属于"活任务"，任何情况下都留在 `tasks.json`。
8. **手动删除活动记录**：`DELETE /api/v1/tasks/{id}` 可删除**终态**任务（`failed`/`interrupted`/`aborted`/`done`）的活动记录；非终态 → `INVALID_STATE`（需先取消）。删除只影响 `tasks.json`，**不动 `task-history.jsonl`** —— 历史是 append-only 的审计日志（排障与追溯都靠它），清空历史是另一个独立操作。

### 6.1 存储迁移触发阈值（何时该从 JSON/JSONL 换 SQLite）

**不提前迁**。满足下列任一条时才评估迁移：

1. `tasks.json` 单文件 > **2MB** 或条目 > **1000**（全量重写开始变痛）
2. 出现「多条件筛选 + 分页」或**聚合统计**需求（如看板历史查询、"各格式成功率 / 耗时趋势"）
3. 出现**多进程 / 多实例**访问同一数据目录（当前 INV-09 单进程串行已天然规避）
4. 需要**跨表事务**（任务 + 删除记录 + 产物三者强一致）

**迁移路径**：存储访问的**唯一入口**是 `server/core/task/store.js`，换实现只改这一层、调用方零改动（与"库收口"同一原则）。首选候选是 Node ≥ 22 内置的 `node:sqlite`（零依赖、事务、WAL），但它目前仍标注为**实验特性**（官方提示 API 可能变化），迁移前需先评估稳定性。

**为什么不现在就上 SQLite**（记录取舍，便于日后回溯）：

- 我们的查询模式只有「按 id 取一条」与「列最近 N 条」—— 用不上索引 / 聚合 / 事务这些 SQLite 的核心优势；
- 单进程串行（INV-09）已规避"多写者"问题；
- JSON / JSONL **人可读、可 diff、可直接 cat 排障** —— 项目尚未稳定时这个价值很实际（验收时就靠直接看 `tasks.json` 结构定位了泄漏与恢复问题）；
- 真正的痛点是"条目无上限增长"，用**保留策略**解决即可，换存储并不划算。

## 七、黑名单三层结构

| 层 | 存储 | 谁能改 | 能否删规则 | 生效范围 |
|---|---|---|---|---|
| 全局默认 `global` | 代码内 `core/blacklist/defaults.js` | 只读（内置） | ❌ 不可删，可整层关闭 | 所有任务 |
| 用户自定义 `user` | `storage/blacklist.json` | 用户在设置页增删 | ✅ | 所有任务 |
| 任务级临时 `task` | 随任务请求提交 | 提交任务时指定 | ✅（仅本次） | 单个任务 |

```jsonc
// GET /api/v1/blacklist 的 data 结构
{
  "global": {
    "locked": true,
    "enabled": true,
    "patterns": [
      "*.jpg", "*.jpeg", "*.png", "*.gif", "*.webp", "*.heic",
      "*.mp4", "*.mkv", "*.mov", "*.mp3", "*.flac",
      "*.zip", "*.7z", "*.rar", "*.gz", "*.bz2", "*.xz",
      "*.docx", "*.xlsx", "*.pptx",
      "Thumbs.db", ".DS_Store", "@eaDir", "#recycle"
    ]
  },
  "user": { "enabled": true, "patterns": ["*.bak", "*.tmp"], "updatedAt": 1730000000000 },
  "task": { "patterns": [], "expiresWithTask": true },
  "effective": { "count": 28, "order": ["task", "user", "global"] }
}
```

匹配规则（可测）：

1. **匹配对象**：条目的 `basename`（不是全路径）。
2. **模式语法（简化 glob，不引入 gitignore 复杂度）**：`*` 匹配任意字符（含点）；`?` 匹配单字符；其余按字面。扩展名类写成 `*.jpg`。
3. **大小写**：不敏感（NAS 上 `JPG` 与 `jpg` 同等对待）。
4. **目录剪枝**：模式命中目录名（如 `@eaDir`、`#recycle`）→ 整个子树不进入扫描（省时间，注意：**不删除**）。
5. **优先级**：`task` > `user` > `global`；命中的第一层写进 `result.skipped[].layer`。
6. **命中语义（关键）**：命中即**跳过压缩但保留在原目录**（docs/04 §三）；删除原文件时**跳过项永不进删除集合**（INV-07）。
7. **空包抑制**：`single` 模式下若某个源的条目全被跳过 → **不生成空压缩包**（M6 验收）；`bundle` 模式下若全部命中 → 创建任务时返回 `ALL_SOURCES_SKIPPED`。
8. **可回滚**：`user` 层做全量替换（幂等），删除某条规则立即生效，无需重启。

单一权威文件：`server/config/defaults.js`（默认值）+ 运行期 `storage/config.json`（覆盖项，可选）。**结构化配置进 JSON，环境变量只用于部署差异单值**。

{

  },

环境变量覆盖白名单（**只允许单值**）：`ZC_PORT`、`ZC_HOST`、`ZC_STORAGE_ROOT`、`ZC_DATA_DIR`、`ZC_LOG_LEVEL`。

校验规则（`server/config/schema.js`）：

- `storage.root` 必须存在且可读可写（否则启动失败并给出明确原因）；禁止指向 `/`（避免白名单退化为"全盘可访问"）。
- `preflightFactor` 必须 ≥ 2（不允许配成 1，否则破坏 INV-04）。
- `parallelEnabled` 若为 `true`，启动时**告警并强制置 false**（v1 契约）。
- `delete.mode` 只接受 `log-only` | `trash`；未知值 → 告警并**回落 `log-only`**（安全默认：绝不因配置写错而真删文件）。
- `delete.mode` **不影响 INV-01**：无论哪种模式，`verifying` 阶段都必须先通过；校验未通过绝不进入 `deleting`。`log-only` 只决定「到了删除阶段要不要真删」，不改变阶段顺序。
- `delete.confirmTimeoutMs`（正整数，**默认 `1800000` = 30 分钟**；`0` = 不超时）—— `waiting_confirm` 的最长等待时长，**超时按放弃删除处理**（`delete.status='skipped'`，reason=`confirm_timeout`；**超时绝不等于确认**）。非法值（负数/非数字）→ 告警并回落默认值。
- 未知字段 → 告警不报错（向前兼容）。
- 敏感字段（`passwordHash`、token 哈希）不得出现在 API 响应与日志中。

## 九、产物与临时文件命名规则

### 9.1 产物（压缩包）

| 场景 | 命名 | 示例 |
|---|---|---|
| `single`，源是文件 | `<basename><ext>` | `/a/notes.txt` → `/a/notes.txt.zip` |
| `single`，源是目录 | `<目录名><ext>` | `/photos/2024` → `/photos/2024.zip` |
| `single`，多源 | 每个源各一个包（同上规则） | — |
| `bundle`，1 个源 | `<源名><ext>` | `/photos/2024` → `/photos/2024.zip` |
| `bundle`，N 个源 | `<首个源名> 等 N 项<ext>` | 参考实现 `compress.ts:100-104` 的命名法 |
| 指定 `outputDir` | 落在 `outputDir` 下，命名同上 | `/backup/2024.zip` |

`<ext>` 取格式包的 `ext`（`.zip` / `.tar` / `.tar.gz` / `.tar.zst`）。

### 9.2 防覆盖（绝不覆盖）

目标已存在时依次尝试 ` (1)`、` (2)`……直至空闲（对齐 `computeTarget`）：

```
2024.zip → 2024 (1).zip → 2024 (2).zip
```

- 后缀插入在**主扩展名之前**，复合扩展名整体保留：`2024.tar.gz` → `2024 (1).tar.gz`。
- 生成后的最终路径写回 `result.packages[].outputPath` 并回传前端。
- 约束：单个产物最多尝试 1000 次，超出 → `TARGET_EXISTS`（避免病态目录下死循环）。

### 9.3 临时文件

| 用途 | 命名 | 生命周期 |
|---|---|---|
| 压缩半成品 | `<最终产物名>.part`（同目录，保证同分区 rename 原子） | 成功 → rename；取消/失败 → 删除；**中断 → 保留** |
| 中断遗留的半成品 | `<最终产物名>.part.interrupted-<ts>`（启动恢复时由 `.part` 改名而来） | 保留（供取证 / 手动处理）；**不再阻塞重试**（重试创建新的 `.part`） |
| 配置/状态原子写 | `<文件名>.tmp`（如 `tasks.json.tmp`） | rename 后消失 |
| 任务级扫描中转（如需） | `storage/tmp/<taskId>/` | 任务终态时清理 |

- `.part` 与 `.part.interrupted-*` 一律**不允许下载**（API `INVALID_STATE`），两者都算"未完成产物"。
- 启动时不清理 `.part`（服务于"中断可重试"），只在用户重试/删除该任务时清理。
- **中断遗留的 `.part` 在启动恢复时改名为 `.part.interrupted-<ts>`**：这既守住 INV-10「保留证据」，又让「中断任务可重试」成立 —— 否则重试会因为遗留的 `.part` 撞上 INV-08「绝不覆盖」而必然失败（实现时真踩过这个矛盾）。

### 9.4 回收站与日志

```
storage/trash/<batchId>/<原相对路径>        # batchId = uuid，删除批次
storage/logs/delete-<yyyymmdd>.jsonl        # 每行一条删除记录
```

删除记录（每行一条，可追溯，M5 验收"删除操作有日志"）：

```json
{ "id": "<uuid>", "taskId": "<uuid>", "batchId": "<uuid>", "at": 1730000000000,
  "source": "/photos/2024/a.jpg", "trashPath": "<storageRoot>/…/<batchId>/photos/2024/a.jpg",
  "sizeBytes": 1048576, "reason": "compress_success_verified", "verifyStrategy": "crc" }
```

> 说明：`trashPath` 在文档示例里用 `<storageRoot>` 占位，实际值由运行期配置决定。

### 9.5 任务与产物的一致性规则

- `result.packages[].outputPath` 必须**存在于磁盘**且 `verified === true`，否则任务不得进入 `done`（INV-01 的前置）。
- `delete.targets[]` 必须是"已进包条目"的子集（INV-07）。**判定来源写死**：= 格式包 `create()` 返回的 `entryPaths[]`（实际写入归档的条目）**−** `result.skipped[]`。**不得**用"全部源条目"（`info.sources`）当删除集合；也**不得**用删除前重扫归档 `list()` 反推（大包成本高，且中央目录损坏时 list 结果不可信，而 `create` 刚成功过，它才是第一手事实）。
- **删除开始前必须再次复核集合差异**：差异非空 → 拒绝删除（`INVALID_STATE`）并记日志，整批不删。**目录级 target** 还须满足「目录 re-scan 内容 == 进包条目集合」才允许整目录删除；否则只删进包的文件，差异项与目录本身保留（记 `delete.skipped`，reason=`entry_mismatch`）。
