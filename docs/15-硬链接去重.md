# 15 硬链接去重（需求 + 评审结论）

> 2026-10-18 提出需求，2026-10-19 三批实现完成（见 §六）。本文件记录设计评审结论与实现补录。
> 分工：由 GLM-5.3-Flash 负责实现，排期在 M8 收口之后（避免与主开发同时改 `web/`）。

## 一、需求

指定一个目录，扫描其中文件，按**白名单文件类型**（典型是视频/大文件）建立硬链接去重：

- 典型场景：几个目录里存着同一部影片的多份副本 → 合并成一份物理数据，省出整份空间
- 必须有保护机制（系统文件、不该动的目录）
- 前端可交互：扫描 → 预览能省多少 → 执行

## 二、评审结论：三个必须先纠正的问题

### ① 抽样哈希不能判定「重复」（会丢数据）

外部建议原话：*"先按 file.size 分组，大小相同则取头部和尾部各 4KB 做 MD5，避免全量读取几百 GB。"*

**问题**：抽样只能证明"部分相同"，不能证明"完全相同"。反例：

- `S01E01.mkv` 与 `S01E02.mkv`：同系列、大小相近、**容器头一致、索引尾往往也一致**，中间内容完全不同
- 一旦被判"重复" → 建硬链接 → **两份合并成一个 inode，其中一集的内容永久消失**

**正确做法**：

1. `size` 分组（零成本，先砍掉绝大部分候选）
2. 头 + 尾 + **中间随机 2~3 段**抽样 → **仅作快速筛**
3. **最终判定必须全量哈希**（或逐块比对）
4. 大文件慢是**安全代价**：dry-run 阶段异步算、进度可见；宁可跑 20 分钟，不能拿数据赌

### ② 黑名单别另写一套，复用 M6 + 路径白名单

外部建议列了 `.git` / `node_modules` / `/proc` / `/sys` / `/etc` / `/usr`。但项目已有两套现成机制：

| 现成机制 | 语义 | 本功能该用吗 |
|---|---|---|
| **M6 三层黑名单**（全局 15 条已压缩格式 / 用户 / 任务级） | "这些格式不值得压" | ❌ 语义不同，别复用 |
| **路径白名单**（`server/core/fs/safePath.js` + `INV-06`） | "这些路径不许访问" | ✅ 保护目录走这里 |

**所以**：保护目录 → 走**路径白名单 / 扫描根限制**（直接拒绝，连扫都不扫）；文件类型筛选 → 走本功能**自己的白名单扩展名**（用户可配）。**不要再写第三套黑名单**，否则三套规则迟早互相矛盾。

### ③ 前端不引 `Element Plus`

项目前端是**手写 CSS + `lucide-vue-next`**，没有 UI 组件库。本功能用现有风格实现；需要组件就自写（如确认弹窗复用已有的 `PromptDialog.vue`）。

## 三、实现规格（评审后）

### 后端 API（遵循项目 `/api/v1/` 规范）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/hardlink/scan` | 扫描并返回重复分组（**默认 dry-run，不动任何文件**） |
| POST | `/api/v1/hardlink/execute` | 对指定分组执行硬链接（需显式确认） |
| GET | `/api/v1/hardlink/tasks/{id}` | 进度查询（进度事件可复用任务系统 SSE） |

### 扫描

- 递归遍历目标目录，**只处理白名单扩展名的普通文件**
- 跳过：符号链接（`lstat().isSymbolicLink()`）、**已有硬链接的文件（`nlink > 1`）**、跨文件系统条目（`dev` 与扫描根不同）
- 分组：`size` → 抽样快筛 → **全量哈希**
- 只报告「组内 ≥ 2 个」的分组

### 执行（替换顺序是安全核心）

对每个"副本"：

```
1. rename(副本, 副本 + '.hl-tmp-<随机>')   // 先把旧副本挪走，原名腾出来
2. link(主文件, 副本)                      // 用硬链接占住原名
3. unlink(临时名)                          // 删掉旧副本
```

**为什么不能"先删后建"**：若已删原副本而未建链接时崩溃 → **数据永久丢失**。按上面顺序，最坏只是留下一个 `.hl-tmp-*` 临时文件，**数据始终有一份可达**。

**必须捕获的错误码**：`EXDEV`（跨文件系统，硬链接的硬限制）、`EEXIST`（目标已存在）、`EPERM`（权限不足）、`ENOSPC`。

**操作日志（必须）**：每次成功/失败都记 `{时间, 主文件, 副本, 结果, 错误码}`，落 `storage/logs/hardlink-*.jsonl`。**没有日志就无法回滚或排查**。

### 前端

- 扫描目录选择 + 白名单扩展名（默认 `mp4 / mkv / avi / mov / iso / zip / 7z`）
- **dry-run 默认开启**：先看"能省多少"，再决定执行
- 结果按组展示（组内路径 + 大小 + 校验状态）
- 执行前**强制确认弹窗**，文案必须说清：**建硬链接后，修改或删除其中任一文件会影响全部副本 —— 只对只读媒体使用**

## 四、风险定级与纪律

**风险等级：与 M5（删除原文件）同级** —— 都是不可逆的信息合并。因此：

- dry-run 默认开；执行需二次确认
- 操作日志必须落盘
- **反例自证**：临时把"全量哈希"改成"仅头尾抽样"→ 测试**必须变红**
- 测试必须造出**伪造重复**：同大小 + 同头尾 + **中间不同** → 断言**不得**被合并。这条测试是这个功能的守门人，缺了它等于没测

### 6.1 实现后新增的关键设计（超出原规格）

| 项 | 做法 | 为什么 |
|---|---|---|
| **`link` 失败回滚** | `link` 抛错时把临时文件 `rename` 回原位 | 否则第 1 步已挪走副本，`link` 一失败原名就空了，用户看到的是「文件消失」 |
| **执行前服务端重新全量哈希** | 不信任客户端传来的判定（扫描到执行之间文件可能变） | 内容不一致则整组跳过（`content_changed_since_scan`） |
| **主文件确定规则** | `absPath` 字典序最小（**不用 mtime**） | mtime 随访问变化 → 同一批数据两次扫描选出不同主文件，不可复现 |
| **快筛含「中间随机 2 段」** | 头 4KB + 尾 4KB + 中间 2 段（各 4KB） | 见 6.2 ① —— 它是一道**独立的第二防线**，不是性能优化 |

### 6.2 三个只在实现/联调期暴露的坑

**① `Math.random` 破坏快筛可比性（最隐蔽）**

`sampleFingerprint` 的中间段偏移用了 `Math.random` → **相同文件每次读到不同位置 → 指纹必不同 → 真重复被快筛排除**（实测 scan 返回 0 组）。

- 单测全绿（没覆盖「同一文件采两次样」）
- 只有**端到端冒烟**才暴露
- 修复：偏移从 `size` **确定性派生**（相同文件同指纹可比较；不同 size 组位置不重叠，仍满足「防恰好取到相同结构区」的原意）

**② 反例自证第一次没红**

注入「抽样当终判」没红 → 因为**快筛本身含中间随机段**，伪造对在快筛阶段就被排除，终判没机会犯错。

- 改成**模拟外部原始建议**（仅头尾 4KB、砍掉中间段）后，守门人测试才红，并当场复现「S01E01/E02 丢一集」的数据丢失场景
- **教训**：反例自证要**按原始的错法错一次**，而不是按当前实现随手破坏 —— 破坏位置选错，测试绿了也不代表守门人有效

**③ 改名残留导致 `ReferenceError`**

`execute` 的 `toAbs()` 里写的是 `return item.absPath`，但变量已改名成 `resolvedEntry` —— 一旦执行硬链接就崩。**因为扫描一直 404 没走到那里，长期未暴露**。

### 6.3 测试纪律（本轮新增）

- **测试不许污染用户回收站**：`test-all.sh` export `ZIPCALM_TRASH_BACKEND=project`（见 `docs/06` §七）
- 单测夹具自建自清，且**要清回收站里的那份**（原路径删掉后副本在 `#recycle` 里）
