# 05 任务系统与进度推送

> 定位：进度连续性的实现方式、任务状态落盘、SSE 推送与断线重连。
> 本文结论已与 `server/core/task/` 实现核对（2026-10-24）。

## 一、进度连续性：事件驱动，不是定时采集

「进度连续」的本质是**每处理完一个文件就刷新一次**，而不是每 500ms 采一次。

- 库方案：监听 `entry`（archiver）/ `onentry`（node-tar）事件，每进一个文件发一条进度
- 二进制方案：`zip -v` / `tar -v` / `zstd` 都会往 stdout 输出当前文件，逐行解析即进度
- 前端：SSE 实时推，**不是轮询**

**为什么不用定时采集**：定时采集会遇到"采的时候刚好没进展 → 显示卡住"。事件驱动是"有进展才刷新"，体验完全不同。

## 二、进度模型

进度是**一个对象**，字段如下（`server/core/task/manager.js` 的 `emptyProgress()`）：

| 字段 | 含义 |
|---|---|
| `percent` | 百分比（由其他字段计算） |
| `processedBytes` / `totalBytes` | 字节级进度 |
| `processedFiles` / `totalFiles` | 文件级进度 |
| `currentFile` | 当前正在处理的文件 |
| `packagesDone` / `packagesTotal` | 打包模式下的包级进度（单独压缩模式用于「第 X/N 个包」） |
| `speedBps` | 当前速度（字节/秒） |
| `etaSeconds` | 预计剩余秒数 |
| `updatedAt` | 最后更新时间 |

**展示优先级**：文件级（「已处理 X/Y 个文件」）比字节百分比更直观；字节级用于算速度和 ETA。单独压缩模式下另有包级进度，形成「第 X/N 个包 + 包内 Y/M 个文件」的两层体验。

## 三、串行队列 + 并行占位

单用户 NAS 场景选**串行**：

- 压缩是 CPU 密集，并行会互相抢资源
- 并行会让进度显示复杂化（多任务同时进行，进度条怎么显示？）
- 串行 + 队列 = 进度可预测、UI 简单、失败好回滚

**并行开关保留但固定关闭**：

- 配置项在，UI 开关置灰，悬停提示"暂未启用"
- 代码读取配置时即使值为真也强制串行（`queue.parallel` 恒为 `false`），只留钩子
- 将来启用时只改开关逻辑，UI 与配置不用动

## 四、任务状态落盘

**两个文件，职责不同**：

| 文件 | 内容 | 写入方式 |
|---|---|---|
| `storage/tasks.json` | **非终态**任务 + `failed` / `interrupted` 任务 | 原子写（写 `.tmp` → rename）+ **500ms 节流** |
| `storage/task-history.jsonl` | 每次进终态**追加一行** | 只追加；内存缓存最近 200 条（`limits.taskHistoryMax`） |

**为什么不全量写盘**：任务进度更新频繁，每次全量写会让磁盘 IO 成为瓶颈（同类项目的常见坑）。节流 + 原子写兼顾了「不丢状态」与「不打满磁盘」。

**为什么分两个文件**：活动任务需要频繁更新（小文件、整体覆盖）；历史记录只需追加（大文件、只增不改）。混在一起会让每次进度更新都要重写整份历史。

## 五、进度推送：SSE

### 协议约定

1. **连接建立后第一帧必是 `snapshot`** —— 进度是「状态」不是「消息」，重连先拿快照（INV-05）
2. 之后推增量事件，每帧带 `seq`（序列号）
3. **`since=<seq>` 续传**：窗口内补发增量；窗口外（replay 返回 null）只靠快照兜底
4. SSE 的 `id` 字段用 `seq`，浏览器自动带 `Last-Event-ID`，前端可据此续接

### 断线怎么办

- 连接断了 → **任务继续跑，状态继续写盘**
- 前端重连 → 拉快照 → 继续接收增量
- 核心原则：**进度是"状态"，不是"消息"。消息丢了可以重拉状态。**

## 六、服务重启时在途任务

- 压缩到一半的 `.tmp` 产物：**保留**，便于用户判断/重跑
- 不能续压的格式：标记为 `interrupted`，让用户决定重跑还是删 `.tmp`
- **绝对不能**：重启后把 `.tmp` 当正式产物，或把原文件删了

启动时执行对账（`server/core/task/recovery.js`）：把上次未完成的任务标为 `interrupted`，并核对删除状态，确保原文件安全。

## 七、删除原文件的时机

这是最危险的环节，流程固定为：

```
压缩完成 → 校验压缩包（CRC / 解压测试）→ 通过 → 标记"可删除"
        → 等待确认（或任务配置里已确认）→ 删除原文件（进回收站，不是真删）
        → 记录删除日志
```

**任何一步失败，原文件都不删。** 详见 [06-删除原文件与磁盘预检.md](06-删除原文件与磁盘预检.md)。

## 八、验收要点（M3）

- 关掉浏览器，任务继续跑
- 重新打开页面，能看到当前任务的实时进度（先快照再增量）
- 服务重启后，未完成任务标记为 `interrupted`，可重试
- 能取消正在执行的任务
- 同一时刻只有一个任务在执行（串行），后续任务排队
- 任务历史可查（最近 N 条）

**关键测试**：`kill -9` 服务进程，重启后状态文件里的任务应为 `interrupted`，且 `.tmp` 产物保留。

```
├── manager.js     任务管理器（状态机、串行队列 activeId、进度聚合）
├── store.js       落盘与读取（tasks.json 原子写+节流 / task-history.jsonl 追加）
├── recovery.js    启动对账（中断任务标记、删除状态核对）

```
