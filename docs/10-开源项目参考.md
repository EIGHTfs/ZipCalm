## 二、采纳的做法

### 1. 插件契约 + 格式注册表（来自 compress-mcp-server）

定义统一的 `CompressionHandler` 接口，各格式实现它，再用**注册表**统一调度 —— 新增格式只加一个 Handler 并注册，不改总入口。

**本项目落地**：`server/plugins/formats/<id>/index.js` + 启动扫描自动注册（见 `docs/03`）。

### 2. 后台任务 + SSE + 取消（来自 file-manager / node-task-manager）

- 任务独立于连接：状态落盘，前端断线重连先拉快照再续接增量
- SSE 单向推送足够（进度/状态/完成都是服务端 → 客户端）
- 取消要能真正终止执行，并清理临时产物
- 流式进度优于定时采样

**本项目落地**：`docs/05` 的整篇设计（任务落盘、SSE 首帧快照、`since` 续传、取消与超时）。

### 3. root 白名单（来自 cloudcmd）

路径防护的正面实现：所有文件接口以某个 root 为基准，拒绝 `..` / 绝对路径 / 盘符 / NUL / 符号链接越界。

**本项目落地**：`server/core/fs/safePath.js` + INV-06；多存储根时**按请求注入 rootAbs**，不改全局。

### 4. 打包/解压的事件转发（来自 node-fileop）

文件操作库把底层事件（entry 级）转发给上层，上层据此算进度、记日志。

**本项目落地**：格式包 `create()` 返回可监听进度的对象；orchestrator 聚合为 11 字段的 progress 结构。

### 5. 校验和与错误分类（来自 kadi-file-manager）

压缩后校验（CRC / 条目比对）+ 错误按类型分类返回，而不是笼统「操作失败」。

**本项目落地**：`verify.js` 校验 + `ERROR_CODES` 机器可读错误码。

## 三、否决的做法（反面教材）

| 项目做法 | 为什么不采纳 |
|---|---|
| **wfmanager 的"路径穿越防护"** | 初判「实现得很干净」，**实际不成立**：只有 `path.resolve`，没有白名单校验。→ 印证「看起来安全的实现要逐行核」 |
| **wfmanager 的压缩接口** | 压缩本身流式，但**接口同步返回**（压完才响应），没有后台任务与进度推送 → 大文件场景不可用 |
| **wfmanager 的 SSE** | 断线重连逻辑可参考，但缺少任务快照机制，重连后丢失历史进度 |
| **WASM 版 zstd** | 性能比内置实现差一档，只作兜底（本项目最终用 Node 内置 zstd，零依赖） |
| **原生绑定 zstd（@mongodb-js/zstd）** | 需在目标机编译，NAS / ARM 上易卡死 |

## 四、zstd 的 JS 实现对比

| 实现 | 特点 | 适用 |
|---|---|---|
| `bokuweb/zstd-wasm` | 条件导出（node / browser / types），有最小 ESM 示例 | 需要 WASM 兜底时 |
| `kpanuragh/zstd-js` | 纯 JS，无原生编译 | 极致零依赖场景 |
| `structured-world/structured-zstd` | Rust + WASM，构建链重 | 追求性能、可接受构建成本 |

**本项目结论**：都不需要 —— Node ≥ 22.15 的 `node:zlib` 内置 zstd，零依赖、流式、跨平台（见 `docs/02`）。

## 六、总结

1. **插件契约 + 注册表**是插件化架构的标准形态，直接照做
2. **任务独立于连接**是后台任务系统的关键，快照 + 增量缺一不可
3. **路径白名单要从第一天做**，且要逐行核实现（wfmanager 的教训：有 `path.resolve` 不等于有白名单）
4. **零依赖优先**：zstd 用 Node 内置，省掉一整类部署问题
5. **参考项目只学做法，不复制代码** —— 各项目许可证不同，直接拷贝有合规风险
