# M5 删除链路审查与修复

> 审查对象：删除原文件链路（`orchestrator` / `deleter` / `verify` / `manager`）。
> 审查方式：白盒静态审查（读代码 + 读契约），逐条对照 `docs/M0/不变量清单.md` 与 `数据模型.md`。
> 本文只留结论：发现的问题、后果、修复方案与复验门禁。

---

## 一、审查结论概要

共发现 **10 个真问题**（P-01~P-10）与 **7 处契约漂移**（D-1~D-7）。按后果分级：

| 级别 | 问题 | 后果 |
|---|---|---|
| **会导致数据丢失** | P-01、P-04、P-06 | 未进包的文件被删 / 新改动被删且包里是旧版 |
| **服务级不可用** | P-03 | 一次未确认的删除任务永久阻塞整个队列，且无法取消 |
| **契约违背** | P-02、P-05、P-09 | 安全屏障失效 / 路径校验缺失 / 枚举漂移 |
| **功能失效（跨卷）** | P-07 | 跨分区删除全部失败 |
| **可对账性缺失** | P-08、P-10 | 崩溃窗口日志断裂、部分删除后状态混乱 |
| **安全 bug（现行）** | D-2 | 内部绝对路径泄漏进 API 响应 |

## 二、真问题清单

### P-01 删除集合取自全部 sources，而非「实际进包 ∩ 未跳过」

- **位置**：`orchestrator.js` 的 `stageDelete`（targets 由 `info.sources` 全量映射）
- **契约要求**：INV-02 —— `delete.targets[] ⊆ 进包条目 − skipped`；数据模型 §9.5 还要求「删除前复核集合差异，非空 → 拒绝」
- **现状**：无任何集合差异复核
- **触发**：黑名单接入后，`skipped` 条目仍在 `sources` 中被列入删除集合；或格式包内部跳过（空文件、读取失败、symlink）
- **后果**：**数据丢失** —— 未进包的原文件被删，回收站也救不回内容差异（用户以为压了 100 个，包里 98 个，删了 100 个）
- **修复**：见 F-03

### P-02 expectedBytes 传入但不比对（INV-03 只兑现一半）

- **位置**：`orchestrator.js` 的确认门禁
- **契约要求**：INV-03 ③ —— 二次确认必须回传 `expectedFiles/expectedBytes`，与实际值不一致则拒绝
- **现状**：只校验 `expectedFiles`，`expectedBytes` 被透传后丢弃
- **触发**：确认弹窗打开后、点确认前源文件被外部改动
- **后果**：契约违背；用户基于过期信息确认
- **修复**：见 F-02

### P-03 waiting_confirm 卡死串行队列，且该阶段不可取消

- **位置**：`manager.js` 的 `pump`（持有 `activeId` 期间 `await runner`）、`CANCELLABLE_PHASES`、`cancelTask` 守卫；`orchestrator.js` 的 `waitConfirm`（无超时永久 await）
- **复现链**：
  1. 任务 A `keepOriginal:false, deleteConfirmed:false` → 压缩校验完成 → 进入 `waiting_confirm` 挂起
  2. `runCompressTask` 未 resolve → pump 的 `await runner` 未返回 → `activeId` 仍为 A
  3. 任务 B 入队，pump 命中 `if (activeId) return` → B 永久 `queued`
  4. 尝试取消 A → `CANCELLABLE_PHASES` 不含 `waiting_confirm` → 抛 `INVALID_STATE`
  5. **只要用户不点确认（或关掉页面忘了），整个队列永久阻塞，无 API 可解锁**
- **性质**：设计缺口（契约未回答「等待期间队列怎么办」）+ 实现遗漏（无超时、不可取消）
- **后果**：压缩功能整体假死，用户唯一自救是重启服务
- **修复**：见 F-04

### P-04 目录级删除可能多删「未进包」的内容

- **位置**：`orchestrator.js` 的 targets 构造（目录级 source）+ 契约侧 targets 示例本身是 `{path:'/photos/2024', kind:'dir'}`
- **证据**：删除粒度是**源条目**（可能整个目录），而校验只验归档完整性，不建立「目录内每个文件都进了包」的对应关系。目录压缩成功 ≠ 目录内全部内容进包：空目录、坏 symlink、压缩中被外部改动/删除的文件、读 I/O 错误的文件都可能没进包
- **后果**：**数据丢失**（与 P-01 同根，但即使没有黑名单也可能触发 —— I/O 错误文件就是例子）
- **修复**：与 P-01 共用防线（见 F-03）

### P-05 回收站移动前的路径安全复核缺失

- **位置**：`deleter.js` 的 `moveToTrash`（`userPath` 直接按 `/` 切段拼进 trash 路径）
- **证据**：`userPath` 未过 `safePath` 复核；`absPath` 也来自调用方而非重新 resolve
- **契约要求**：INV-06 —— 任何接受路径的入口都必须过白名单。删除阶段是独立入口
- **后果**：潜在越权移动（当前被上游挡住，但对未来调用方是裸的）
- **修复**：见 F-06

### P-06 「校验通过 → 等待确认/删除」期间源文件变动无 re-check

- **位置**：`orchestrator.js` 校验完成 → `stageDelete` 之间隔着 `awaitDeleteConfirm`
- **证据**：校验通过到执行 rename 前，没有任何 stat/re-scan 比对；删除集合与 absPath 都是校验前确定的
- **触发**：用户在确认弹窗停留期间用另一工具（或 SMB 挂载）改了源目录
- **后果**：**数据丢失** —— 包里是旧版本，删掉的是新版本，新改动丢失且包里没有
- **修复**：见 F-05

### P-07 trash 跨分区移动会失败（EXDEV）

- **位置**：`deleter.js` 的 `fsp.rename(target.absPath, destination)`
- **证据**：`rename` 不跨文件系统（Linux EXDEV）；`trashDir` 默认 `storage/trash`，与源文件通常不同卷
- **触发**：源分区 ≠ trashDir 分区，`mode=trash`
- **后果**：所有删除逐条失败，跨卷场景功能全废
- **升级风险**：若为「修复」而回退到 `unlink`，就变成数据丢失
- **修复**：见 F-07

### P-08 崩溃窗口：rename 进 trash 与写日志非原子

- **位置**：`deleter.js`（先 rename，后 `recordLog`）
- **触发**：rename 完成后、appendFile 完成前进程被 kill
- **后果**：文件安全（在回收站），但审计链断裂 —— `delete-*.jsonl` 无记录、任务停在 `deleting`，破坏「删除操作有日志可追溯」的验收
- **修复**：见 F-09

### P-09 log-only 模式下 `delete.status` 出现契约外枚举

- **位置**：`orchestrator.js`（`mode === 'log-only' ? 'logged' : 'deleted'`）
- **证据**：契约枚举只有 `pending/deleting/deleted/skipped/failed`，无 `logged`
- **触发**：log-only 模式（**默认**）跑完删除阶段
- **后果**：契约违背 + 前端按枚举渲染会落未知分支；用户可能误以为已删
- **修复**：见 F-08

### P-10 中断恢复对 waiting_confirm/deleting 中间态的 delete 字段语义未定义

- **位置**：`manager.js` 的 `markInterrupted`（无条件把非终态迁 `interrupted`，不区分 phase）
- **证据**：`deleting` 中途重启 → 一半文件在 trash、一半在原地；`confirmResolver` 已不存在 → 重试会重跑全流程
- **后果**：不丢数据但状态混乱、日志难对账
- **修复**：见 F-09

## 三、契约漂移（实现 ≠ 契约文字）

| # | 契约 | 实现 | 处置 |
|---|---|---|---|
| D-1 | `delete.status ∈ {pending, deleting, deleted, skipped, failed}` | 产出 `'logged'`（log-only 默认模式） | 收敛（见 F-08：映射回 `skipped`） |
| D-2 | DeleteState 字段集固定 | 额外写 `mode/batchId/logFile/deleted/skipped/failed`；且 `targets` 有两套形状，API 响应可能含 `absPath` | **现行安全 bug**（内部绝对路径泄漏进 API），见 F-01 |
| D-3 | INV-03：files 与 bytes 都要比 | 只比 files | 实现遗漏，见 F-02 |
| D-4 | 删除前复核集合差异 | 无复核逻辑 | 实现遗漏，见 F-03 |
| D-5 | `waiting_confirm` 属活任务；但取消守卫排除该 phase | 与契约一致，**但契约本身有张力**：可无限期挂起却不可取消 | 设计缺口，契约需补「可取消」或「等待有界」条款，见 F-04 |
| D-6 | 删除阶段错误记 `delete.error`，不改任务 status | 基本符合；但错误码取自 `failed[0].code`，未校验是否在错误码枚举内 | 轻微，建议收敛 |
| D-7 | 删除日志字段 `{id, taskId, batchId, at, source, trashPath, sizeBytes, reason, verifyStrategy}` | 实际 `{ts, batchId, taskId, kind, reason, mode, source, sizeBytes, action, trashPath?, error?}`（无 `id`/`verifyStrategy`，时间叫 `ts`） | 风格级漂移，追溯能力等价；建议对齐或契约 v2 更新 |

## 四、修复清单

| # | 对应问题 | 修复内容 |
|---|---|---|
| **F-01** | D-2 | 任务对外的 `delete.targets` 剥离内部字段（`absPath` 等），只出 `{path, kind, sizeBytes}`；内部形状与对外形状分离 |
| **F-02** | P-02 / D-3 | 比对 `expectedBytes` 与 `Σ targets[].sizeBytes`，不一致抛 `VALIDATION_FAILED` 且不删除；补 bytes 维度的「数字不符」测试 |
| **F-03** | P-01 / P-04 / D-4 | 删除集合改为「**实际进包条目 ∩ 未跳过**」；删除前强制复核集合差异，非空 → 拒绝删除（`INVALID_STATE`）并记日志 |
| **F-04** | P-03 / D-5 | `waiting_confirm` 加入可取消集合（取消 → `delete.status='skipped'`、任务 aborted、队列恢复）；确认等待加**可配超时**（超时按「放弃删除」处理 —— **超时绝不等于确认**） |
| **F-05** | P-06 | 确认后、删除前对每个 target 做 `stat` 比对（size/mtimeMs/ino 与扫描快照），任一变化 → 跳过该条（`reason='source_changed'`），只删一致的 |
| **F-06** | P-05 | `deleteTargets` 入口对每个 target 的 `userPath` 跑与 HTTP 入口同一套 `safePath` 校验；`absPath` 由模块内部 `path.resolve(rootAbs, userPath)` 自推导，不信任调用方 |
| **F-07** | P-07 | EXDEV 时回退「copy → 校验 size → 原件移入**源分区内**暂存」；**严禁**任何路径回退到直接 `unlink` |
| **F-08** | P-09 / D-1 | log-only 模式的 `delete.status` 映射回 `skipped`（reason='log-only'），不扩枚举 |
| **F-09** | P-08 / P-10 | 启动对账：识别「`delete.status='deleting'` 且 `trashBatch` 非空」的任务，标 `failed` 并附 `trashBatch` 指引；对「trash 有 batchId 而日志无记录」补写 `reconciled-crash` 日志 |

**修复顺序**：F-01（安全 bug，改动小收益立现）→ F-03（数据丢失主因）→ F-02 / F-05 / F-06（安全屏障补全）→ F-04（服务级可用性）→ F-07 / F-08 / F-09（边界与对账）。

## 五、复验门禁

修复全部完成后必须通过：

1. **不变量脚本全绿**（INV-01/02/03/06/12）
2. **原文件不丢的四个场景**：校验失败 / 中途 kill / 磁盘满 / 权限不足
3. **数字不符测试**：`expectedFiles` 不符、`expectedBytes` 不符都要拒绝
4. **队列不阻塞测试**：未确认删除的任务 + 后续任务 → 后续任务能正常跑（或确认超时后队列恢复）
5. **跨卷删除**：源分区 ≠ trash 分区 → 走 copy+verify 回退，原文件不丢
6. **部分删除后重启**：断言原文件要么全在原位、要么全在回收站，任务状态与 `delete.status` 自洽
7. **API 响应不含内部字段**：`delete.targets` 无 `absPath`
