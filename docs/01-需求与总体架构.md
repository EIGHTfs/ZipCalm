# 01 需求与总体架构

> 定位：项目起点需求、决定架构的关键问题、必须提前想清楚的决策。
> 本文结论已与实现核对（2026-10-24），与代码不符处以代码为准并已修正。

## 一、项目起点需求

在 NAS 上提供一个 Node.js 网页服务端：浏览目录、选择文件或文件夹压缩，支持 zip / tar / tar.gz / tar.zst 多种算法与格式，并附带性能监控看板；实现上优先用开源库组装。

## 二、需求细化

- **核心目的**：压缩是为节约 NAS 空间，而不是"有个压缩工具"本身
- **任务模型**：压缩任务进任务列表、不阻塞网页；进度要连续（每处理完一个文件即刷新），而非按时间间隔采样
- **多选行为**：可选「每个文件/文件夹各自一个包」或「合并成一个包」
- **保留策略**：可选压缩后是否保留原文件
- **并发策略**：单人使用，默认串行排队；并行只留配置占位，暂不启用
- **实现选型**：库 vs 直接调用二进制，需按格式分别权衡

## 三、先定架构，别先挑库

功能看起来是"浏览 + 压缩 + 看板"，但真正决定架构的是三个问题：

**1. 压缩是同步还是异步？**

- 小文件（几十 MB）可以边压边流式返回，等待几秒即可
- 大文件夹（几 GB）必须走「后台任务 + 进度查询 + 完成后取用」
- 两者体验完全不同。只做同步，后面加异步等于重写

**2. 压缩产物是「下载即弃」还是「落盘保留」？**

- 下载即弃：省磁盘，但重试/多格式导出要重压
- 落盘保留：要管理产物生命周期、清理策略、磁盘配额

**3. 多用户还是单用户？**

- 单用户（NAS 自用）：几乎不用考虑并发隔离、配额
- 多用户：目录权限、任务隔离、资源抢占都要做

这三个定下来，库选型基本就定了。本项目按**异步任务 + 落盘保留 + 单用户**设计。

## 四、库选型（按功能拆）

### 压缩

| 格式 | 方案 | 备注 |
|---|---|---|
| zip | `archiver` | 成熟、流式、API 顺手；大文件内存占用低 |
| tar | `node-tar` | 比 tar-stream 封装好，支持 gzip 集成 |
| tar.gz | `node-tar` + 内置 `zlib` | `tar.create({ gzip: true })` |
| tar.zst | `node-tar` + **Node 内置 zstd** | node-tar 不原生支持 zstd，用 `node:zlib` 的 zstd 流拼管道（零依赖） |
| zstd 单文件 | 同上（`zlib.createZstdCompress`） | 见下方回退链 |
| 7z / rar | `node-7z` 调外部二进制 | 需系统装 7z/unrar，跨平台麻烦 |

**zstd 实现（已落地，`server/plugins/formats/_shared/tar/compression.js`）**：能力自探测 + 三级回退链。

1. **首选**：Node ≥ 22.15 的 `node:zlib` 内置 zstd（流式，零依赖、零编译、跨平台）。该 API 标注 `Stability: 1 - Experimental`，大版本升级需回归往返用例
2. **回退**：系统 `zstd` 命令（路径可用 `ZC_ZSTD_BIN` 覆盖）—— 本机实测没有该命令，故不能作首选
3. **都不可用** → 该格式 `available() = false` 并给出明确原因（不静默降级，前端按 `available()` 置灰）

排障开关：`ZIPCALM_DISABLE_BUILTIN_ZSTD=1` 可强制禁用内置实现，用于验证回退链真的生效。

**已弃用**：原生绑定 `@mongodb-js/zstd`（需在目标机编译，NAS/ARM 易卡）、WASM `zstd-codec`（性能差一档，仅作备用）。

### 文件浏览

- 不用 serve-index：它是给静态文件服务设计的，不可控
- 自己用 `fs.promises.readdir + withFileTypes` 遍历，配合路径白名单
- **目录穿越是这里的头号安全问题**：`path.resolve + startsWith` 白名单是底线

### 性能监控看板

分两层采集：

**系统层**（CPU、内存、磁盘 IO、网络）：`systeminformation` 信息全但调用开销不小；`pidusage` 只看进程级、轻量。

**Node 进程层**（事件循环、GC、堆）：`perf_hooks` 的 `eventLoopUtilization`、`process.memoryUsage()`，几乎零开销。

**图表库用 uPlot**（极轻、零依赖、时间序列专用）。不用 ECharts —— 为一块看板引入巨无霸不划算。

### Web 框架

- 单用户 NAS 场景：原生 `http` 就够，省一层依赖
- 需要路由、中间件、鉴权：**Fastify** 比 Express 现代、性能好、内置 schema 校验
- 本项目选 **Fastify**

## 五、几个必须想清楚的决策

### 1. 压缩任务的执行方式

压缩是 CPU 密集 + IO 密集。三个候选：

- Worker Thread：同进程内，共享内存，但有 V8 堆隔离问题
- 子进程：隔离彻底，通信开销大
- 外部二进制：完全隔离、性能最好，但要求系统有工具

**实际实现选择：主线程 + 流式管道 + 串行队列**（`server/core/compress/orchestrator.js` + `task/manager.js` 的 `activeId` 单槽位）。

理由：压缩全程是流式的（`archiver` / `node-tar` 都是流），**内存占用由流的高水位控制而非文件大小**，主线程不会被单个大文件钉死；同时串行队列保证全局只有一个压缩任务在跑，避免多任务争抢磁盘 IO。引入 Worker 的收益（隔离）在单用户场景下不足以抵消复杂度（进度转发、错误传播、生命周期管理）。

> 若将来需要并行压缩，再考虑 Worker 或子进程隔离；当前 `parallel: false` 是刻意选择，不是遗漏。

### 2. 进度反馈

选了 100 个文件压缩，最怕"点了没反应"。

`archiver` 与 `node-tar` 都有事件，但粒度不同：

- `archiver`：可监听 entry 事件（每个文件开始处理），总进度需自己算
- `node-tar`：事件更少，基本靠「输出字节数 / 预估总量」估算

**做法**：先遍历一遍拿到文件总数和总大小，压缩时用「已处理大小 / 总大小」算百分比。预扫在几万文件时会慢，但比"无进度"体验好得多。

### 3. 压缩产物的生命周期

落盘保留模式下必须定清：

- 产物放哪（临时目录 / 专用目录 / 源同目录）
- 保留多久
- 谁清理
- 磁盘满怎么办（拒绝新任务 + 告警）

**本项目结论**：产物放**源同目录**（命名加后缀），用户容易找；压缩后若删了原文件，目录里只剩压缩包，很清爽。磁盘不足时任务直接拒绝启动（见 `docs/06` 的预检规则）。

### 4. 取消与超时

- 取消要能真的终止（Worker 可 terminate、子进程可 kill、外部二进制可 SIGTERM）
- 压缩卡在某个大文件要能兜底
- 取消/超时后临时文件与部分产物要清理

### 5. 并发控制

同时来 5 个压缩任务，4 核机器直接炸。

- 轻量队列，并发上限 = CPU 核数 − 1
- 或更保守：串行压缩，队列里排着一个个来
- 看板要显示"队列中有几个任务"

**本项目选串行**，配置项 `parallel` 保留但固定为 `false`。

## 六、性能监控看板的坑

### 1. 监控本身的开销

采得太密（每秒一次全系统扫描）本身就成了性能问题。

**实际配置**（`server/core/metrics/collector.js`）：系统指标 **5 秒**一次，进程指标 **1 秒**一次，环形缓冲保留 **5 分钟**，前端 **2 秒**轮询一次。双口径实测开销 < 0.1% CPU。

### 2. 事件循环延迟怎么量

**不用 `perf_hooks.monitorEventLoopDelay`**：实测内置直方图在空载下也不够准。改用**定时器漂移法** —— 记录每次定时器的「计划触发时刻」与「实际触发时刻」，差值即延迟；取最近若干次采样的最大值作为"卡顿"判据。

### 3. 数据从哪来

- 后端定时采集 + 内存环形缓冲
- 前端轮询 `/api/metrics` 拿最新一段
- 不用 WebSocket 推 —— 除非要做秒级实时图，否则轮询简单可靠

### 4. 看板要展示什么

最小可用集：CPU 使用率（系统 + 本进程）、内存（RSS + Heap）、**事件循环延迟**（最关键，反映"卡不卡"）、磁盘 IO、活跃压缩任务数 + 队列长度。

不堆砌指标 —— 用户看不懂也不看。

## 七、同类项目的常见坑（本项目已防）

这些是在其他 Node 文件服务项目里反复出现的问题，本项目在设计阶段就纳入防线：

| 常见坑 | 本项目的应对 |
|---|---|
| 路径穿越（`/api/browse` 类接口） | 文件浏览接口一律走路径白名单（`..` / 绝对路径 / 盘符 / NUL / 符号链接拒绝） |
| 任务状态全量写盘 | 进度与看板数据不做每次全量写；任务状态用原子写 + 节流 |
| 同步 IO 阻塞 | 遍历大目录用 `fs.promises` |
| `.tmp` 残留 | 压缩中断的临时产物要清理；原子写失败也要清 `.tmp` |
| Token/凭据落盘 | 只存哈希，不存明文 |
| 优雅重启 | 重启前等在途任务完成或标记中断 |

## 八、架构结论

1. **异步任务模型**：压缩进任务列表，后台串行执行，SSE 推真实字节进度
2. **zstd 用 Node ≥ 22.15 内置 `node:zlib`**（零依赖），带系统命令回退链
3. **主线程流式管道 + 串行队列**（不是 Worker），内存由流的高水位控制
4. **路径白名单从第一天就做**，不事后补
5. **看板指标只留 5~6 个**，多了是噪音
6. **并发默认串行**，并行开关保留但固定关闭
7. **启动前预检磁盘空间**（两倍规则，见 `docs/06`），避免压到一半满盘

## 九、需求细化后的补充结论

> 完整展开见：[02-压缩格式与库选型](02-压缩格式与库选型.md)、[04-压缩模式与黑名单](04-压缩模式与黑名单.md)、[05-任务系统与进度推送](05-任务系统与进度推送.md)、[06-删除原文件与磁盘预检](06-删除原文件与磁盘预检.md)

### 1. 压缩产物的存放位置

同目录 vs 集中目录：同目录用户容易找但会"搞乱"文件系统；集中目录整齐但要跳过去取。

**结论：同目录**，命名加 `.zip` / `.tar.zst` 后缀。压缩后若删了原文件，目录里只剩压缩包。

### 2. 任务持久化

NAS 重启或服务重启，任务丢了怎么办？

**结论**：任务状态落盘；重启后对账，把中断任务标记为"已中断"，并确保**原文件未被删除**，用户可重新发起。残留 `.tmp` 产物在启动时清理。

### 3. 磁盘空间预检

压 100 GB，产物可能 30 GB，但过程中原文件 + 临时产物同时存在，峰值可能需要 130 GB。启动前必须预检，否则写到一半满盘，原文件也删不了。

**结论**：剩余空间 ≥ 待压量 × 2，不足则拒绝启动（详见 `docs/06`）。

### 4. 进度推送的连接管理

SSE 连接断了（关浏览器再打开），进度怎么恢复？

**结论**：任务状态存服务端，前端重连时先拉一次当前快照，再续接事件序号。**进度绝不只存在连接会话里。**
