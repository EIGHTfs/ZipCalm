# 14 工程执行约定

> **契约**管"做成什么样"，**本文**管"怎么做"。

## 一、每个任务的固定收尾（必做，不靠人提醒）

每完成一个功能任务，收尾按这四步走：

1. **跑一遍审计**（`code_audit`，本次任务用 `scope=diff`，必要时 `scope=full`）
   - **真实命中** → **顺手修掉**：函数过长 / 圈复杂度过高 / 重复代码 / 注释含会话措辞 / 未使用变量 / 缺失错误处理 等
   - **误报或设计使然** → 不动，但在汇报里说明为什么（如 CSS 大文件、参考项目目录、原始讨论转录）
   - 判据：**规则判错了事实**才是误报；规则正确命中了真实存在的东西（哪怕不想改）叫真命中，应修或显式豁免
2. **跑全套验收**：`bash scripts/test-all.sh`（八套全绿才算过）
3. **停服务、清残留**：`bash scripts/start.sh stop`，确认端口已释放、无残留进程
4. **汇报**：交付清单 + 实测证据（不接受"应该没问题"）+ 遗留事项

> **为什么把它写死**：审计警告会累积成债（M4 时全量已达 305 条）。每次顺手清掉**自己碰过的那部分**，边际成本最低；攒到后面集中清理，代价高且容易引入回归。

## 五、踩过的坑（别重复踩）

1. **不要在项目根直接 `npm install`** —— 工作区是 noexec 挂载，且 npm reify 会删掉 `node_modules` 软链 → 一律走 `setup-dev-deps.sh`
2. **套件有服务依赖顺序**：`m1`/`m2`/`m3` 要求服务**已在跑**；`crash`/`probes`/`retention`/`m4` 自己管服务。顺序错会造成整片假失败 → 用 `test-all.sh`
3. **`npm run build` 后必须重启服务**：`@fastify/static` 用 `wildcard:false`（启动时按文件注册路由），不重启则新哈希资源 404、页面白屏
4. **测试脚本日期口径**：服务端日志用**本地日期**，脚本若用 `toISOString()`（UTC）会在凌晨差一天、盯错文件 → 统一按本地日期
5. **`storage/fs-root/` 下的测试夹具**是运行态数据（已 gitignore）；大夹具用完即清（或移入回收站）

## 六、审计豁免的三种方式（实测结论，别重复踩）

| 方式 | 实测是否生效 | 说明 |
|---|---|---|
| `.auditignore`（文件/目录级） | ❌ **对已跟踪文件无效** | 豁免判定走 `git check-ignore`，而 **git 语义下已跟踪文件不受 ignore 规则影响**。只有「尚未提交的未跟踪文件」才可能被它拦下 |
| 文件头标记 `dsh-skip-quality` | ⚠️ **视规则而定** | 它覆盖的是 `blacklist` / `func-lines` / `magic-number-smart` / `comment-density` 等 kind；而 `conv-user-decision`、`conv-session-ref` **不在其豁免清单里**，写了也不生效 |
| 私有库豁免 | ✅ **自动生效** | 私有仓库下审计**只报告不拦截**（`privateExempt`）—— 文档措辞类命中不会挡住提交 |

**三条教训（都是真踩过的）**：

1. **改豁免配置前先做最小实测** —— 拿一个文件验证目标规则是否真的被免除，再铺开。凭「代码里有这个机制」就假定生效，会连做两轮返工。
2. **`scope=diff` 的拦截数不能代表全量** —— diff 只报**变动行**的命中，很容易得出「已经豁免了」的假结论。**验证豁免必须用 `scope=full`**。
3. **写豁免标记时，说明文字本身不能含被禁词面** —— 例如在标记里写「含某某等词」，这行标记自己就可能命中规则，反而把拦截数抬高。

## 七、判读纪律：疑似问题必须走完整链路再定性

**教训（2026-10-17，M5 审查中审查方与验收方都栽在这里）**：`orchestrator.js:286-291` 构造的 delete targets 含 `absPath`，`manager.js:143` 的 `publicTask` 又原样透出 —— 看起来是确凿的「绝对路径泄漏进 API」。但**中间还夹着一层映射**（`orchestrator.js:124` 调用的 `buildDeleteTargets`：它把 `userPath → path`、`size → sizeBytes`，`absPath` 根本不进 `info.delete.targets`）。**两边都漏读了那一层，把它当成已确认的安全 bug。**

由此定下三条：

1. **「看到了可疑代码」≠「证实了问题路径」**。要定性为真问题，必须**从输入到后果走完整条链路**，尤其注意中间是否有转换 / 兜底 / 白名单。缺一环就只能标「**待实证**」。
2. **定级前先跑最小实证**（构造最小依赖 + 探针读实际输出）。静态读代码容易在「中间层」翻车；运行时探针一次就能拍死。
3. **误判要留记录，不静默改**。在报告 / 方案里标注「误报收回 + 实证记录」，保留「当初为什么会误判」的证据 —— 这比改干净更有价值。

> 配套：审计误报判据说的是「规则有没有判错事实」；本节说的是「**我们自己有没有把疑点当结论**」。两条一起用。

## 八、版本与 README 维护纪律

**版本号两处必须同值**：`package.json` 的 `version` 与 `shared/app-version.js` 的 `APP_VERSION`（后者是前后端共用的单一来源，前端界面版本也取它）。

**升版规则**：

| 改动性质 | 动作 |
|---|---|
| **里程碑完成**（新增功能 / 格式 / 能力） | 升 **minor** → `0.x.0` |
| **修复 bug / 优化**（行为或契约无新增） | 升 **patch** → `0.x.y` |
| 纯内部重构（无行为、无契约变化） | 可不升版 |

**升版时三处同步**：

1. `package.json` → `version`
2. `shared/app-version.js` → `APP_VERSION`
3. `README.md` → 「版本记录」表加一行，并更新「当前进展」的里程碑状态

**README 是持续维护的活文档**，不是一次性产物：

- 「当前进展」的里程碑状态（✅ / ⏳）与「已实现能力」必须跟得上代码 —— 不许停留在旧阶段（本项目真出现过「README 写着尚未开始写代码，实际已到 M4」）
- 功能有增删 → 同批更新「已实现能力」条目
- 提交前扫一眼「版本记录」与「当前进展」：**版本升了吗？描述还跟得上代码吗？**

## 九、前端改动自检：必须走「build → 重启 → cache-bust」三步

**教训（2026-10-18，M7 看板开发中踩到）**：改完前端执行 `npm run build` 后**没重启服务**就直接刷新页面 → **整页白屏**。

**根因**：静态资源服务用的是 `wildcard: false`，构建产物带新哈希（如 `index-a1b2c3.js`），而服务进程仍持有旧清单 —— **新哈希资源在重启前一律 404**。

**判读纪律**：看到白屏，**不要先怀疑自己刚写的组件崩了**，先确认资源有没有加载到：

1. 打开 DevTools → Network，看 `index-*.js` 是不是 404
2. 是 **404** → 重启服务再刷新（不是代码问题）
3. 是 **200 但控制台报错** → 才是组件问题

**三步固定动作**（少一步都可能误判）：

```
1. npm run build                       # 产出新哈希资源
2. bash scripts/start.sh restart       # 让静态服务重新扫描产物
3. 打开页面时带 cache-bust 参数        # 如 ?v=$(date +%s)，绕过浏览器缓存
```

**为什么值得写进来**：这个坑的代价不是"多花五分钟"，而是**把「资源 404」误判成「组件崩了」**，然后去改本来没问题的代码 —— 方向一错就白干。

## 十、前端改动自检：另外两件必须在交付前做的事

### ① 必须看窄视口（390×844）

只在 1920 宽下验收，会漏掉整类问题。本项目 M8 一次实测就抓到 **3 个只在窄屏暴露的真 bug**：

| 窄视口才暴露的 | 1920 宽下的表现 |
|---|---|
| 侧栏常驻 → 主内容被挤成「竖排单字」 | 完全正常 |
| 底部任务条不换行 → 390px 页面被撑到 **676px** | 完全正常 |
| 断点样式根本没生效 | 看不出来 |

**窄屏检查清单**：
- 无横向滚动（`scrollWidth === clientWidth`）
- 侧栏为抽屉（不是常驻）
- 所有按钮 ≥ 40px、行高 ≥ 44px

### ② 必须扫「悬停专属操作」

```bash
grep -rn "opacity: *0" web/src
grep -rn "visibility: *hidden" web/src
```

**任何只在 `:hover` 时可见的操作，在触屏上等于不存在**。当前基线：**0 处**（唯一 `opacity` 是 disabled 态 0.5）。改前端前后都扫一遍，数字涨了就要审。

## 十一、功能验收：必须用浏览器实际点击，不能只跑 API

**任何涉及网页的功能，验收标准是「用浏览器走完整流程」，不是「接口返回 200」。**

### 必做五条

1. **实际点击** —— 用浏览器打开页面，点按钮、填表单、走完整个用户流程（登录 → 选文件 → 压缩 → 看进度 → 看产物）
2. **看画面** —— 布局是否错乱、文字是否可读、按钮是否可见可点、空态与错误态是否友好
3. **截图留证** —— 关键步骤与最终结果各一张
4. **窄视口必看** —— 390×844（见 §十 ①）
5. **API 只作交叉验证** —— 确认产物真落盘、任务状态真变了；但**不能替代界面验收**

### 为什么这条必须写死

**API 通 ≠ 页面正常。** 历史上反复出现：

| 现象 | API 表现 | 只有看页面才发现 |
|---|---|---|
| 压缩抽屉的「开始压缩」被底部操作栏压住 | 接口 200 | 按钮点不到，用户以为功能没用 |
| 侧栏把主内容挤成「竖排单字」 | 接口 200 | 1920 宽完全正常，390 宽才暴露 |
| 文案显示成「产物将保存到「VirtualDSM」的 」（末尾空） | 接口 200 | 字段名写错渲染成空串，控制台不报错 |
| 压缩按钮灰到几乎看不见 | 接口 200 | 用户找不到入口，认为「没有这个功能」 |

**结论**：涉及界面的验收，浏览器实测是**必需项**，不是加分项。

## 十二、CIFS 挂载环境：写文件必须走 bash 兜底（2026-10-26）

工作区当前挂载在 **CIFS**（`\\10.10.10.64\Artificial Intelligence`，原 NFS 已停用）。此环境下 **`write` / `edit` 工具会失败**：

```
EPERM: operation not permitted, chmod '<file>.<pid>.<rand>.tmpdir'
```

**根因**：`write`/`edit` 的实现是「写临时文件 → `chmod` 设定权限 → `rename` 原子替换」。CIFS 不实现 POSIX `chmod`，第二步就 EPERM，整个写入中断。

**误判陷阱**：报错指向 chmod，容易误判成目录权限问题 —— 但 `ls -ld` 显示 `drwxrwxrwx`、`touch` 也能成功。**看到这个错误不要再查目录权限，直接换写法。**

## 十三、测试断言口径：网络盘（CIFS/NFS）上的瞬时抖动要「重试后仍失败」才算失败

**问题**：断言直接拿"一次性读数"当绝对值判据时，网络盘的读缓存/写入窗口会把**正常的原子写**判成失效。
实测例子：`tasks.json` 原子写检查连续采样 25 次全解析成功，但在整套件连跑时出现过 1/25 —— 单跑复现不了。

**口径**：

- **区分三档**，不要只有"成功/失败"两档：
  - 直读成功 → 正常
  - 直读失败、**有界重试后成功** → 瞬时抖动（单独计数，不算失败）
  - 直读与重试都失败 → 确实读到半截/读不到 ⇒ 真失败（FAIL）
- **重试必须有间隔**（如 3 次 × 100ms）：零延迟连续读两次可能落在同一个缓存/写入窗口里，抖动照样被判成失败。
- **为什么不会放过真 bug**：真正写了半截的文件在几百毫秒内不会自己变好（要等下一次写入覆盖），
  所以"重试后仍解析失败"就是真失败；而被替换前的旧 inode 内容始终是完整的。
- **失败必须带原因**：记录错误码（`ENOENT` / `EIO`）、JSON 解析位置、读到多少字节；
  泄漏类断言则打印命中片段（前后各几十字符）。只报"失败 N 次"等于让人从零重查。

**同理适用于**：文件是否存在的轮询、任务状态轮询、`.tmp` 残留检查（轮询到稳定再断言，超时才 FAIL）。

## 十四、改完服务端代码必须重启再验（Node 没有 HMR）

**现象**：改完 `server/` 下的代码，直接跑测试或 curl，看到的还是旧行为 —— 于是误判成「改了没生效 / 逻辑有 bug」，甚至推翻正确改动重写一遍。

**根因**：Node 进程启动时把模块读进内存，**没有热重载**。`bash scripts/start.sh restart` 之前，进程跑的一直是旧代码。

**实测代价（2026-10-27）**：修加密 RAR 的错误码传递，改完 `orchestrator.js` 与 `rar/index.js` 后直接 curl 验证，得到 `status=failed` 但 `error.code=null`，据此判断「错误码在传递链上丢了」，白查一轮。**重启服务后同一个请求立刻返回 `BAD_PASSWORD`** —— 代码一直是对的。

**纪律**：

1. **改 `server/` 任何文件 → 先 `bash scripts/start.sh restart` → 再验**，不要用重启前的进程下结论
2. 验收脚本里若依赖新代码，自己负责起停服务（或在脚本开头 `ensureService`），别假设"服务在跑就是新代码"
3. **判据**：报错/行为与改动预期不符时，**第一个怀疑对象是"进程还没加载新代码"**，而不是"我改错了"

> 与第九章（前端 build 后必须重启）是同一个根因的两个面：前端是静态资源清单不刷新，后端是模块缓存不刷新。

## 十五、CIFS 上 `fs.copyFile` 会 EPERM，必须用流式

**现象**：把文件从本地盘搬到 CIFS 目录，`fs.copyFile()` 报 `EPERM: operation not permitted`；加 `COPYFILE_EXCL` 也一样。

**实测对照（2026-10-27，同一个源与目标）**：

| 方式 | 结果 |
|---|---|
| `fs.copyFile` | ✗ EPERM |
| `fs.readFile` + `fs.writeFile` | ✓ 可以（但大文件吃内存） |
| **流式 `pipeline(createReadStream, createWriteStream)`** | ✓ 可以，且不吃内存 |

**纪律**：跨盘（本地盘 → CIFS）搬文件一律走**流式**，不要用 `copyFile`。

**连带**：`fs.rename` 跨盘也是 EXDEV，同样不能用；同卷内的 `rename` 没问题。

**为什么放这里而不是只写 skill**：这是本项目**部署环境**（storage 在 CIFS）的具体约束，改任何"产物落盘/中转搬移"的代码都会踩到。

## 十六、新增格式插件：外部引擎一律走 `server/core/engineRunner.js`

**规则**：任何格式插件要跑外部程序或 WASM 引擎（`7z` / `unrar` / `node xxx.mjs`），**必须调 `runEngineProcess()`**，禁止自己 `spawn`。

**为什么**：绑核、`nice` 降优先级、跨格式全局串行、超时/取消整组 SIGKILL、逐行进度回调——这五件事是**部署环境约束**（本机 3 核，跑满会触发宿主的"系统 CPU 过载"保护，实测已造成一次 503），不是某个格式的特性。写在插件里必然被下一个格式漏掉；各插件各有一把串行锁时，两个任务还能同时跑把 CPU 打满。

**判断标准**：新增一个格式插件的作者**不需要知道限核这件事**——执行入口已经帮他做了。

**降级原则**：探测不到绑核手段时只降级（只 `nice`）并写日志，**不许**静默顶满 CPU，也不许写"看起来在限其实没限"的代码（例如 macOS 上假装绑核）。

## 十七、发现文档与实现不一致：立即修，不要先问

**为什么单列一条**：发现「文档写着未实现、代码其实早就实现了」这类不一致时，很容易顺手记下来、攒着一起问「要不要改」。但这类问题是**纯纠错、方向无歧义**，问一次就多一轮往返，而文档继续以错的形态被别人读到（下一个接手的人会照着过时的结论做决策）。

**纪律**：

1. **当前状态类的过时表述，发现即改**，不必等确认（同 `bugfix-auto-authority`：bug 直接修，修完告知）
2. 改完在回复里**列出改了哪几处、原说法是什么**，让用户能复核
3. **版本记录表里的历史条目不算漂移** —— 「0.12.0 当时未接入」是史实，不要改成「已接入」；但应补一句「后续 X.Y.Z 补齐」，避免读者误以为现在还没做
4. 改完**全文再扫一遍同类词**（`未实现` / `未接入` / `待做` / `当前没有`），一次清干净，别一次只修用户指出的那一处

## 十八、多方案选型的实测数据必须留档（不留在聊天里）

**问题**：做过一轮「几个库/几个方案谁更好」的实测后，结论进了代码，但**数据只存在于当次对话**。等下次要新增一个类似选型时，没人记得当初测了什么、口径是什么、为什么选它 —— 于是重测一遍，或者凭印象拍脑袋。

**纪律**：

1. **凡是「≥2 个候选方案之间做过对比」的选型**，必须在 `docs/18` 留一节（仿 §附四 的形态），包含：
   - **口径**：测试数据怎么造的（大小、构成），机器条件
   - **对比表**：每个候选一行/一列，指标列出来（耗时、产物大小、内存峰值、维护活跃度、许可、能力边界）
   - **结论 + 选定理由**，以及**被否掉的理由**（否掉的候选也要留名，否则以后有人又提它）
   - **可复现线索**：用了哪个包哪个版本、样本怎么造
2. **数据要能复测**：写清依赖包版本；包被卸载时在文档里注明（否则后人以为随时能复跑）
3. **只记可量化的**，不写「感觉更快」「应该够用」这类
