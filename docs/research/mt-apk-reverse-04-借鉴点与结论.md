## 一、对 ZipCalm 的借鉴点（按价值排序）

### ★★★ 最值得学的三条

**1. 常用密码本（自动按序尝试 + 成功记忆 + 自动填入）**

MT 的做法（arsc 原文）：
```
"将常用密码添加到此处，解压加密的压缩文件时将自动按顺序尝试这些密码，
 若全部失败再手动输入；压缩文件时也可快速选择这些密码进行输入。
 当前暂无记录，最近一次压缩文件密码成功匹配记录将会显示在此处。"
配套 UI：常用密码管理 / 该密码已存在 / 最近匹配记录 / 发现重复密码 / 已自动输入压缩包密码
```

- 为什么值得学：**实现成本极低**（一个本地列表 + 解压失败时遍历重试），**体验收益极大**（批量解压加密包时不用反复输密码）
- ZipCalm 落点：解压任务失败且错误为"密码错误"时，自动用密码本重试 N 次；成功则在密码本里置顶该密码
- 注意：密码本涉及敏感信息，**必须本地存储 + 明确告知用户**（MT 的做法是"您输入的密码不会被记录"指单次密码，密码本是用户主动加的）

**2. 压缩包测试（test）作为独立功能**

MT 有完整的「测试压缩文件」流程（arsc 文案）：`正在测试压缩文件 / 测试完成，未发现错误 / 测试发现压缩文件错误：%1s / 该压缩文件正在测试 / 不支持测试此压缩文件 / 压缩文件在测试过程中发生变化，请重新测试`

- 为什么值得学：ZipCalm 做压缩服务，**"压完自检"是低成本高信任度的功能**——压完立刻 test 一遍，比让用户下载后自己发现损坏好得多
- ZipCalm 落点：压缩任务完成后自动 test（可配置开关），结果写入任务记录

**3. 双层进度 + 冲突计数**

MT 的进度模型：`总进度`（整体）+ `正在写出文件 %d个文件`（当前项）+ `已存在项 / 待写入项`（冲突阶段计数）

- 为什么值得学：**NAS 上压大文件时，用户最想知道的是"还有多少"**。单层百分比（0~100%）在几十 GB 场景下几乎没有信息量；"第 12/340 个文件 + 当前文件 45%"才有用
- ZipCalm 落点：任务进度至少三层——总文件数进度、当前文件名、当前文件字节进度；冲突（目标已存在）单列计数

### ★★ 值得学的其他点

**4. 压缩级别 6 档命名**（`[字符串]`）：`仅存储 / 极速压缩 / 快速压缩 / 标准压缩 / 最大压缩 / 极限压缩`
- 比单纯 1~9 数字友好得多。ZipCalm 若暴露 level，建议用这套中文档位 + 数字双显
- MT 的「极限压缩」有独立开关与说明："使用极限压缩算法对必要的数据重新压缩，以获得更小的体积，该处理步骤需要等待较长的时间" → **把"慢"明确告诉用户**，ZipCalm 的 level 说明也该这么做

**5. APK 专用模式**（`[字符串]`）："对安装包内不规范的文件以 APK 模式进行重新打包并执行 Zipalign 对齐优化"
- 思路：**特定内容类型有特定最优策略**。ZipCalm 可考虑对图片目录（已压缩，再压无益）自动降级为"仅存储"——MT 的「大小优先」说明正是这个逻辑："尽可能对所有文件以压缩方式进行打包以减小体积"

**6. 分卷下限硬约束**（`[字符串]`）：`分卷大小至少 64 KB`
- 工程上防呆。ZipCalm 若支持分卷，同样要设下限并明确提示

**7. 密码错误与文件损坏不区分**（`[字符串]`）：统一文案「密码错误或文件已损坏」
- 反直觉但正确：**用户不需要知道到底是哪种，只需要知道"换个密码或换个文件"**。ZipCalm 不必做精细的错误码区分（内部日志可分，用户可见文案合并）

**8. 取消需"再按一次"确认**（`[字符串]`）：`再按一次取消操作 / 正在取消操作`
- 长任务防误触。ZipCalm 的网页端取消按钮可加二次确认

**9. SMB 中断态细分**（`[代码]`）：`SMB write canceled / failed / interrupted / timed out / returned no progress`
- 五种中断态分别处理。ZipCalm 后端读 SMB（若用 smb 协议直读）时，**应区分"超时"与"无进度"**——后者往往是服务端挂起，该断连重试而不是傻等

**10. "压缩传输"开关**（`[字符串]`）：HTTP 传输可选压缩
- ZipCalm 的下载/上传链路可考虑 gzip 传输（文本类压缩包收益明显）

**11. 权限不足时引导"先复制到内部存储"**（`[字符串]`）
- 产品策略：**不在做不到的地方硬做，而是给用户一条明确出路**。ZipCalm 遇到目标目录不可写时，文案也该给"下一步做什么"，而不是只报 `EACCES`

### ✗ 不适用 / 不该学的

| MT 的做法 | 为什么 ZipCalm 不学 |
|---|---|
| 手机上做压缩主力 | NAS 场景数据量大，手机压会发烫/断网即毁。**ZipCalm 的核心价值就是"服务端压"** |
| SMB 上提示"先复制到内部存储" | 这会把几十 GB 数据过一遍手机。ZipCalm 要的正是绕开这一步 |
| VIP 门槛 | ZipCalm 是自建服务，不该有付费墙 |
| `libmtprotect.so` 加固 | ZipCalm 无对抗需求，加了只会让自己难维护 |
| 把 `bin.mt.plugin.api` 编进宿主 dex | 那是 MT 的插件体系设计，与 ZipCalm 无关 |

## 二、总结论

### 2.1 MT 压缩栈（可直接照思路设计）

```
多库组合，不重复造轮子：
  zip/7z/tar/gz/bz2/xz/lzma/lz4  → net.sf.sevenzipjbinding（JNI，含固实/多线程/头加密/级别）
  zstd                            → com.github.luben.zstd（zstd-jni，自带 .so）
  zip/gz 轻量路径                 → java.util.zip.ZipOutputStream/Deflater/GZIPOutputStream
  xz 加速                         → sevenzipjbinding 自带 NativeXZInputStream/OutputStream（native 失败降级纯 Java）
  rar                             → 只读
```

**给 ZipCalm 的直接启示**：Node 侧做压缩，同样该"按格式选现成实现"而不是自研——zstd 用 `structured-zstd`（参考项目里已有），7z 调 `7z` 二进制（本机已有），zip 用现成库。**MT 作为成熟产品也是这么干的。**

### 2.2 MT 插件路线（复核上一轮结论，未变）

| 项 | 结论 | 证据强度 |
|---|---|---|
| v3 插件 API 有文件菜单扩展点？ | **没有** | **宿主 dex 实证**（`[代码]`，比官方文档更强） |
| 插件能拿到选中文件列表？ | **没有公开 API** | **宿主 dex 实证** |
| SMB 路径形态 | `smb://` | `[代码]` |
| 插件能出现在 SMB 文件菜单？ | **大概率不能** | `[推断]`（无扩展点）→ **需真机实测确认** |
| 宿主有 SMB 写能力？ | **有**（完整 SMBJ 写栈） | `[代码]` |
| 插件能调到这个写栈？ | **无公开接口** | **宿主 dex 实证** |
| MT 自带 zstd-jni？ | **是**（1.5.7-7，三 ABI） | `[代码]` + so 文件实证 |

**→ 上一轮"v3 插件无文件菜单扩展点 → 走文本编辑器曲线或降级网页/PWA"的结论不变，且这次是从用户实际运行的 APK 里拿到的证据，比官方文档更硬。**

### 2.3 新增的、对设计有影响的事实

1. **SMB 是 MT 的 VIP 功能**（`[代码]` `SMB (VIP)`）→ ZipCalm 插件目标用户**必须有 MT VIP**。这是硬门槛，09 文档没写，应补。
2. **"MT 原生压缩 SMB 是灰的"这一前提 `[未验证]`**。证据更支持"可点但提示权限不足、引导复制到内部存储"（`[字符串]`）。建议 09 §11.2 改表述，真机确认。
3. **MT 原生有完整 SMB 读栈 + `smb://` 路径 + `SmbFileInputStream`** → 若哪天 MT 开放文件侧 API，ZipCalm 的"路径→后端"映射（`share` + `relativePaths`）可以直接解析 `smb://ip/share/x` 得到，**接口契约不用改**。

## 三、未验证项汇总（跨四份文档）

**必须真机实测（阻塞设计决策）**：
1. `TextEditor.getFilePath()` 打开 SMB 上的 txt 时返回什么（`smb://…` / null / 内部句柄）
2. 插件菜单项在 SMB 文件长按时是否出现（预期不出现）
3. MT 原生压缩菜单在 SMB 目录是"灰色"还是"可点但报权限不足"
4. `zstd-jni` 能否打进 MT 插件（dex 模式 + jniLibs 打包兼容性）
5. 插件进程能否直连局域网 NAS（预期能，需确认）

**本机缺工具导致未做**：
6. `libmt1/2/3.so` 的导出符号扫描（无 `nm`/`readelf`）——`[推断]` 与压缩无关，因压缩已确认走 Java 层
7. jadx 全量反编译（宿主类名混淆，收益低；如需读 sevenzipjbinding / zstd-jni 库源码可单独跑，它们类名未混淆）
8. `assets/0`~`assets/9`、`android_dex`、`compile_dex` 的内容（自定义资源包，未解出）
9. `libmtprotect.so` 的保护机制（与压缩无关，主动放弃）

**字符串/文案级别拿不到的**：
10. 宿主压缩/传输的实现类与方法体（类名全混淆 `l.XXXX`）——**本报告所有"逻辑"均为库符号 + UI 文案反推，无一处来自 MT 自己的实现代码**
11. 压缩策略除「大小优先」外另两个选项名
12. zip 加密 ZipCrypto 与 AES-256 的分流条件
13. 取消压缩后临时文件是否清理
14. 「极限压缩」的具体算法
15. 多线程压缩线程数是否可配
16. SMBJ 确切版本号

## 四、复现方法（供他人复核）

```bash
# 1. 解包（7z 即可，无需 apktool）
7z x 参考项目/MT管理器_2.26.10.apk -o/tmp/mtdec/out

# 2. manifest 需 apktool（⚠️ 中文路径会让 java -jar 失败，必须复制到 ASCII 路径）
cp 参考项目/MT管理器_2.26.10.apk /tmp/mtdec/mt.apk
java -jar apktool.jar d -f -s -o /tmp/mtdec/mt-apktool /tmp/mtdec/mt.apk

# 3. dex 字符串扫描
python3 -c "
import re
data=open('classes.dex','rb').read()
ss=[s.decode('utf-8','ignore') for s in re.findall(rb'[\x20-\x7e]{4,}',data)]
print([s for s in ss if 'zstd' in s.lower()])
"

# 4. arsc 中文文案（注意是 UTF-8，不是 UTF-16LE）
python3 -c "
data=open('resources.arsc','rb').read()
t=data.decode('utf-8','ignore')
import re
for m in re.finditer('压缩', t):
    print(re.sub(r'\s+',' ',t[m.start()-80:m.start()+120]))
"
```
