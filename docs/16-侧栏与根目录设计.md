**实测补充**：

- 侧栏每个位置带**容量进度条**（3px；`<80%` 正常 / `80~90%` 黄 / `>90%` 红）+ `role="progressbar"` + `aria-label`（如「Download 已用 86%」）
- C 模式排除 `@` / `#` / `.` 开头的系统目录
- **运行身份决定权限**：服务以**启动者**身份访问文件（手动启动 = 你的账号；套件代启 = 套件用户），所以 `PERMISSION_DENIED` 提示必须动态显示实际 uid/用户名 —— 详见 `docs/06` §七

**遗留**：首屏「可读根」竞态（刷新时可能先落在不可读的共享 → `PERMISSION_DENIED`）。修法已定：**侧栏先探测可读根并把结论写进 store，文件页等这个结论再加载**（带 3 秒超时兜底，不因探测卡住白屏）。

## 一、现状与问题

| 现象 | 原因 |
|---|---|
| 侧栏「根目录 /」是静态文字 | `Sidebar.vue` 里写死的 `<li>` |
| 侧栏「目录树（M1 接入）」是占位 | 从未实现 |
| 点 `/` 列出 0 项 | API 白名单基准是 `storage.root`（默认 `./storage/fs-root`），**不是文件系统 `/`** |
| 用户找不到 NAS 上的真实数据 | 真实数据在 `/volume1`，但没有任何入口能到那里 |

**结论：「根目录 /」这个设计是错的。** 本项目的"根"是**可配置的存储根**，不是文件系统 `/`；对 NAS 用户来说，"根"应该是**卷**。

## 二、设计：两套模式 + 自动探测

### 2.1 探测规则

| 条件 | 模式 |
|---|---|
| 存在 `/etc/synoinfo.conf`（群晖 DSM 特征文件） | **C 模式**（只列共享文件夹） |
| 其他（Linux / Windows / macOS） | **B 模式**（列卷，点选切根） |
| 将来其他特殊系统 | 各自单独模式，复用同一套「探测 → 选模式」机制 |

> 实测依据：本机 `/etc/synoinfo.conf`、`/etc.defaults/synoinfo.conf`、`/usr/syno/bin/synopkg` 均存在，`uname` 含 `synology_kvmx64_v`。

```js
function detectPlatform() {
  if (fs.existsSync('/etc/synoinfo.conf')) return 'synology';
  // 将来：其他厂商在这里加分支（同一套机制）
  if (process.platform === 'win32') return 'windows';
  return 'posix';
}

function pickSidebarMode(platform) {
  if (platform === 'synology') return 'C';   // 卷 + 目录树
  return 'B';                                // 列卷，点选切根
}
```

### 2.2 B 模式（默认，非群晖）

```
左侧栏 ── 存储卷
  ├─ volume1 (31G, 剩 4.3G)    ← 点击：切到 /volume1
  ├─ volume2 (8T, 剩 300G)
  └─ /mnt/data (2T, 剩 1.1T)
```

- 侧栏只列**卷**（挂载点）+ 磁盘用量
- 点击 = 切换「根」，主区重新列出该卷内容
- **不显示目录树**（保持简单）

### 2.3 C 模式（群晖：只列共享文件夹）

```
左侧栏 ── 位置
  ├─ photos      ← 点击：切到 /volume1/photos
  ├─ videos
  └─ backup
```

- **不列卷，直接列共享文件夹**（DSM 里"共享文件夹"就是 `/volume1/<name>`）
- **排除系统目录**：以 `@` / `#` 开头的（`@appdata`、`@eaDir`、`@docker`、`#recycle` 等）
- 点击 = 切到该共享文件夹为根，主区直接列出内容
- **为什么这样更好**：NAS 用户的心智里根本没有 "volume1 / volume2" 这层 —— 他要找的是"照片存在哪个共享"，卷对他只是容量来源

挂载/共享的发现方式：

```js
// 群晖：所有 /volumeN 下的非 @/# 目录，都视为共享文件夹
for (const vol of ['/volume1', '/volume2', ...]) {
  entries = readdir(vol).filter(name => !/^[@#]/.test(name) && isDirectory);
}
```

### 2.4 两模式差异

| | B（默认，非群晖） | C（群晖） |
|---|---|---|
| 侧栏标题 | 存储卷 | **位置** |
| 列什么 | **卷/挂载点**（`/volume1`、`/mnt/data`） | **共享文件夹**（`/volume1/photos`） |
| 切根方式 | 点卷 → 根 = 该卷 | 点共享 → 根 = 该共享 |
| 粒度 | 粗（先看卷，再往下点） | **细（直接到用户要找的那层）** |
| 适用 | 桌面 Linux / Win / macOS | NAS（卷少、共享多、心智是共享） |

## 三、需要的改动

### 后端

1. **多根支持**（当前只有单 `storage.root`）

   ```jsonc
   "storage": {
     "root": "./storage/fs-root",   // 保留：默认 / 回退根（单根模式用）
     "roots": [                     // 新增：可切换的根列表（空/缺省则单根模式）
       { "id": "volume1", "label": "volume1", "path": "/volume1" },
       { "id": "volume2", "label": "volume2", "path": "/volume2" }
     ]
   }
   ```

2. **`GET /api/v1/fs/volumes`** → `{ platform, mode, roots: [{ id, label, path, totalBytes, freeBytes }], canSwitch }`
   - 容量用 `fs.statfs`；拿不到时 `null`（**降级不报错**）
   - 非群晖额外扫描 `/mnt/*`、`/media/*` 挂载点

3. **`fs/list` 等端点接受 `rootId`** —— 路径校验基准随 `rootId` 切换（**INV-06 不能被绕过**：换根只是换基准，`..` / 绝对路径 / 符号链接照旧拒绝）

### 前端

4. `Sidebar.vue` 去掉两个硬编码 `<li>`，改为按模式渲染**同一个列表组件**（数据源不同，外观一致）：
   - B 模式：数据源 = 卷/挂载点
   - C 模式：数据源 = 共享文件夹（`/volumeN` 下非 `@`/`#` 目录）
   - 标题随模式变（"存储卷" / "位置"）
5. 新增 `ui.currentRootId`（pinia）；切换时**重置** `currentPath`、多选状态、目录树展开状态
6. **`/`（文件系统根）从 UI 消失** —— 它是 API 内部概念，不是用户入口

## 四、验收标准

- [ ] 群晖上：侧栏显示**共享文件夹**（排除 `@` / `#` 开头的系统目录）；点共享切根
- [ ] 非群晖（用 `ZIPCALM_FORCE_PLATFORM=posix` 强制模拟）：侧栏**只显示卷**；点卷切根
- [ ] 未知系统**回退 B 模式**（不能白屏、不能报错）
- [ ] 卷/共享列表的容量与剩余；`statfs` 失败时降级为不显示（**不报错**）
- [ ] 切根后：面包屑 / 多选状态**全部重置**（不留上一个根的残留路径）
- [ ] **路径校验仍以当前根为基准**（换根不能绕过 INV-06）

## 五、排期
