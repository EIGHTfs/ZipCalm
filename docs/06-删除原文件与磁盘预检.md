# 06 删除原文件与磁盘预检

> 定位：删除流程的安全约束、磁盘预检的空间策略、落盘位置与运行身份。
> 本文结论已与 `server/core/compress/{orchestrator,preflight,verify,deleter}.js`、`server/core/fs/systemTrash.js` 核对（2026-10-24）。

## 一、最危险的选项

「压缩后删除原文件」是**本项目唯一会丢数据的功能**。压缩失败 + 删除执行 = 数据永久丢失。

六条底线：

1. **默认保留原文件**，删除必须由用户主动勾选
2. **删除必须二次确认**，明确告知「将删除 X 个文件、共 Y GB，且压缩包校验通过后才执行」
3. 技术上必须**先压 → 校验 → 再删**，不能边压边删
4. **校验方式**：zip 用 CRC、tar 系列比对条目与大小；至少要能重新列出包内文件与原文件对比
5. **删除进回收站，不是真删**（见 §七）
6. **失败时绝不删原文件** —— 哪怕只失败一个文件，那一个也不删

### 精确对应：跳过的不删

一个目录 100 个文件，用户选了「删除原文件」，但包里只有 98 个（2 个被黑名单跳过）——**只能删那 98 个**。

这条是 INV-02 的核心：

```
delete.targets ⊆ 进包条目 − skipped
```

删除前必须复核集合差异，非空 → 拒绝删除。详见 [docs/audit/M5-审查与修复.md](audit/M5-审查与修复.md) 的 P-01 / F-03。

## 二、删除流程（五步）

```
压缩完成 → 校验压缩包（CRC / 解压测试）→ 通过 → 标记"可删除"
        → 等待确认（或任务配置里已确认）→ 删除原文件（进回收站）
        → 记录删除日志
```

**任何一步失败，原文件都不删。**

### 执行模式（`delete.mode`）

| 模式 | 行为 | 用途 |
|---|---|---|
| `log-only`（**默认**） | 只写删除日志、**不真删** | 开发期核对「校验通过 → 触发删除」的时机；日志里能直接看到"本应删除哪些文件" |
| `trash` | 真删并进回收站（可恢复） | 正式使用 |

**模式只决定「到删除阶段要不要真删」，不改变上面的顺序** —— 无论哪种模式，都必须先通过校验才允许进入删除阶段（INV-01）。

## 三、磁盘空间预检

「剩余空间 ≥ 待压量 × 2」在**打包模式**下是硬要求（原文件 + 临时产物同时存在）；**单独压缩模式**可以更精细。

### 单独压缩模式

- 不需要一次性预留「所有项总量 × 2」
- 逐项检查：**剩余空间 ≥ 该项大小 × 2**
- 压完一个删一个，空间滚动释放
- 比整体预留更省空间，尤其是一堆小文件夹的场景

### 打包模式

- 临时产物通常写在目标目录（与源同目录或指定目录）
- **目标目录与源目录在不同分区时，空间要分别看**
- zstd 的中间状态可能比最终产物大，预留两倍是合理的

**预检要点：不只看"剩余空间"，还要看目标目录所在分区的剩余空间** —— 压缩包最终写在那里。

### 为什么必须预检

压 100 GB，产物可能 30 GB，但过程中原文件 + 临时产物同时存在，**峰值可能 130 GB**。不预检 → 写到一半磁盘满 → 原文件也删不了。

## 四、验收要点（M5 / M6）

**M5（删除原文件）：**

- 默认不删除原文件
- 勾选后二次确认弹窗明确列出「将删除 N 个文件、共 X GB」
- 压缩失败时原文件绝不删除
- 校验失败（压缩包损坏）时原文件绝不删除
- 删除进回收站，不是真删
- 删除操作有日志，可追溯
- **跳过项不参与删除**（INV-02）

**M5 关键测试：**

- 压缩一个 10 GB 文件，中途 `kill` 进程 → 原文件必须还在
- 压缩完成后手动损坏压缩包 → 校验失败 → 原文件必须还在
- 正常压缩 + 删除 → 回收站里能找到原文件

**M6（磁盘预检）：**

- 磁盘剩余 < 待压量 × 2 时，任务拒绝启动并给出明确提示
- 关键测试：把磁盘塞到只剩 1 GB，尝试压 500 MB 目录 → 应拒绝

## 六、硬链接与压缩格式（实测补录）

**结论：ZIP 不支持硬链接，同一份数据会被存两份；TAR 支持，只存一份。**

### 实测数据（走项目自己的 API）

造两个互为硬链接的文件（`a.bin` / `b.bin`，同一 inode，各 2MB，**物理占用 2,000,020 字节**）：

| 操作 | 产物大小 | 说明 |
|---|---|---|
| 压 **zip**（archiver） | **4,001,476** | 数据存两份，**体积翻倍** |
| 压 **tar**（node-tar） | 2,002,432 | 单份；tar 内表现为 `hrw-r--r--` + `link to ...` |
| 系统 `zip` / `tar` 命令 | 4,001,076 / 2,007,040 | 与上面一致 → 是**格式本身**的差异，不是库的 bug |

### 对设计的影响

1. **空间预检是安全的，不用改**：`preflight` 用 `lstat().size` 逐条累加，硬链接各算一份 —— 对 zip 恰好**准确**（它真存两份），对 tar **偏保守**（多算但不会漏拦）。保守方向正确，**不会打爆磁盘**。
2. **用户看不见这个差异**：选 zip 压一个硬链接很多的目录，用户以为占 2GB，实际产出 4GB。理想做法是预检同时给出「逻辑大小」与「按格式估算的实际产出」，差异超阈值时提示「检测到 N 个硬链接，ZIP 会存多份，建议用 TAR」。**当前未实现**，已登记于 [17-设计与实现差异记录](17-设计与实现差异记录.md) D-1。
3. **删除原文件 + 硬链接 = 信息损失**（不丢数据，但不可逆）：zip 压完删原文件，链接关系永久丢失（解压出来是两份独立文件）；tar 能保留，**但解压目标文件系统不支持硬链接时（FAT32 / exFAT / 部分 Windows 盘）依然会变两份** → 二次确认弹窗应提示这一句。

> 硬链接去重功能本身见 [15-硬链接去重.md](15-硬链接去重.md)。

## 七、落盘位置：进群晖系统回收站

### 为什么改

最初删除只是把文件移进**项目自己的** `storage/trash/<batchId>/`：

- 占 NAS 空间，要手动清
- 用户在 File Station 里**看不到**（项目 trash 与群晖回收站是两套）

### 按 `delete.trashBackend` 选路

| 后端 | 行为 | 适用 |
|---|---|---|
| `auto`（默认） | 探测到群晖 `synorecycle` → 系统回收站；否则项目 trash | 通用 |
| `system` | 强制系统回收站；不可用/失败 → **回退项目 trash**（不报错） | 群晖 |
| `project` | 强制项目 `storage/trash` | 非群晖 / 测试 |
| `none` | **拒绝删除**并记 `failed(TRASH_DISABLED)`（**绝不退化成真删**） | 保守场景 |

每条删除记录都带 `backend: 'system-recycle' | 'project-trash'`，出问题能追是哪条路。

### 群晖回收站怎么调

```bash
/usr/syno/bin/synorecycle --unlink share=<共享名> rpath=<共享内相对路径>   # 删文件
/usr/syno/bin/synorecycle --rmdir  share=<共享名> rpath=<共享内相对路径>   # 删目录
```

**共享名解析**（`systemTrash.js` 的 `toSharePath`）：

```
/volume1/VirtualDSM/photos/a.jpg  →  share=VirtualDSM  rpath=/photos/a.jpg
/volume10/data/f                  →  share=data        rpath=/f       （两位数卷号）
/volume1/@appdata/x               →  null             （@ 开头不是共享）
/volume1                          →  null             （卷根，不删）
```

### 三条安全约束（实现红线）

1. **模块内零 `rm`/`unlink`** —— 失败一律交回调用方回退，模块自己绝不删
2. **`stat` 因权限失败时按「存在」处理** —— 宁可判失败，也不把「没删掉」报成「删掉了」
3. **删后校验**：原位消失 + （`#recycle` 可读时）确认文件真出现在 `#recycle/<rpath>`；落点有延迟 → **轮询 10×200ms** 而非查一次

### 权限前提

`#recycle` 默认 `root:root d---------`（普通用户读不了）。`synorecycle` 以套件特权执行能写入，但**校验只能靠「原位是否消失」**；管理员放开读权限后，校验会自动升级为「确认文件在回收站里」。

### 测试不许污染它

跑测试时设 `ZIPCALM_TRASH_BACKEND=project`（`test-all.sh` 已内置 export）—— 否则测试删除会进用户的 File Station 回收站（实测堆了 11 条嵌套路径：顶层看起来干净，实际全在 `#recycle/<共享>/<项目路径>/...` 里）。

### 运行身份决定权限

服务以**启动它的用户**身份访问文件：

- 手动 `bash scripts/start.sh start` → 该 SSH 用户
- 由 DSH 等套件代启 → 套件用户

两者权限不同，所以：

- `PERMISSION_DENIED` 提示必须**动态显示实际运行身份**（`process.getuid()` + `os.userInfo()`），不能写死某个用户名
- 排查权限问题时，先确认「谁启动的」，再看该账号在 DSM 里有没有该共享的权限
