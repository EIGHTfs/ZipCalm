# 07 性能监控看板

> 定位：监控分层、采集频率、零依赖采集方案与开销自证。
> 本文结论已与 `server/core/metrics/` 实现核对（2026-10-24）。

## 一、监控分两层

### 系统层（CPU、内存、磁盘 IO）

候选库：`systeminformation`（信息全但调用开销不小）、`pidusage`（只看进程级、轻量）。

**实际实现：都不用，零新依赖** —— 直接读 `/proc`（`server/core/metrics/procfs.js`）+ Node 内置 `os` 模块。理由是 NAS 场景下 `/proc` 稳定可用，而引入第三方采集库会带来「库本身的开销比被监控对象还大」的风险。

### Node 进程层（事件循环、GC、堆）

- `perf_hooks` 的 `eventLoopUtilization`：几乎零开销
- `process.memoryUsage()`：堆大小、RSS
- 这两项必上

## 二、监控本身的开销

采得太密（每秒一次全系统扫描）本身就是性能问题。

**实际频率**：

| 项 | 频率 |
|---|---|
| 系统指标 | **5 秒** |
| 进程指标 | **1 秒** |
| 环形缓冲 | 保留最近 **5 分钟** |
| 前端轮询 | **2 秒**（`METRICS_POLL_MS`） |
| 「最近完成」卡片 | 每 3 个 tick 拉一次（≈6 秒） |

**实测开销**：双口径（自采集耗时 + 进程 CPU 占用）实测 **< 0.1% CPU**。

## 三、事件循环延迟怎么量

**不用 `perf_hooks.monitorEventLoopDelay`**：实测内置直方图在空载下也不够准。

**实现：定时器漂移法** —— 记录每次定时器的「计划触发时刻」与「实际触发时刻」，差值即延迟；取最近 5 次采样的最大值作为判据。

**语义分档**（不能只给毫秒数）：

| 延迟 | 档位 | 含义 |
|---|---|---|
| < 10 ms | 正常 | 事件循环响应及时，服务不卡 |
| 10~50 ms | 有压力 | 主线程开始排队，长任务可能拖慢请求 |
| > 50 ms | 卡顿 | 主线程被占用，接口会明显变慢 |

## 四、数据流

- 后端定时采集 + 内存环形缓冲（最近 5 分钟）
- 前端轮询 `/api/metrics` 拿最新一段
- **不用 WebSocket 推** —— 除非要做秒级实时图，否则轮询简单可靠

## 五、看板布局：六个卡片

参考同类监控面板（响应式卡片网格 + 紧凑列表双模式），本项目固定 **6 个卡片**（2×3 或 3×2）：

| 卡片 | 内容 |
|---|---|
| **CPU** | 系统总占用 + 本进程占用（双线图） |
| **内存** | RSS + Heap |
| **事件循环延迟** | 最重要，反映「服务卡不卡」，带语义分档 |
| **磁盘 IO** | 读/写速率 |
| **活跃任务** | 数字 + 队列长度 |
| **最近完成** | 最近 N 个终态任务的节省比例 |

**不堆指标**：温度、风扇、网络都不做 —— 用户看不懂也不看。

**图表库：uPlot** —— 极轻（约 40KB）、零依赖、专为时间序列，与 CPU/内存/事件循环趋势图对口。不用 Chart.js / ECharts。

## 六、验收要点（M7）

- 6 个卡片实时更新（2 秒刷新）
- 事件循环延迟能反映「服务卡不卡」（有语义分档，不只数字）
- 压缩任务执行时，看板能看出 CPU / 磁盘变化
- **监控本身开销 < 1% CPU**（实测 < 0.1%）
- 离开页面即停轮询、切后台暂停

**关键测试**：启动一个大压缩任务，看板显示 CPU 飙升、磁盘 IO 飙升。

## 七、代码落点

**后端**：

```
server/core/metrics/
├── collector.js    定时采集（系统 5s / 进程 1s）、环形缓冲、事件循环延迟
└── procfs.js       /proc 解析（CPU、内存、磁盘 IO）
```

**前端**：

```
web/src/pages/MetricsPage.vue          六卡片页面（含语义分档与布局）
web/src/components/metrics/TrendChart.vue   通用趋势图（uPlot 封装）
web/src/stores/metrics.js              轮询与节流（快照每次拉，历史/最近完成按节流拉）
```
