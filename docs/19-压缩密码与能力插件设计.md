# 19 压缩密码与「能力插件」架构

> 定位：把「压缩密码」实现成**可插拔的能力**（而非塞进格式插件或编排层），并确立「能力插件」这一新扩展点。
> 本文是设计提案，实现前需评审。

---

## 一、设计目标与边界

### 目标

1. **密码是能力，不是格式**：ZIP 支持、TAR 系列不支持 —— 差异用「格式声明能力」表达，而不是在各格式里写 `if (zip) {...}`
2. **加密算法本身可追加**：AES-256 / ZipCrypto 只是首批实现，将来加新算法只加一个模块，前端下拉自动出现
3. **编排层不认识「密码」**：`orchestrator` 只做通用装配，加密码不新增任何 `if (password)` 分支
4. **前端不硬编码**：哪些格式能加密、有哪些算法可选，全部由 API 下发

### 不做什么

- 不做 RAR 加密（RAR 压缩本身需用户自装 `rar`，见 `docs/18` §附三）
- 不做「忘记密码找回」（密码学上不可能）→ 只做事前警告 + 常用密码本辅助
- 不改动不变量（INV-01~10 全部继续生效）

## 二、为什么不用「格式插件内嵌」

反例（**不采用**）：

```js
// zip/index.js 里直接判断 —— 不采用
if (ctx.options.password) {
  archive = archiver.create('zip-encrypted', { password: ctx.options.password });
} else {
  archive = archiver.create('zip', { zlib: { level } });
}
```

看起来只要两行，但带来三个问题：

| 问题 | 后果 |
|---|---|
| 每个支持加密的格式都要各写一遍 | 将来 7z 也支持加密 → 再抄一遍，逻辑漂移 |
| 算法列表硬编码在格式插件里 | 加新算法要改每个格式插件 |
| 自测、脱敏、删除护栏没有归属 | 散落在 orchestrator / deleter / routes 各处 |

**能力插件把这些收敛到一处**，格式插件只负责「声明我支持什么」+「把参数喂给引擎」。

## 四、三层契约

### 4.1 格式插件：声明能力

在现有契约（`docs/03`）基础上**新增一个可选字段**：

```js
export default {
  id: 'zip',
  name: 'ZIP',
  ext: '.zip',
  // ... 现有 14 个字段/方法不变 ...

  capabilities: ['password'],   // ★ 新增：本格式支持哪些能力（缺省 = []）
};
```

`tar` / `targz` / `tarzst` 写 `capabilities: []` 或省略 —— 前端据此把密码开关置灰。

### 4.2 能力插件契约

```js
export default {
  id: 'password',
  name: '加密密码',

  // 本能力可作用于哪些格式（与格式插件的 capabilities 取交集才生效）
  // 双向声明：任一方不声明就不生效，避免「格式说支持但能力没实现」或反之
  appliesTo: ['zip'],

  // 参数字段（不含算法枚举 —— 算法由 methods/ 动态提供）
  params: {
    password: { type: 'string', required: true, minLength: 1, secret: true, maxLength: 1024 },
    method:   { type: 'methodRef', required: false, default: 'aes256' },
  },

  /** 参数校验与规范化 → { ok, value, error } */
  validateParams(raw, { formatId }) { /* ... */ },

  /** 压缩前：把能力参数翻译成格式插件认识的东西（本能力不做 IO） */
  prepareCreate({ params, formatId }) {
    return {
      archiverFormat: 'zip-encrypted',
      extra: { encryptionMethod: params.method, password: params.password },
    };
  },

  /** 压缩后自测：用同一密码试解一次。这是删除原文件的前置条件 */
  async verify({ archivePath, params, formatApi }) { /* → { ok, error } */ },

  /** 解压时：给出候选密码序列（用户输入优先，其次常用密码本） */
  prepareExtract({ userPassword, archivePath }) { /* → { candidates: [...] } */ },

  /** 脱敏：日志 / API 响应一律过这里 */
  redact(params) { return { hasPassword: true, method: params.method }; },
};
```

**关键约束：能力插件不碰文件系统、不碰 archiver**，只做「校验 + 参数翻译 + 编排自测」。真正落盘仍由格式插件完成 —— 这样能力可替换、可复用。

### 4.3 算法模块契约（可追加的关键）

```js
// server/plugins/capabilities/password/methods/aes256.js
export default {
  id: 'aes256',
  name: 'AES-256',
  description: 'WinZip 2003 标准，安全性最高',

  // 兼容性事实（前端据此生成提示文案，不是硬编码文案）
  compatibility: {
    sevenZip: true,
    winZip: true,
    macArchiveUtility: true,
    winExplorer: false,      // 能看列表不能解压
    linuxUnzip: false,       // Info-ZIP unzip 6.00 不支持
  },
  caveat: 'Linux unzip 6.00 与 Windows 资源管理器无法解开；7-Zip / WinZip / macOS 可解',

  // 该算法是否真的可用（将来若某算法依赖外部工具，在这里探测）
  available() { return true; },

  // 引擎适配：告诉能力插件该算法需要什么
  engine: { archiverFormat: 'zip-encrypted', encryptionMethod: 'aes256' },
};
```

**追加一个新算法** = 在 `methods/` 下加一个文件，前端下拉自动出现，格式插件与编排层零改动。

### 图 2：一次带密码压缩的完整时序

```
用户：选 3 个文件 → 点「压缩」→ 格式选 ZIP → 打开「启用密码」→ 输密码 → 算法选 AES-256
  │
  ├─ 前端读 formats：zip.capabilities 含 'password' → 密码开关可点
  │   （若选 TAR：capabilities=[] → 开关置灰 + 「TAR 格式不支持加密」）
  │
  ├─ 前端读 capabilities/password：methods=[aes256, zip20] + 各自 caveat
  │   （AES-256 旁显示「Linux unzip / Windows 资源管理器解不开」）
  │
  ↓ POST /compress/tasks
  │
  ├─① validateParams：非空 / 长度 / 算法必须在可用列表内
  │      ✗ → 400 VALIDATION_FAILED（不建任务）
  │
  ├─② 任务落盘：{ hasPassword:true, method:'aes256' }  ← 明文不落盘
  │      明文只活在内存（进程重启 → 任务重试需重输密码）
  │
  ├─③ capRegistry 取交集：zip.capabilities ∩ ['password'] = ['password'] ✓
  │      （若 format=targz 且用户强行带 password → 后端 400，不只靠前端置灰）
  │
  ├─④ prepareCreate → { archiverFormat:'zip-encrypted',
  │                     extra:{ encryptionMethod:'aes256', password:'***' } }
  │
  ├─⑤ zip 插件 create() → archiver.create('zip-encrypted', { zlib, encryptionMethod, password })
  │      → 写出 out.zip（AES-256）
  │      → entryPaths 照常返回（INV-02 的删除集合依据）
  │
  ├─⑥ verify()：用同一密码试解一次
  │      ✓ 通过 → 继续
  │      ✗ 失败 → 任务 failed(VERIFY_FAILED)，**原文件一个不删**（INV-01）
  │
  └─⑦ 删除阶段（仅当用户勾了「删除原文件」）
         PL-1：hasPassword=true 且 verify 未通过 → 拒绝删除
         PL-2：二次确认弹窗额外一句「密码丢失后压缩包无法恢复」
         PL-3：删除日志记录 hasPassword=true（不记密码）
```

### 图 4：常用密码本（独立文件，服务端自动维护）

```
用户输密码 / 或用过某密码成功解密
        │
        ↓
  storage/passwords.json          ← git 忽略，不入库；文件不存在 = 空列表，不报错
  {
    "version": 1,
    "entries": [
      { "password": "***", "label": "工作备份", "createdAt": "...", "lastUsedAt": "..." }
    ]
  }
        │
        ├─ 服务端自动维护：首次写入时自动创建（mkdir -p storage）
        ├─ 文件权限 0600（仅服务账号可读）
        └─ 解压加密包时：用户输入优先 → 全部失败 → 按 lastUsedAt 倒序自动尝试
```

**明文存储说明**（已知并接受的风险）：该文件是明文 JSON。若需更强保护，后续可加「主密码派生密钥加密」，但会让「自动尝试」变复杂（需要用户先解锁）。当前按「独立文件 + 不入库 + 0600 权限」处理。

## 六、数据模型变更

### 任务对象（tasks.json）

```diff
  options: {
    level: 6,
    keepOriginal: false,
+   hasPassword: true,          // 布尔，不含明文
+   passwordMethod: 'aes256',   // 算法标识
  },
```

**明文字段 `options.password` 只在内存中存活于任务创建到压缩完成之间**，`store.js` 落盘时显式剔除（有测试断言：grep 全 storage 找不到明文）。

### 常用密码本（storage/passwords.json）

独立文件，见 图 4。不进 `tasks.json`、不进 git。

## 七、安全设计（四条硬约束）

| 编号 | 约束 | 落点 |
|---|---|---|
| **PW-1** | 密码不经日志、不进 API 响应、不落 `tasks.json` | `redact()` + `store.js` 剔除 + 日志脱敏测试 |
| **PW-2** | 加密包必须**压完自测**（同密码试解），失败即 `failed` 且不删原文件 | `cap.verify()` → 任务失败 → INV-01 拦住删除 |
| **PW-3** | 删除原文件前额外确认「密码已试解通过」+ UI 已提示「密码丢失不可恢复」 | `deleter.js` 前置检查 + 二次确认文案 |
| **PW-4** | 前端置灰只是体验，后端必须独立校验「该格式是否声明此能力」 | `orchestrator` 取交集时 400，不信前端 |

## 八、分阶段实现

| 阶段 | 内容 | 验收关键 |
|---|---|---|
| **P1** | `capRegistry` + `formats/capabilities` 声明 + `capabilities/password` + `methods/{aes256,zip20}` + zip 装配点 + `verify()` | 加密包能用密码解开、错密码打不开、自测失败不删原文件 |
| **P2** | 前端：格式能力驱动开关 + 算法下拉（含 caveat）+ 忘记密码警告 | 浏览器实测：选 TAR 置灰、选 ZIP 可点、算法提示正确 |
| **P3** | 常用密码本（增删查 + 自动尝试 + 记住最近成功） | 密码本文件自动创建、不存在不报错、自动尝试命中 |
| **P4** | 解压侧支持加密包（ZipCrypto 走 `unzipper` 的 Decrypt；AES-256 需实测确认） | 能解开 P1 自己产出的 AES 包（若不支持则明确提示） |

## 九、验收要点

- [ ] `zip` 加密压缩 → 用密码解压成功；错密码失败且提示「密码错误」而非「文件损坏」
- [ ] 选 `TAR`：密码开关置灰，后端也拒绝带 password 的 TAR 任务
- [ ] 算法下拉显示 `aes256` / `zip20` 及各自兼容性提示
- [ ] 新增一个算法文件 → 前端自动出现，其余零改动（插件化验收）
- [ ] 明文密码在 `storage/` 全目录 grep 不到（含 `tasks.json` / 日志）
- [ ] `storage/passwords.json` 不存在时功能正常（空列表，不报错）；首次添加时自动创建
- [ ] 加密压缩 + 删除原文件 → 删除前已验证密码可解
- [ ] 自测失败（模拟坏包）→ 任务 failed 且原文件仍在
- [ ] 浏览器实际点击全流程（含窄视口 390x844）
