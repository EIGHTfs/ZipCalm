# 00 需求演进与设计决策

> 本文记录项目从最初构想到当前形态的**需求演进轨迹与决策依据**：每一阶段提出什么诉求、为什么采纳某个方案、最终落在哪篇文档。
>
> 主题化设计见同目录 `01` ~ `16`；契约条款见 `docs/M0/`。

---

## 一、项目缘起：压缩是手段，省空间才是目的

**诉求**：在 NAS 上跑一个 Node.js 网页服务端，能浏览目录、选择文件或文件夹压缩，支持多种算法与格式（zip / tar / tar.gz / tar.zst），并带性能监控看板；尽量用开源库组装而非从零造轮子。

**关键判断**：核心目的不是"有个压缩工具"，而是**节约 NAS 空间**。这一条决定了后续所有取舍 —— 包括为什么必须做磁盘预检、为什么"跳过已压缩格式"要可配置、为什么硬链接去重值得单独做一个功能。

**落点**：`docs/01-需求与总体架构.md`、`docs/02-压缩格式与库选型.md`

## 二、任务模型：后台执行，进度连续

**诉求**：

- 压缩任务进任务列表，**不阻塞网页**
- 进度要**连续**（像桌面压缩软件那样），而不是按固定时间间隔采样
- 多选时可选「每个文件/文件夹各自一个包」或「合并成一个包」
- 可选压缩后是否保留原文件
- 单人使用场景，默认**串行排队**；并行只留配置占位，暂不启用
- 网页只负责"看"和"发任务"，任务执行**不受前端网络波动影响**

**决策**：

- 任务状态落盘（`tasks.json` + `task-history.jsonl`），进程重启后能对账
- 进度用 SSE 推送，且**推送真实字节进度**而非定时估算
- 串行执行通过 `activeId` 单槽位控制，避免多人并发把磁盘打满

**落点**：`docs/05-任务系统与进度推送.md`、`docs/11-开发里程碑与验收标准.md`

## 三、格式插件化：加目录即注册

**诉求**：每种格式/算法按**插件**设计，便于单独增删改某一种；总入口统一管理。

**决策**：

- 一个格式 = 一个插件文件，声明 `id / ext / mime / 是否支持 / 实现`
- 启动自检：能力**真探测**（zstd 走「Node 内置 → 系统命令」回退链），不可用则该格式置灰并说明原因
- 不引入"格式注册中心"这类中间层，避免为扩展性付出的抽象成本超过收益

**落点**：`docs/03-插件化架构与格式契约.md`

## 四、行为对齐成熟工具：跳过与删除

**诉求**：功能行为对齐成熟压缩工具（桌面端 Bandizip、移动端 MT 管理器那类）—— 它们都提供「每文件夹一个包 / 整体一个包」两种模式，并且支持压缩完删除源文件；跳过某些文件的需求通过**压缩黑名单**管理。

**决策**：

- 两种打包模式落地为 `mode: single | bundle`
- 「压缩后删除」不是简单删：必须**校验通过才删**、删除集合必须是「已打包项 − 已跳过项」、且进回收站可恢复
- 黑名单分三层（全局默认 / 用户自定义 / 任务级临时），命中项**既不进包也不参与删除**
- 全局默认只保留系统垃圾（`Thumbs.db` / `.DS_Store` / `@eaDir`）—— 因为**打包不一定是为了省体积**（把一批照片打成一个包发给别人也是合理用法），默认替用户决定"这个不值得压"会违背意图

**落点**：`docs/04-压缩模式与黑名单.md`、`docs/06-删除原文件与磁盘预检.md`

## 五、安全底线：预检与不变量

**诉求**：磁盘空间预检必须重视，要求**剩余空间 ≥ 待压缩量的两倍**。

**决策**：把安全要求固化成可测的不变量（`docs/M0/不变量清单.md`），而不是散落在代码里的 if：

- 校验通过才删；删除集合 ⊆ 已打包 − 已跳过；删除前复核文件状态（`size / mtimeMs / ino`）
- 路径白名单：`..` / 绝对路径 / 盘符 / NUL / 符号链接一律拒绝
- 绝不覆盖同名产物；半成品用 `.part` 后缀

**为什么值得写这么细**：删除是不可逆操作，而"看起来对"的实现（先删后建、抽样判断重复）在真实数据上会造成数据丢失。**不变量是给未来的自己留的护栏。**

## 六、前端：按网盘做，侧重压缩

**诉求**：

- 前端按开源网盘那种形态设计，只是额外侧重压缩
- **要支持触屏**，文件浏览要方便
- 设计时**提供接口**，方便后续开发手机 APK 连服务端管理
- 最终确定**两套 UI**：APK 等网页端完全开发完再开始；网页端先按鼠标角度开发，触屏只做最低兼容（不做独立交互逻辑）

**决策**：

- 布局采用「侧边栏 + 主区 + 底部状态栏」经典三件套
- 触屏不另写一套逻辑，只保证**可点区 ≥40px、行高 ≥44px、无「悬停才显示」的操作**
- API 与 UI 解耦，认证支持 cookie 与 bearer 双通道，为 APK 铺路
- 曾评估「做 MT 管理器插件」路线，调研后发现其 v3 插件接口没有文件菜单扩展点，**放弃该路线，APK 回到 PWA 方案**（详见 `docs/research/mt-plugin-feasibility.md`）

**落点**：`docs/08-前端布局设计.md`、`docs/09-API契约与APK铺路.md`

## 七、工程方法：契约先行 + 里程碑验收

**诉求**：这是中大型项目，需要**分步计划大纲**和**里程碑验收标准**；前端与目录结构要用文字表达清楚。

**决策**：

- **M0 先冻结契约**（API 规范 / 插件契约 / 数据模型 / 不变量清单），之后实现方不用猜、验收方有据可依
- M1~M9 分里程碑推进，每个里程碑有逐条可测的验收标准
- 每个任务收尾固定四步：审计 + 顺手优化 / 全套验收 / 停服务 / 带证据汇报
- 验收**不采信"我跑绿了"**：套件由验收方独立复跑，关键路径亲手复现

**落点**：`docs/11-开发里程碑与验收标准.md`、`docs/12-项目目录结构.md`、`docs/14-工程执行约定.md`

## 八、后期演进（实现阶段新增）

以下需求在实现过程中陆续加入，均已落地：

| 功能 | 为什么加 | 落点 |
|---|---|---|
| **硬链接去重** | NAS 上重复大文件（同系列视频、多份备份）占空间，硬链接能在不改内容的前提下省一倍 | `docs/15-硬链接去重.md` |
| **多存储位置** | 单一「根」不够用：群晖有多个共享、桌面有多个挂载点；且原先的「根目录 /」是硬编码占位，用户看不到真实数据 | `docs/16-侧栏与根目录设计.md` |
| **文件名搜索** | 文件多了以后靠逐层点开找太慢 | `docs/09-API契约与APK铺路.md`（搜索端点） |
| **删除进系统回收站** | 原先删到项目自己的 `storage/trash`，占空间且用户在 DSM 里看不到、恢复不了 | `docs/06-删除原文件与磁盘预检.md` §七 |

## 九、贯穿全程的三条原则

1. **安全优先于便利**：删除、硬链接合并这类不可逆操作，宁可多一次确认、多一条日志，也不省步骤。
2. **契约优先于默契**：同一事实只写一处（不变量清单 / API 规范），实现与验收都对照它，避免"代码说 A、文档说 B"。
3. **可复现优先于"看起来合理"**：主文件选择用字典序而非 mtime、测试夹具自建自清、反例自证要按**原始错法**破坏 —— 都是为了同一批数据跑两次能得出同样结论。
