# 02 压缩格式与库选型

> 定位：四种格式的库选型、库与二进制的取舍、zstd 的实现方案。
> 本文结论已与实现核对（2026-10-24）：实际落地格式为 **zip / tar / tar.gz / tar.zst** 四种。

## 一、库选型总表

| 格式 | 方案 | 说明 |
|---|---|---|
| zip（写） | `archiver` | 成熟、流式、API 顺手；大文件内存占用低 |
| zip（读：list / test / extract） | `unzipper` | 纯 JS、流式；**archiver 只能写不能读**，读侧必须另配 |
| tar | `node-tar` | 官方库，比 tar-stream 封装好，支持 gzip 集成 |
| tar.gz | `node-tar` + 内置 `zlib` | `tar.create({ gzip: true })` |
| tar.zst | `node-tar` + **Node 内置 zstd** | node-tar 不原生支持 zstd，用 `node:zlib` 的 zstd 流拼管道（零依赖） |
| zstd 单文件 | `zlib.createZstdCompress` | 见 §二 |

**未实现的格式**：7z / rar 需要 `node-7z` 调外部二进制（依赖系统安装 7z/unrar，跨平台麻烦），**当前未实现**。如需扩展，按 `docs/03` 的插件契约加一个格式包即可，无需改动总入口。

## 二、zstd：走 Node 内置，零依赖

**环境实测**（Node v22.22.3，满足 ≥ 22.15）：

- `node:zlib` 内置 zstd：`zstdCompressSync` / `zstdDecompressSync` / `createZstdCompress`（流式，可拼 `node-tar` 管道）
- 往返一致（4400 字节重复文本 → 40 字节），无实验警告输出
- **系统 `zstd` 命令在本机不存在**（PATH 实测无）→ 「外部二进制」方案的部署前提不成立

**实现：能力自探测 + 三级回退链**（不假设环境）

1. **首选 `node:zlib` 的 zstd** —— 零依赖、零编译、流式、跨平台；要求 **Node ≥ 22.15.0**
2. **回退**：探测系统 `zstd` 命令（`ZC_ZSTD_BIN` 可覆盖路径，否则 PATH 探测）
3. **都不可用 → 该格式 `available() = false`** 并给出明确原因（不静默降级、不假装可用；前端按 `available()` 置灰）

排障开关：`ZIPCALM_DISABLE_BUILTIN_ZSTD=1` 强制禁用内置实现，用于验证回退链真的生效。

**两条必须写清的代价**：

- **Node 最低版本提升到 ≥ 22.15**（另因 `fs.statfs` 也需要较新版本）—— 这是部署约束，已在 `package.json` 的 `engines` 与启动自检里体现
- zstd API 标注 **Stability: 1 - Experimental** → Node 大版本升级时必须回归 zstd 往返用例

**已排除的候选**：

| 候选 | 结论 |
|---|---|
| 原生绑定 `@mongodb-js/zstd` | 性能最好但需在目标机编译，NAS/ARM 易卡死 |
| WASM `zstd-codec` / `@bokuweb/zstd-wasm` | 零编译但性能与内存差一档，仅作备用 |
| 外部 `zstd` 二进制 | 依赖系统安装，且本机实测没有 → 仅作回退项 |

## 三、库 vs 二进制：用库，不用二进制

**纯二进制方案的问题**：

- 系统要装 zip / tar / zstd / gzip
- 群晖默认有 tar，但 zip 常要额外装，zstd 肯定没有
- Windows 开发机没问题，但目标 NAS 上要装一堆
- 进度从 stdout 解析，不同工具格式都不一样

**最终方案：全部格式走零依赖路径**

| 格式 | 方案 | 理由 |
|---|---|---|
| zip | `archiver`（写）/ `unzipper`（读） | 纯 JS，事件丰富，进度好做 |
| tar / tar.gz | `node-tar` | 官方库，稳定，纯 JS |
| zstd / tar.zst | **Node 内置 `node:zlib`**（回退系统命令） | 零依赖零编译；可用性由能力探测决定 |

部署时**不需要用户额外安装任何压缩工具**。

## 四、Web 框架与前端图表库

**Web 框架：Fastify**。原生 `http` 在单用户场景够用但缺路由/中间件/鉴权；Express 生态大但相对老旧；Fastify 现代、性能好、内置 schema 校验。

**前端图表库：uPlot**。极轻、零依赖、时间序列专用。不用 ECharts（为一块看板引入巨无霸不划算），也不用 Chart.js。

## 五、可选的纯 JS / WASM zstd 实现

若将来内置 zstd 不可用且系统命令也缺失，备选：

- `@bokuweb/zstd-wasm`
- `zstd-js`（纯 JS）
- `@structured-world/structured-zstd`（Rust 编译的 WASM）

注意：WASM 版本性能不如原生，仅作兜底。
