# 04 压缩模式与黑名单

> 定位：两种打包模式的取舍、黑名单分层与「跳过不等于忽略」的语义。
> 本文结论已与 `server/core/compress/blacklist.js` 实现核对（2026-10-24）。

## 一、两种压缩模式：本质是两个任务模型

「每个文件/文件夹单独压缩」与「压缩成一个包」是两个不同的任务，UI 上必须明确分开：

| 模式 | 任务模型 | 进度单位 | 产物 |
|---|---|---|---|
| 单独压缩（`mode: single`） | N 个子任务 | 「第 X/Y 个文件」 | N 个压缩包 |
| 打包为一个（`mode: bundle`） | 1 个任务 | 「已处理 X/Y 个源文件」 | 1 个压缩包 |

**UI 形态**：单选框（不是两个按钮）—— 两者互斥。默认值可配置。

## 二、两种模式的行为差异

### 模式 A：单独压缩（每个文件夹一个包）

- 选中 N 个文件夹 → 生成 N 个压缩包
- 每个包命名 = 源名 + 格式后缀
- **两层进度**：「第 X/N 个包」+ 当前包内「已处理 Y/M 个文件」
- 空间预检逐个检查：某个文件夹放不下时**跳过它继续压后面的，不整体失败**

### 模式 B：打包为一个

- 选中 N 个项 → 生成 1 个压缩包
- 进度：「已处理 Y/M 个源文件」
- 空间预检一次性检查总量

## 三、黑名单：三层结构

参考 Bandizip 的分层思路（全局设置 / 压缩对话框临时指定 / 预设排除），本项目做成三层：

| 层级 | 内容 | 谁改 | 优先级 |
|---|---|---|---|
| **任务级临时**（`task`） | 本次任务临时排除 | 提交任务时通过 `extraPatterns` 指定 | 最高 |
| **用户自定义**（`user`） | 用户添加的扩展名或文件名模式 | 设置页 | 中 |
| **全局默认**（`global`） | 系统垃圾（见下） | 内置，不可删，可整体关闭 | 最低 |

**命中判定**：按优先级顺序遍历，第一个命中的层与 pattern 即为结果（`{ pattern, layer }`）。

### 全局默认只放系统垃圾

```
Thumbs.db
.DS_Store
@eaDir
```

**为什么不含「已压缩格式」**：默认曾包含 jpg / png / mp4 / zip / docx 等 12 个扩展名，已移除。理由是**打包不总是为了省空间** —— 「把一批照片打成一个包发给别人」是常见需求，默认静默跳过会让打包结果与预期不符。

**机制保留**：这些规则可以显式加进用户层，或在任务级用 `extraPatterns` 临时加。

### 匹配方式

- 按扩展名（`*.bak`）
- 按文件名（`Thumbs.db`）
- 支持分号分隔的多模式（`*.bak;*.tmp`）

### 硬约束：跳过 ≠ 忽略

**黑名单命中后，文件「跳过不压」但必须保留在原目录。** 因为它没进压缩包，若此时删除原文件就永久丢失。

这条在实现上体现为删除集合的定义：

```
删除集合 = 已打包条目 − 已跳过条目
```

详见 `docs/06` 与 `docs/M0/不变量清单.md` 的 INV-02。

## 四、智能跳过：值得压与不值得压

核心目标是节约 NAS 空间，但有些文件不该被压：

| 类型 | 是否值得压 | 原因 |
|---|---|---|
| jpg / png / mp4 / mp3 | ❌ | 已是压缩格式，再压几乎无收益 |
| zip / 7z / rar / gz | ❌ | 已压缩，二次压缩浪费 CPU |
| docx / xlsx / pptx | ❌ | 本质是 zip，再压无收益 |
| 文本 / 代码 / 日志 | ✅ | 压缩比通常 3~10 倍 |
| 数据库备份 / 虚拟机镜像 | ✅ | 压缩比通常 2~5 倍 |
| 未压缩图片（bmp / tiff / wav） | ✅ | 压缩比大 |

**本项目的取舍**：**不默认跳过**，但**在选目录时实时提示**「X 个文件已是压缩格式，压缩收益很小」，并把命中规则与所在层显示出来，由用户决定是否继续。这比"默默跳过"更符合真实使用场景。

## 五、验收要点（M6）

- 选中一个全是 jpg 的文件夹 → 提示「X 个文件已跳过」（若用户层配置了该规则）
- 打包模式下，跳过文件**仍保留在原目录**
- 单独压缩模式下，跳过文件**不生成空压缩包**
- 用户能在设置里添加/删除黑名单扩展名
- **删除原文件时，跳过项不参与删除**（INV-02）

## 六、未实现的能力

- **压缩包密码**：当前不支持给 zip 设密码。若将来支持，需配套「删除原文件前可反查包密码」的防丢失机制（参考 MT 管理器的做法：压缩时记录当前路径下的密码，避免永久丢文件）

## 七、参考过的行为

- Bandizip 的 `bc`（batch compress）= 每个文件/文件夹单独压缩，各自生成同名包
- Bandizip 高速归档的「自动绕过已压缩文件」策略
- Bandizip 的 CRC 校验流程：压缩时计算并存储，测试时比对
