## 六、文档层面的已知问题

| D-3 | RAR 解压的加密包应自动弹密码框（`docs/18` §① 浏览器验收第 3 条） | **已解决**：加密探测从「写死 `plugin.id === 'zip'`」改为「插件自报 `probeEncryption(archivePath)`」——ZIP 复用 `openArchive`+`detectEncryption`，RAR 复用 `inspectEntries` 的加密标志。实测加密 RAR 预检返回 `encrypted=true`，对话框出现「解压密码（该压缩包已加密）」 | 未改前：任务报 `MISSING_PASSWORD` 但界面无密码输入，用户无法重试 | 已对齐 |
| D-4 | RAR 不应出现在压缩格式列表（`docs/18` §① 边界验收第 2 条） | **已解决**：`registry.list()` 透出 `extractOnly`，压缩抽屉在「先过滤再选默认项」后渲染。实测压缩格式只剩 tar / targz / tarzst / zip，默认选中 `tar`，无 RAR | 未改前：RAR 会出现在压缩列表，还可能被默认选中 | 已对齐 |
| D-6 | 加密包解压后的"同一密码再验一次"应由谁执行（`docs/19` P4 原设计：统一 `7z t`） | **改为按格式分流**：`stageVerifyArchive` 优先问插件要 `verifyWithPassword(archivePath, password)`（RAR 用它自己的 `unrar t`），插件没提供才回落 `7z t`（ZIP 的 AES 只有 7z 读得了）。错误码原样透传（`BAD_PASSWORD` / `ARCHIVE_CORRUPTED`），不再一律压成 `VERIFY_FAILED` | 原设计假设"7z 能读所有加密包"不成立：**p7zip 16.02 读不了加密 RAR5**（实测 `Can not open the file as archive`），若仍一律走 7z，加密 RAR 会"产物正确但任务标 failed(VERIFY_FAILED)"。工具能力按格式不同，这类知识属于插件自己 | 已对齐（实现超出原设计） |
| D-5 | 中文文件名不乱码（`docs/18` §① 功能验收第 8 条） | 未达成，且不是本插件代码问题：`unrar 5.70` 对 `s7-chinese.rar` 的 `lb/lt` 输出把非 ASCII 名打成 `?`，解出的文件名为乱码；`LC_ALL=zh_CN.GBK/GB18030/UTF-8` 与 `unrar -scuc` 均无效（unrar 不支持中文代码页），`p7zip 16.02` 对该包直接 exit 2 | 该样本的名字在归档内以非 Unicode 代码页存储，unrar 无中文代码页转换能力 → 属**样本/工具能力限制**。若要验中文名，需用带 Unicode 标志的包重建样本。当前对外行为：能解出、内容正确、名字可能乱码 | 受限（登记） |

## 七、如何判断该改文档还是登记差异

- **文档是设计意图**：写"为什么这么设计、当时的约束是什么"。设计合理但实现另有选择 → **登记差异**，不改文档
- **文档是事实陈述**（契约字段、目录结构、接口签名、配置项名）→ **必须与代码一致**，不一致就改文档
- **实现比设计更好**（如 D-2 的回收站方案）→ 文档按实现更新，并在本文注明"实现超出原设计"
