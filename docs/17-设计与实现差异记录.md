## 六、文档层面的已知问题

| D-3 | RAR 解压的加密包应自动弹密码框（`docs/18` §① 浏览器验收第 3 条） | **已解决**：加密探测从「写死 `plugin.id === 'zip'`」改为「插件自报 `probeEncryption(archivePath)`」——ZIP 复用 `openArchive`+`detectEncryption`，RAR 复用 `inspectEntries` 的加密标志。实测加密 RAR 预检返回 `encrypted=true`，对话框出现「解压密码（该压缩包已加密）」 | 未改前：任务报 `MISSING_PASSWORD` 但界面无密码输入，用户无法重试 | 已对齐 |
| D-4 | RAR 不应出现在压缩格式列表（`docs/18` §① 边界验收第 2 条） | **已解决**：`registry.list()` 透出 `extractOnly`，压缩抽屉在「先过滤再选默认项」后渲染。实测压缩格式只剩 tar / targz / tarzst / zip，默认选中 `tar`，无 RAR | 未改前：RAR 会出现在压缩列表，还可能被默认选中 | 已对齐 |
| D-6 | 加密包解压后的"同一密码再验一次"应由谁执行（`docs/19` P4 原设计：统一 `7z t`） | **改为按格式分流**：`stageVerifyArchive` 优先问插件要 `verifyWithPassword(archivePath, password)`（RAR 用它自己的 `unrar t`），插件没提供才回落 `7z t`（ZIP 的 AES 只有 7z 读得了）。错误码原样透传（`BAD_PASSWORD` / `ARCHIVE_CORRUPTED`），不再一律压成 `VERIFY_FAILED` | 原设计假设"7z 能读所有加密包"不成立：**p7zip 16.02 读不了加密 RAR5**（实测 `Can not open the file as archive`），若仍一律走 7z，加密 RAR 会"产物正确但任务标 failed(VERIFY_FAILED)"。工具能力按格式不同，这类知识属于插件自己 | 已对齐（实现超出原设计） |
| D-5 | 中文文件名不乱码（`docs/18` §① 功能验收第 8 条） | 未达成，且不是本插件代码问题：`unrar 5.70` 对 `s7-chinese.rar` 的 `lb/lt` 输出把非 ASCII 名打成 `?`，解出的文件名为乱码；`LC_ALL=zh_CN.GBK/GB18030/UTF-8` 与 `unrar -scuc` 均无效（unrar 不支持中文代码页），`p7zip 16.02` 对该包直接 exit 2 | 该样本的名字在归档内以非 Unicode 代码页存储，unrar 无中文代码页转换能力 → 属**样本/工具能力限制**。若要验中文名，需用带 Unicode 标志的包重建样本。当前对外行为：能解出、内容正确、名字可能乱码 | 受限（登记）；**2026-10-27 补测确认根因**：这是 `unrar < 6.x` 的 bug —— 同一份 rar5 样本，`unrar 5.70` 解出 `????????????????.txt`（落盘字节 `efbfbe`=U+FFFE + 私有区字符，UTF-8 被误当 UTF-16），`unrar 7.23` 解出正确的 `中文文件名.txt`（`e4b8ad e69687` 标准 UTF-8）。**rar5 里本来就是 UTF-8，不需要猜编码**（猜编码是 RAR4 才有的问题）。解法：升级 unrar ≥ 6.0，或用 `node-unrar-js` 纯 JS 解析兜底（进行中） |
| B-5 | 解压默认目标目录在浅层路径下算错（验证 RAR 时发现） | 现象：归档放在共享根下一层（`/zipcalm-xxx/s2-rar4.rar`）时，`/extract/preflight` 返回的 `targetDir` 为 `/../../../../../zipcalm-xxx/s2-rar4.rar (1)`，提交时被路径白名单以 `PATH_OUT_OF_ROOT` 拒绝 | **与本插件无关**：同一目录下的 `test.zip` 复现完全相同的错误值，说明是既有的默认目标目录推导缺陷（与 RAR 代码路径无关）。影响：共享根浅层归档无法用默认目标解压（手填目标可正常解压） | 待处理（产品侧） |

| D-7 | 7z 三级回退链的②「WASM 引擎（js7z-tools）」 | **已接入（2026-10-27）**：`js7z-tools@2.5.0`（内置 7-Zip 25.01，MT+FS+EC）作为项目依赖装入，`resolveEngine()` 做三级探测（native → wasm → null），WASM 执行走独立子进程并严格等 `onExit`。接入前的历史形态：依赖未安装时 `kind` 保持 null，`available()` 不误报可用，`unavailableReason()` 说明「仅检测到 WASM 引擎但调用适配尚未接入」 | 接入需要三件事：① 新增 `js7z-tools` 依赖（LGPL + unRAR 限制）② 按 MT 版 `callMain` 的**异步 `onExit`** 语义写适配 ③ 预检加 2 GB 输入上限（32 位地址空间）。接入前没有系统 7z 的机器上 7z 格式会整体不可用，现在由 WASM 兜底 | ✅ 已解决（细节见 D-9 / D-10） |
| D-8 | 压缩时向 7z 传条目清单的方式（原计划 `-i@listfile`） | **改为「条目名分批走 argv」**：本机 `p7zip 16.02` 是 `Utf16=off` 构建，读 UTF-8 listfile 里的中文名会报 `???? : No more files`（实测 `-scsUTF-8/-scsUTF-16LE` 也都失败），而中文名走 argv 正常。分批阈值 60 KB 字符，避免 ARG_MAX | listfile 本可一次传几十万条目；argv 分批会多开几次 7z 进程（追加写同一归档），大目录下压缩启动开销略增 | 已对齐（实现方式变更，行为不变） |

| D-9 | 7z 引擎三级回退的落地形态（原设计只写"优先原生 → 否则 WASM"） | **实现比原设计更具体**：① 原生 `7z/7za`（`ZC_7Z_BIN` 设了即**独占**，配错如实报不可用而不是偷偷换一个）；② WASM `js7z-tools@2.5.0`（7-Zip **25.01**）——**每次操作跑独立子进程**、严格等 `onExit` 再读产物；③ 都不可用则置灰（`ZC_7Z_DISABLE_WASM=1` 可临时关 WASM）。另加两条工程约束：**CPU 绑「总核数 − 1」+ `nice` + 全局串行**（否则整机被打满，实测触发宿主"系统 CPU 过载"中断）；**单任务输入 > 2 GB 在写盘前拒绝**并建议 tar.zst | 关键实测差异（原设计没写、实现必须处理）：① MT 版 `callMain` 异步，同步判定会误报"缺产物"——必须等 `onExit`；② js7z 的 7z 输出**直接写真实 stdout**，覆盖 `instance.print` 不生效，所以信封走 stderr、日志走 stdout；③ 同进程复用实例/连建多实例会**挂住**，因此一次操作一个进程；④ 7-Zip 25.01 密码错只说 `Archives with Errors`（不含 password 字样），密码三态必须结合"包是否加密"判定，否则会误报成"压缩包损坏"；⑤ 25.01 的 `Attributes` 写 `D drwxr-xr-x`（16.02 是 `D_`），目录/符号链接判定要同时兼容两种 | 已对齐（实现超出原设计） |
| D-10 | WASM 引擎的落盘位置（原设计默认"像原生一样直接写目标目录"） | **WASM 模式下所有可写路径先落本地盘**（`os.tmpdir()` 下的临时工作目录），再由 Node 搬到目标；原生引擎保持直写零拷贝。原因：WASM 经 Emscripten NODEFS 落盘时会做 chmod/chown/utime，**CIFS 挂载直接拒绝** → 7z 报 `errno=63 : Operation not permitted`（该构建 `errno 63 = EPERM`，已在 js7z.js 的 ERRNO_CODES 里核对）。另：把本地产物搬到 CIFS 目标时**不能用 `fs.copyFile`**（实测必 EPERM，`COPYFILE_EXCL` 同样失败），改用**流式 pipeline**（`readFile+writeFile` 也可，但大包吃内存） | 对照实验（同一份 runner，只改挂载根）：挂 CIFS → `exit=2`、产物 0B、`errno=63`；挂本地 btrfs → `exit=0`、166B；**读 CIFS + 写本地 → `exit=0`**（说明只有"写网络盘"不行，读没问题）。因此修复只需挪可写路径，不需要把输入也拷到本地。这类问题**模块级单测（跑在 /tmp）永远测不出来**，已补"真实服务 + WASM"用例（起服务带 `ZC_7Z_BIN` 假路径 → 走 HTTP 建压缩/解压任务 → 连跑 3 轮） | 已对齐（实现方式变更） |
| D-11 | RAR 引擎回退链（原设计只有"unrar 优先、7z 兜底"） | **改为三级**：① 系统 `unrar`（`ZC_UNRAR_BIN` 设了即独占）→ ② `node-unrar-js@2.0.2`（纯 JS/WASM，内置 unrar 6.1.7）→ ③ 置灰并给原因。新增 `ZC_UNRAR_ENGINE=native\|js` 强制选择、`probe()` 报 `{kind, version, filenameSafe}`。**关键：有原生 unrar 时仍优先原生**（哪怕版本旧），因为实测 js 既修不了文件名、又对损坏包不报错 | **RAR5 中文名乱码的根因实测**（同一份 `s7-chinese.rar`）：`unrar 5.70` → `s7/????????????????.txt`、落盘 `efbfbe ee83a5…`（UTF-8 被当 UTF-16）；`unrar 7.23` → `s7/中文文件名.txt`、落盘 `e4b8ad e69687…`；**`node-unrar-js` 内置的 6.1.7 同样乱码**（`createExtractorFromFile` 与 `fromData` 都一样）。→ 换 js **修不了文件名**，所以 `filenameSafe` 阈值取 7.0，且默认不把 5.70 换成 js。**js 的另外两条限制**：① 损坏包不报错（`s6-broken` 静默只解出 1 个文件，条数/字节比对也抓不到，因为它的清单本身已被截断）② `extract()` 返回 `{files}` 且 **`files` 是惰性迭代，必须消费才会写盘**（只调 `extract()` 不迭代 = 目标目录为空，实测会把正常包误判成损坏） | 已对齐（实现方式变更；能力边界如实登记） |


| D-12 | 外部引擎的限核/超时/串行该放在哪（原设计：各格式插件自己 spawn） | **收口为统一入口 `server/core/engineRunner.js`**：`runEngineProcess({command,args,cwd,timeoutMs,signal,onLine,label})` 内部统一做 ① 绑核（按平台分层）② 优先级 ③ **跨格式全局串行**（一把锁，7z 与 RAR 不能同时跑）④ 超时/取消**整组 SIGKILL**（`detached` + `kill(-pid)`，避免孙进程变孤儿）⑤ 逐行回调。四个调用点全部迁过来：7z 原生、7z WASM、RAR unrar、RAR js；旧的两份 spawn 实现已删除 | 为什么必须收口：限核是**部署环境约束**（本机 3 核，跑满会触发宿主保护，实测造成过一次 503），散在各插件里 → 每加一个格式漏一次；且各插件各有一把串行锁时，一个 7z 任务 + 一个 RAR 任务能**同时**跑，一起打满 CPU（这是收口前的真实隐患）。**跨平台三层**：① 应用层 `-mmt`（只有 7z 原生支持；unrar 无线程参数、7z WASM 库内固定 3 线程）② OS 绑核（Linux `taskset -c`，实测能把 `Cpus_allowed_list` 收到指定核；Windows 用 PowerShell 设 `ProcessorAffinity` + `Idle`，**本机无 Windows 未真机验证**；**macOS 无可用手段 → 如实降级为只 nice**）③ 优先级。**Windows 不用 `cmd /c start /wait`**：`start` 不保证透传子进程退出码，而"code 必须是引擎退出码"是硬要求，故改走 `Start-Process -Wait -PassThru` 后 `exit $p.ExitCode`。跨平台分支由 `scripts/test-engine-runner.mjs`（20 条，注入 platform/探测结果）证明 | 已对齐（架构收口；等价性用迁移前后基线 JSON 逐项比对：7z 原生/WASM 与 RAR 的条目数、字节数、逐文件 sha256、退出码全部一致） |

| D-13 | 乱码文件名怎么处理（原认知："旧版 unrar 中文名有 bug、需换库"） | **实测推翻原认知：是可逆的字节转义，不需要换库**。落地为两处能力：① 解压时自动还原（在共享 `planTargets`、**还原后的名字上**做 zip-slip 判定；撞名保留原名并记日志；`namesDecoded` 进任务结果）② `POST /fs/repair-names` + CLI 修复已解压目录（dryRun 默认 true、绝不覆盖、四类计数、深度/条数上限、从深到浅改名、跳过符号链接）。判定三重校验：含 U+FFFE 标记 / 合法 UTF-8 / 往返一致 | **实测数据**：三款引擎对同一 RAR5 中文名产出的字节**完全一致** `73 37 2f efbfbe ee83a4 …`（U+FFFE + 私有区），解码后都是 `s7/中文文件名.txt`——`unrar 5.70`、`node-unrar-js 2.0.2`（内置 unrar 6.1.7）、`js7z-tools`（7-Zip 25.01）。**locale 陷阱**：默认 locale 与 `C.UTF-8` 输出**有损 `?`**（不可还原），只有 `en_US.UTF-8` / `zh_CN.UTF-8` 给可逆转义 → 引擎 spawn 强制 `LC_ALL=en_US.UTF-8`。**六库实测**：`unrar-async@3.1.0`（Worker Thread + Stream，架构最合适但 API 未适配成功）、`libarchive-wasm@1.2.0`（API 形态未查清）、`7z-wasm@1.2.0` / `sevenzip-wasm@26.5.0`（后者 WASM abort）均未采用；`js7z-tools` 加密错密码**不报错仍落盘**（比 node-unrar-js 差）。结论：**保留现有引擎 + 做解码**，零依赖、零版本要求 | 已对齐（实现超出原设计：原设计只想"修文件名"，实际做成了跨格式共享能力 + 可回修的 API） |

**locale 决定 unrar 输出可逆与否（实测，实现里强制 locale 的依据）**：

| locale | `unrar 5.70` 输出 | 可逆? |
|---|---|---|
| 默认 | 有损 `?` | ❌ |
| **`C.UTF-8`** | **有损 `?`**（陷阱：看着像 UTF-8 却不行） | ❌ |
| `en_US.UTF-8` | `U+FFFE` + 私有区转义 | ✅ |
| `zh_CN.UTF-8` | 同上 | ✅ |

因此 RAR 引擎 spawn 时强制 `LANG/LC_ALL=en_US.UTF-8`（选 en_US 而非 zh_CN：不假设部署机装了中文 locale）。

## 七、如何判断该改文档还是登记差异

- **文档是设计意图**：写"为什么这么设计、当时的约束是什么"。设计合理但实现另有选择 → **登记差异**，不改文档
